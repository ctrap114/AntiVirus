# 主防与驱动关联约定

本文记录 Everbloom Security 当前主防链路的责任边界。设计只借鉴公开的通用思路：行为防护持续观察程序行为，行为序列/签名作为多步证据，再根据策略执行响应；不复制任何厂商的专有实现。

## 责任边界

```text
用户态服务
  HIPS/ETW/沙箱事件
        ↓ 进程 ID + 时间窗口
  行为去重 → 序列关联 → 静态/AI/威胁情报融合
        ↓ 多步决策与回滚计划
  日志/告警/阻断/终止

内核驱动
  固定 ABI 校验 → 设备访问控制 → 高置信度紧急拦截
        ↑ request_id 对齐响应
```

主防决策的所有者是 Rust 用户态服务。驱动只负责低成本、可验证的早期防线，不在内核中复用 `std::string`、`std::vector`、`std::mutex` 或用户态策略对象。

## 请求关联

- `driver/include/everbloom_driver_protocol.h` 是唯一的用户态/内核 ABI。
- 每个请求包含版本、操作码、请求 ID、调用进程 ID、固定长度目标和有界 payload。
- 驱动响应必须回显相同的 `RequestId`；Rust 桥接层拒绝版本或请求 ID 不匹配的响应。
- C++ 用户态核心同样使用该协议中的操作码，避免 Rust、C++ 和 `.sys` 三套常量漂移。
- HIPS 事件在发送给驱动后保留原事件；只有驱动明确返回阻断时才追加 `DriverBlocked` 事件。
- 沙箱结束后会再次读取 HIPS 队列，并且只接收与沙箱 `target_pid` 相同的事件，避免把其他主机进程的告警归因给当前样本。

## 多步主防策略

1. **观察**：采集静态、HIPS、ETW/沙箱、网络威胁情报和模型结果。
2. **关联**：按进程分组；同一行为类别在一个评分窗口内只计一次；使用有序行为序列匹配多步链路。
3. **干预**：驱动明确阻断、命中行为序列、或高置信度多源证据进入 `intervene` 阶段；普通单点告警保留为 `correlate` 阶段，默认不执行回滚。
4. **恢复**：只有存在已验证沙箱报告和回滚记录时才执行回滚；沙箱隔离或清理校验失败时返回错误，不把失败伪装成“安全”。

`FusionDecision` 为保持现有 API 仍返回 `Clean`/`Malicious`，但 reason 中会记录 `stage=correlate|intervene`。后续 GUI 可以据此展示“观察/告警/阻断/恢复”而不需要重新解析规则。

## 驱动部署边界

`driver/sys_driver.cpp` 是控制面；`driver/src/kernel_components.cpp` 已把拦截点落到合适的 Windows 内核回调，共六处：进程创建（可否决）、镜像加载（仅遥测）、文件系统 minifilter、注册表、对象句柄、WFP 网络。因此「把拦截点落到回调」这一项已完成。

仍需在发布前完成：

- 驱动签名与加载策略（每个 `.sys` 独立签名）；
- minifilter altitude 必须使用 Microsoft 分配的区段，不能沿用开发值；
- 保持设备 ACL 仅允许 SYSTEM/管理员访问；
- 在服务端验证调用者身份、目标进程和请求生命周期。

内核紧急门限保持窄口径：短于 5 字节的指示器必须落在词边界上，避免 `"rop"` 这类短针误命中普通单词。该门限只是低成本早期防线，不是检测主体；真正的多步关联仍在用户态服务。

关于把驱动改为「矩阵」形态（多驱动拆分 / 内核整数推理）的可行性与代价，见 `docs/driver_matrix_architecture.md`。

缺少驱动时 Rust 主防仍可运行，并明确处于 degraded mode；缺少沙箱时不会把隔离失败当成恶意检测或安全结论。
