# 12. 检测质量与验证（Detection Quality & Validation）

前 11 章回答的是"**Everbloom 是什么、怎么工作**"。本章回答另一半问题：

> **Everbloom 检测得有多准？误报从哪里来？在哪些样本上会失败？**

必须先把话说清楚：**这一章目前是"验证体系"的设计 + 已跑通部分的实测数据，不是一份完整的效能报告。** 凡是尚未实测的项，本章都显式标注为「待实测」，不做任何估计或推断。文档里出现具体数字的地方，都注明来源与复现命令。

---

## 12.1 为什么需要单独一章

前 11 章建立的是一套**设计契约**：权威 / 证据分级、融合裁决顺序、降级可见、fail-closed 沙箱。这些契约证明的是"系统被设计成什么样"。

它们**不能**证明：

- 融合器的阈值（0.55 / 0.70 / 0.85）在当前启发式权重分布下是否真的合适；
- 启发式 ~55 条规则里，哪些在真实软件上贡献了最多误报；
- 12 维基向量 + 1283 维模型输入在真实样本上的区分度；
- 沙箱在真实机器上的实际耗时与失败率；
- 内核事件环在真实负载下的丢失率。

这些都是**经验量**，只能测出来，不能推导出来。

### 证据链现状（2026-10-01）

本节最初只列出"缺什么"。工具链和合成语料跑通后，这条链已经分成两半：**工程侧已闭环，真实世界侧仍未开始**。

```
设计契约                        ✅ 第 1–11 章
  │
  ├─ 生产装配验证                ✅ 12.6.1 / 12.4.2：ProductionFusion 已接入生产入口
  ├─ 融合决策与标签的对照         ✅ 12.4 结果 4 / 7：1805 条合成语料，逐样本 AttributionRecord
  ├─ 误报归因（层 / 分支 / 规则名）✅ 12.5：可用；逐规则数值贡献仍缺
  ├─ 端到端性能基线              ✅ 12.4 结果 5 / 12.4.3：harness 与生产 NDJSON 各自成 profile
  │
  ✗ 每层在真实样本上的独立表现     ← 缺真实语料
  ✗ 真实良恶性检出率 / 误报率      ← 缺真实语料
  ✗ 动态分支（沙箱 / HIPS / ETW）  ← 缺隔离环境
  ✗ 内核事件丢失率                ← 缺真机驱动负载
```

**已经能回答的问题**：改动有没有让已有行为退化、某个样本走了哪条裁决分支、误报由哪个融合分支与哪些规则名造成、各层在合成语料上的延迟分布。

**仍然回答不了的问题**：真实世界能检出多少、真实良性软件误报率是多少。这两项只能靠外部语料补齐，写代码补不出来。

> 读本章时请注意：12.4 起的实测数据**全部来自合成惰性语料**。它们证明的是引擎行为与可复现性，不是产品效能。

## 12.2 验证体系设计

### 主链路

任何一次可复现的验证，都必须能回答这条链上的每一环：

```
① Sample（样本 + 已知标签）
        ↓
② Layer outputs（每一层的独立输出）
        ↓
③ Fusion inputs（喂进融合器的证据集合）
        ↓
④ Fusion decision（Clean / Suspicious / Malicious + reason）
        ↓
⑤ Ground truth（人工/数据集标注）
        ↓
⑥ TP / FP / FN / TN + 归因
```

**关键点**：② 和 ③ 必须**可导出**。如果只记录最终裁决，就无法回答"是哪一层错了"。

### 四类必须分开统计的指标

把不同性质的错误混在一起统计，会掩盖真正的问题：

| 类别 | 定义 | 关注点 |
|------|------|--------|
| **权威误报（Type B）** | 精确哈希 / YARA / ClamAV / 情报 / 严格序列 / 驱动阻断造成的误报 | **代价最高**——白名单不压制它，用户无法自行排除 |
| **证据误报（Type A）** | 启发式 / AI / 行为 / 静态沙箱经融合后产生的误报 | 可通过阈值、权重、白名单、模型校准调整 |
| **漏报（FN）** | 已知恶意但判 Clean | 按恶意家族分类统计 |
| **降级型不可用** | AI 加载失败、沙箱不可用、规则加载 0 条 | 不是误报也不是漏报，但会让上述指标失真 |

> **Type A / Type B 的区分是本体系的核心。** 系统对二者的处置能力完全不同：
> - Type A 有完整的调节旋钮（融合阈值、规则权重、路径乘数、白名单、模型校准）；
> - Type B 几乎没有旋钮——一条误报的 YARA 规则会命中所有同类合法文件，且白名单压制不了它。
>
> 因此**必须分开统计**，否则一个 Type B 误报会被平均进总体 FP 率里，看起来"只是 0.1%"，实际影响面却大得多。

## 12.3.1 端到端 harness：`engine/examples/eval_harness.rs`

`run_quality_baseline.py` 只测 YARA 与模型两个**孤立**层。它无法回答"这个文件最终被判成什么、因为哪条证据"。补上这条路径的是 `eval_harness`：

```text
manifest → Scanner → 全部已启用层 → ProtectionFusion → verdict
        → AttributionRecord → 指标汇总 → 可选门控
```

它复用**同一 `Scanner` 类型与检测实现**，但自行装配评测 profile；它不是调用生产二进制的 `main.rs::build_scanner()`，因此生产环境额外加载的 hash DB、allowlist、Threat Intel、ClamAV 与环境选项不一定完全一致。生产构造器现已默认装配 `ProtectionFusion::Normal`，与 harness 默认一致；`--no-fusion` 用于保持其余 harness 选项不变的消融对照。要报告"出货完整 profile"仍须通过正式入口运行（见 12.4.2）。

### 用法

```bash
cargo run --release --example eval_harness -- \
    --manifest artifacts/quality-baseline/eval-corpus.jsonl \
    --records-out artifacts/quality-baseline/records.jsonl \
    --json-out artifacts/quality-baseline/eval-summary.json
```

| 参数 | 说明 |
|------|------|
| `--manifest` | 必填，`.jsonl` / `.json` / `.csv` 自动识别 |
| `--records-out` | 逐样本归因记录（JSONL） |
| `--json-out` | 汇总指标（JSON） |
| `--rules` / `--model` / `--model-kind` | 层输入，默认 `data/rules` 与根目录的 `everbloom_feature_cnn.onnx` |
| `--no-yara` / `--no-ai` / `--no-fusion` / `--no-cache` | 关闭对应层 |
| `--response-level` | `aggressive`(0.55) / `normal`(0.70) / `relaxed`(0.85)，用于**阈值校准**；默认 `normal`，与生产 `Scanner::with_default_fusion()` 一致 |
| `--ai-threshold` | AI 独立直接裁决阈值；默认 0.5。生产 NDJSON 默认是 0.9，做生产对照时要显式设 `--ai-threshold 0.9` |
| `--sandbox` / `--sandbox-timeout-ms` | 启用沙箱（慢，需隔离环境） |
| `--max-fp-rate` / `--max-fn-rate` / `--max-p95-ms` / `--min-labelled` | 门控，任一越界即退出码 1 |

### 清单格式

三种语料写法都能直接读：

| 格式 | 说明 |
|------|------|
| `.jsonl` | 每行一个对象：`{"path","label","family","category"}` |
| `.json` | 顶层数组，或 `{"samples":[...]}`（`tests/corpus/manifest.json` 就是这个形状） |
| `.csv` | 表头同列名 |

`label` 同时接受 `"malicious"` / `"benign"`、`1` / `0`、`1.0` / `0.0`、`true` / `false`——仓库里三份语料各用了一种写法。**只有 `path` 必填。**

### 清单合成：`tools/build_eval_manifest.py`

`category` 是误报归因里最关键的切片维度（"哪一类良性文件在被误报"），但现有语料都没有这一列。该工具把它派生出来，并合成一份统一清单：

```bash
python tools/build_eval_manifest.py --out artifacts/quality-baseline/eval-corpus.jsonl
```

它只**重贴标签**，不下载也不伪造样本，且会拒绝写入磁盘上不存在的条目。

### 门控语义（两个必须遵守的规则）

1. **未标注样本不计入任何比率。** 缺 `label` 或标签无法识别时，样本进入 `unlabelled` 桶并从所有分母中排除。把"未知"默认当成"干净"是发布一个好看误报率最省事的方式。
2. **无法判定的扫描不计入比率。** `Skipped`（超限未扫）/ `Error` / `Cancelled` 进入 `undecided` 桶。引擎不可用不能被算作"没检出"。
3. **`Incomplete` 要分两种，不能一刀切。** 扫描器把一个"跑完但什么都没命中"的结果记成 `reason = "unknown"`，并**刻意拒绝**把它叫 `Clean`——"没找到"不等于"证明干净"（`ScanResult::verdict` 有一条测试专门钉住这个语义）。但对检出质量而言，问题是另一个：**引擎没有报警**，所以它必须进入真阴分母，否则任何语料上 FP 率都算不出来（实测第一版就是 `TN 0` / `FP rate n/a`）。
   判据是**有没有 `error`**：

   | 记录 | 判定 |
   |------|------|
   | `reason = "unknown"`、`error = None` | **阴性决策**（跑完了，没报警） |
   | `reason = "sandbox_unavailable"` 等，`error` 非空 | 仍然 `undecided`（根本没评估） |

   这是**评估层**的解释，生产语义未改动。

| 指标 | 实测值 |
|------|--------|
| 总耗时 | **20,416 ms**（墙钟 7.4 s，含启动与模型加载） |

### 结果 6：AI 层单文件延迟 —— ✅ 已实测（并且推翻了一个错误结论）

`engine/examples/ai_probe.rs` 用引擎自己的计数器把三种耗时拆开：

| 场景 | 每次推理 | 排队等待 |
|------|----------|----------|
| 从主线程串行调用（`serial`） | **4.0–4.3 ms** | 0.001 ms |
| 从扫描器的 rayon worker 调用（`par`） | **修复前 5–18 s / 修复后 3.8–5.0 ms** | 修复后 3.6 ms |

模型加载 10–12 ms，`fallback=false`（ONNX 图真的执行了）。

**这一条推翻了本章初稿的一个结论。** 初稿写的是"AI 层 ≈ 1.0 s/文件、占其余流水线 65×"，那是把**排队超时**当成了推理耗时。真实推理是 4 ms，慢了 250 倍的是别的东西——见 12.4.1。

## 12.4.1 harness 交付当天就抓到的两个缺陷（已修）

写这一章的目的是"把验证从 Wiki 里的设计变成代码和实测数据"。**在第一次真正跑通全量语料之前，这条测量路径本身暴露了两个生产缺陷**——它们都是"不跑起来就永远看不见"的类型。记录在这里，因为它们的价值高于本章任何一张指标表。

### 缺陷一：`ThreadPool::install` 跨池调用把 4 ms 变成 5–18 s

**症状**：harness 在 25 条样本上跑不完；1805 条跑 21 分钟无输出。逐样本记录显示 22/25 的 `reason = scan_error`，错误文本是：

```text
AI inference failed: inference error: AI inference queue is full; request was not scheduled
```

`duration_ms` 全部整齐地落在 **5,005–5,024 ms**——这正是 `EVERBLOOM_AI_QUEUE_TIMEOUT_MS` 的默认值，说明耗掉的是**排队超时**，不是推理。

**定位过程**（关键是把三个变量分开）：

1. 分层隔离：`--no-ai --no-yara` 25 条 1 s，`--no-yara` 25 条 26 s → 时间全在 AI 层。
2. `ai_probe` 从主线程串行调用：**4 ms/次**，排队 0.001 ms。AI 层本身没问题。
3. `ai_probe` 改成从 `into_par_iter` 的 worker 里调用（复刻扫描器的真实嵌套）：**5–18 s/次**。
4. 批量阈值：n=1/2/3/4 全部正常，**n=8 直接崩**（2 成功 / 6 失败，10 s/次）。

**根因**：`AiModel::infer_path_with_cancel` 把推理放进**专用** rayon 池执行：

```rust
match AI_POOL.as_ref() {
    Some(pool) => pool.install(run),   // ← 跨池 install
    None => run(),
}
```

而扫描器是在**全局** rayon 池的 worker 里调用它的（`scanner.rs` 的 `paths.into_par_iter()`）。`ThreadPool::install` 从**另一个池的 worker** 调用时会阻塞调用方 worker，再叠上 ensemble 模式内部的 `rayon::join` / `par_iter`，两个池互相饿死。**这不是容量问题**——把 AI 池调到 1 线程、把许可容量调到 1，每种组合都一样糟：

| `EVERBLOOM_AI_THREADS` / `MAX_IN_FLIGHT` | 每次推理 |
|---|---|
| 1 / 2（默认 2） | 6.3 s |
| 1 / 1 | 15.0 s |
| 4 / 4 | 8.0 s |
| 2 / 1 | 10.0 s |

积压把许可闸门撑爆 → 排队请求在 5 s 后**返回硬错误** → 扫描器把整个文件判成 `scan_error`。

**修复**（`engine/src/layers/ai.rs`）：调用方已经是 rayon worker 时**不再跳池**，直接在调用方 worker 上跑。真正的并发上限仍然是上面的许可闸门，池跳本来就是多余的。

```rust
let inline = rayon::current_thread_index().is_some();
let result = match AI_POOL.as_ref() {
    Some(pool) if !inline => pool.install(run),
    _ => run(),
};
```

**效果**（`ai_probe`，同一台 12 核机、同一个模型与样本）：

| n | 修复前 | 修复后 |
|---|--------|--------|
| 8 | 2 成功 / 6 失败，10.0 s/次 | **8/8，墙钟 21 ms** |
| 25 | 5 成功 / 20 失败，12.0 s/次 | **25/25，墙钟 55 ms** |
| 100 | — | **100/100，墙钟 205 ms，0 拒绝** |

harness 侧（n=25，`--no-yara`）：

| | 修复前 | 修复后 |
|---|---|---|
| 错误数 | **22 / 25** | **0 / 25** |
| P50 延迟 | 5,015 ms | **10 ms** |
| 墙钟 | 30.6 s | **1.4 s** |
| 1805 条全量 | 21 分钟未完成（kill） | **7.4 s 完成** |

> **这是生产缺陷，不只是 harness 的问题。** 生产默认 `EVERBLOOM_AI_ENSEMBLE=true`（`main.rs` 的 `unwrap_or(true)`），扫描器同样是 `spawn_blocking` + `into_par_iter`，所以**任何多文件批量扫描都会走到这条路径**。单文件扫描不受影响（`into_par_iter` 只有一项，闭包在非 rayon 线程上执行），这也解释了为什么它一直没被发现。

### 缺陷二：AI 队列繁忙 = 整个文件扫描失败

即使上面修好了，闸门的设计本身还是错的。原实现里 `acquire_ai_permit` 超时返回 `AiError::Infer(...)`，扫描器把它当成致命错误：

```rust
Err(e) => {
    let message = format!("AI inference failed: {e}");
    res.reason = "scan_error".to_string();
    res.error = Some(message);
    return res;          // ← 整个文件不再有结论
}
```

后果是：**AI 排队繁忙，一个本来会被 YARA / 哈希 / 启发式判定的文件，变成"没有任何结论"**。这直接违反 12.6 的两维模型——AI 是**证据源**，不是**权威源**，证据源不该有否决权。

**修复**（两处）：

1. `ai.rs`：新增 `AiError::Busy`，与 `Infer` 区分开；`infer_path_with_cancel` 遇到 `Busy` 时**降级为带标记的启发式估计**（复用已有的 `is_fallback` 机制）而不是抛错。
2. 把降级标记一路带到归因记录：`ScanResult` 新增 `ai_fallback_reason`，`AttributionRecord` 的 `ai` 贡献项据此填 `unavailable`。

**顺带修掉一个 §12.5 的诚实性缺口**：以前 `infer_sample_from_model` 内部已经有启发式兜底，但 `is_fallback` 在 `scanner.rs` 就被丢掉了。结果是归因记录里无论"模型真的跑了 0.47"还是"模型没跑、启发式顶了个 0.47"，都显示成同一句 `ai = 0.47`。**误报归因最不能容忍的就是这种混淆**——现在记录里能直接看出来。实测这一轮 1805 条中降级数为 **0**（模型全程正常执行），这个"0"本身也是有信息量的。

### AI 并发闸门容量校准（2026-10-01 实测并调整）

跨池缺陷修复后，单次推理约 4 ms，原默认 `min(available_parallelism, 2)` 会让 4 线程扫描池有一半 worker 等 AI 许可。用 `ai_probe` 固定全局扫描池 4 线程、同一模型与 7 KiB 样本，每个容量跑 500 次、重复两轮：

| `EVERBLOOM_AI_MAX_IN_FLIGHT` | 墙钟（两轮） | 平均 AI 排队 / 请求 | 平均推理 / 请求 | 拒绝 |
|---:|---:|---:|---:|---:|
| 1 | 1.94–1.96 s | 11.35 ms | 3.86 ms | 0 |
| 2（旧默认） | 0.98–1.02 s | 3.76 ms | 3.97 ms | 0 |
| 4 | 0.57–0.64 s | <0.001 ms | 4.45 ms | 0 |
| 8 | 0.54–0.56 s | <0.001 ms | 4.14 ms | 0 |

独立的 400 文件端到端复验也给出相同判据：容量 1/2/4/8 的 confusion matrix 完全一致；均值分别 **15.58 / 9.87 / 9.64 / 9.74 ms**，P95 为 **17 / 12 / 12 / 12 ms**。从 2 提到 4 有轻微收益；提到 8 没有端到端收益。容量 4 是**足够且有根据的拐点**，不再盲目放大。

因此 `ai_permits()` 默认已从 `min(available_parallelism, 2)` 改为 **`min(available_parallelism, 4)`**，与 `Scanner::configure_worker_pool` 的默认最多 4 个扫描 worker 对齐；仍可用 `EVERBLOOM_AI_MAX_IN_FLIGHT` 显式调低（受可用并行度与 4 的上限约束）。这只是吞吐/排队校准，不改变任何检测阈值或判定结果。

容量 4 下同一份 1805 条语料连续三轮：confusion matrix 均为 **TP 393 / FP 1 / TN 641 / FN 770 / undecided 0**；mean **10.18–12.85 ms**、P50 **10–12 ms**、P95 **14–19 ms**、P99 **16–30 ms**。墙钟 **6.5–8.9 s**。单轮 max 出现 399 ms 长尾，故这些延迟是本机构建机观测值，不是 SLA。新默认的全量性能与 500 次微基准一致：排队下降、检测结论不变。

### 结果 7：Production Fusion 接线前后与 harness 消融对照 —— ✅ 已实测

本次把 Fusion 接到 `main.rs::build_scanner()` 后，以同一 1805 条 manifest 做了三组（外加生产入口前后复验）对照。请求共同使用 heuristics/YARA/AI 开启、`ai_threshold=0.9`、沙箱关闭、AI permit=4。所有 1805 个样本都有结果帧。

**能得出的结论要精确：**

1. 生产接线已经确认有效：当前正式入口把 Fusion 装配到同一 `Scanner` 后，Normal Fusion 的静态融合运行；生产二进制三态输出与 harness 同一输入配置的目标分布一致。
2. 这套语料禁用沙箱、没有动态事件，主要测静态融合。`static_high` 对 357 个 API-heavy 样本报告 `heuristic=1.00 / ai≈0.47`，在到达单源 override 之前就已定案，所以最终标签与分支归因都稳定。override 本身在该区间的行为见 12.6.2。
3. 因此不能把“Fusion 已接线”直接说成“Fusion 提高了本语料检出率”。本数据上的 TP/FP/FN 数值相同；要检验动态 HIPS/ETW/行为/沙箱分支，需要隔离环境和明确配置的 `--sandbox` 语料；要评价真实效能仍需真实良恶性样本。
4. A 的 harness no-fusion 与 B 的生产历史基线是不同装配 profile，**不用于单独估计 Fusion 效应**。判断 Fusion 对这套固定样本的增量，应看同 harness 下 A↔C；判断真实生产接线，应看 B↔D。数据与逐样本输出：`artifacts/quality-baseline/fusion-ablation-comparison.json`、`harness-{no_fusion,normal_fusion}-records.jsonl`、`production-{no-fusion,normal-fusion}-records.jsonl`。

### 12.4.3 基准 profile 分类（性能数字必须带 profile 才能比较）

上表里同时出现了 `6.51 s`（harness）与 `26.88 s`（生产 NDJSON）。**这两个数不能互相比较**——它们测量的是不同的东西。为避免"引擎平均 10 ms"和"生产扫描 26 秒"看起来自相矛盾，本章的性能数字一律按下列 profile 标注，跨 profile 不做比较：

| Profile | 入口 | 包含什么 | 不包含什么 |
|---------|------|----------|------------|
| **Layer** | `ai_probe`、`run_quality_baseline.py` | 单层自身的推理 / 匹配耗时 | 流水线编排、I/O、进程启动 |
| **Harness** | `eval_harness` | 完整 Scanner 流水线，**进程内并行**，显式装配的评测 profile | 生产额外数据库、allowlist、Threat Intel、ClamAV、单请求单进程开销 |
| **Production NDJSON** | `everbloom_engine --ndjson` | 真实 `build_scanner()` 装配，**每个文件一个请求、串行**，含响应序列化与 stdout 刷新 | GUI 事件循环、内核/驱动交互、真实磁盘 I/O 抖动 |
| **GUI real workflow** | GUI + 引擎 | 端到端用户可见延迟 | —（**尚未测量**） |

已实测的三个 profile 的对应数字：

| Profile | 语料 | 观测 |
|---------|------|------|
| Layer（AI 单文件推理） | 7 KiB 合成样本 × 500 | 推理 3.8–4.5 ms；排队 <0.001–11.35 ms（随许可容量变化） |
| Harness（含 Fusion） | 1805 条 | 平均 10.26–12.85 ms/文件；P95 14–19 ms；墙钟 6.5–8.9 s |
| Production NDJSON | 1805 条 | 墙钟 26.88 s（约 14.9 ms/文件），逐请求串行 |

**结论**：harness 与生产 NDJSON 的差异主要来自**每文件一次请求/响应的串行开销**，不是引擎算得更慢。要报告"引擎多快"用 Layer，要报告"批量扫描多快"用 Harness，要报告"出货二进制实际多快"用 Production NDJSON。GUI 端到端延迟仍未测（见 12.7）。

## 12.5 误报归因系统（False Positive Attribution）

### 问题

当前的反馈是二值的：`Clean` / `Suspicious` / `Malicious` + 一段 `reason` 字符串。

当用户报"绿色安装包被误报"时，能拿到的只有类似：

```
fusion:static:stage=correlate:heuristic=0.76:ai=0.31:combined=0.49:corroboration=0.31
```

这告诉你"走了静态加权分支、两个分数分别是多少"，但**不告诉你这 0.76 是由哪几条规则凑出来的、路径乘数放大了多少、哪些 API 命中了**。

于是唯一的处置手段就退化成"把总分调低"——这会同时牺牲真阳性。

### 设计：逐次误报的完整归因记录

目标是为每一次判定导出一份**可逐项复核**的结构：

```jsonc
{
  "sample": "C:/Users/x/Downloads/setup.exe",
  "verdict": "Malicious",
  "stage": "correlate",
  "fusion_branch": "fusion:static",

  // ---- 启发式逐项贡献 ----
  "heuristic": {
    "total": 0.76,
    "path_context": { "matched": "Downloads", "multiplier": 1.05 },
    "families": [
      { "id": "api_injection_chain",          "weight": 0.70, "contribution": 0.70 },
      { "id": "packer_detected",              "weight": 0.10, "contribution": 0.10 },
      { "id": "timestamp_anomaly",            "weight": 0.05, "contribution": 0.05 }
    ],
    "matched_apis":     ["CreateRemoteThread", "VirtualProtect", "WriteProcessMemory"],
    "matched_strings":  ["defender", "crowdstrike"],
    "entropy": { "high_windows": 4, "windows": 96, "threshold": 7.40 }
  },

  // ---- 其它层 ----
  "ai":            { "score": 0.31, "is_fallback": false },
  "behavior":      { "score": 0.00, "indicators": [] },
  "sequence":      { "strict": [], "tolerant": [] },
  "static_sandbox":{ "families": [["injection", 0.30]], "calibrated": 0.30 },
  "yara":          { "matches": [] },
  "hash":          { "exact": null, "fuzzy": null },
  "threat_intel":  { "matches": [] },
  "driver":        { "blocked": false },

  // ---- 决策 ----
  "fusion": { "strongest": 0.76, "weakest": 0.31, "combined": 0.49,
              "threshold": 0.90, "corroborated": false }
}
```

有了这份记录，才能回答：

| 问题 | 靠哪个字段 |
|------|-----------|
| 是启发式本身错了，还是融合校准错了？ | `heuristic.total` vs `fusion.*` |
| 是单条规则太重，还是多条叠加？ | `heuristic.families[].contribution` |
| 路径乘数有没有把它推出阈值？ | `heuristic.path_context` |
| 是不是安全产品名称识别触发的？ | `heuristic.matched_strings` |
| 高熵是不是主因？ | `heuristic.entropy` |
| AI 有没有"帮倒忙"？ | `ai.score` + `fusion.combined` |
| 权威层是否参与？ | `yara` / `hash` / `threat_intel` / `driver` |

### 实现落点（已落地）

归因记录已实现于 `engine/src/attribution.rs`，由 `eval_harness` 消费。

| 类型 | 作用 |
|------|------|
| `AttributionRecord` | 单样本完整记录：`sample` / `label` / `is_malicious` / `family` / `category` / `verdict` / `reason` / `fusion` / `contributions[]` / `duration_ms` |
| `EvidenceContribution` | 单层贡献：`source` / `authority` / `confidence_basis` / `fired` / `score` / `detail[]` / `unavailable` |
| `FusionBreakdown` | `ProtectionFusion` 决策的分解：`branch` / `stage` / `heuristic` / `ai` / `combined` / `corroboration` / `evidence` / `payload[]` / `raw` |
| `DetectionAuthority` + `ConfidenceBasis` | 见 12.6 的两维拆分 |
| `EvaluationSummary` | 汇总指标：两套混淆矩阵、分支直方图、按类别的分支分布、误报来源与规则排行、延迟分位数 |
| `GateLimits` | 门控阈值 |

**关键设计选择：解析 `reason` 而不是改 `FusionDecision`。**

`ProtectionFusion::evaluate` 已经把决策依据编码进了 `reason`
（`fusion:static:stage=correlate:heuristic=0.76:ai=0.31:combined=0.49:corroboration=0.31`）。
`FusionBreakdown::parse` 把它还原成结构体，于是：

- **零算法改动**——不需要动 `fusion.rs` 的判定逻辑，也就不会引入行为回归；
- **缓存重放也保留归因**——`cached:` 前缀会被剥掉再解析，`raw` 字段保留原串以便发现 schema 漂移；
- 8 种 `fusion:` 分支形状各有单元测试覆盖（含 `fusion:atc:<score>:...` 这种"裸浮点在 `key=value` 之前"的例外）。

**新增的 `ScanResult` 字段：`heuristic_indicators: Vec<String>`。**

原先 `ScanResult` 只带 `heuristic_score: Option<f32>`，明细被丢弃——而"这 0.76 是哪几条规则凑出来的"恰恰是误报调查唯一需要的答案。该字段在启发式阶段就地填充（二进制与脚本两条路径都填），并同步加入 `CacheScanResult`，使缓存命中仍能自解释。同名字段已在 `scanner.rs` / `ndjson.rs` / `cache.rs` 的**全部**构造点补齐。

> 新增 `ScanResult` 字段会改变 NDJSON 帧的 JSON 形状。GUI 侧 `WinUIEngineClient.cpp` 的 `DecodeJsonLine` 是按名字取值、缺字段回退默认的（`NamedString` / `NamedNumber` / `NamedBool` 都带 fallback），因此**新增可选字段对旧 GUI 是兼容的**。

### 仍然缺失的归因字段（诚实声明）

上面那张 JSON 示例里的字段**并非全部已实现**。当前实际能拿到的与目标的差距：

| 目标字段 | 现状 |
|----------|------|
| `heuristic.families[].weight` / `.contribution` | **缺**——只有规则名列表，没有每条规则的权重与贡献 |
| `heuristic.path_context.multiplier` | **缺**——路径乘数参与了打分但未导出 |
| `heuristic.matched_apis` / `.matched_strings` | **缺**——命中过程未收集 |
| `heuristic.entropy.high_windows` | **缺**——`EntropyProfile` 未进入 `ScanResult` |
| `ai.is_fallback` | ✅ **已补**（2026-10-01）——`ScanResult.ai_fallback_reason` → `contributions[ai].unavailable`。以前模型真跑的 0.47 和启发式顶替的 0.47 在记录里长得一样，现在能分辨（见 12.4.1 缺陷二） |
| `hash.exact` / `.fuzzy` | **部分**——仅能从 `reason` 前缀（`hash:`）判断命中，取不到摘要值 |
| `threat_intel.matches` | **部分**——同上，仅 `reason` 前缀 |
| `fusion.threshold` | ✅ **已补**（2026-10-01）——`FusionBreakdown.threshold`；`fusion:high_confidence_override` 直接带 `threshold=` 字段，不再需要从 `corroboration` 反推 |

要补齐这些，需要在 `HeuristicScore` 上返回逐规则贡献（而不是仅 `indicators: Vec<String>`），并在 `ScanResult` 上增加熵剖面与路径上下文。这属于**扩展打分器的返回结构**，不是改判定逻辑，因此可以在不改变现有判定的前提下分步完成。

**当前能回答的问题**（用已实现的字段）：

- 误报走了哪个融合分支？→ `fusion.branch` + `fusion.stage`
- 是启发式、AI，还是两者一致？→ `fusion.heuristic` / `fusion.ai` / `fusion.combined` / `fusion.corroboration`
- 哪些**规则名**参与了这次误报？→ `heuristic_indicators`（可跨样本聚合成排行榜）
- 哪些层在这个误报上"开火"了？→ `contributions[].fired`
- 哪一类良性文件最容易进 `fusion:static`？→ `category` × `fusion.branch`

**当前还回答不了的问题**：单条规则的**权重贡献**、路径乘数放大了多少、哪些 API/字符串命中、熵窗口分布。

## 12.6 Detection Confidence 与 Detection Authority 应当拆成两个维度

当前文档（以及实现）把两件事绑在一起：

```
命中 → Malicious
```

但"**有多确定**"和"**能不能被覆盖**"是两个独立的属性。

### 两个维度的定义

| 维度 | 含义 | 取值 |
|------|------|------|
| **Authority（权威性）** | 这条证据能否**独立**产生裁决、能否被白名单覆盖 | `authoritative` / `evidential` |
| **Confidence（置信度）** | 这条证据本身有多可靠 | `[0, 1]` |

### 按两维重新看现有来源

| 来源 | Authority | Confidence | 备注 |
|------|-----------|------------|------|
| 精确哈希（SHA-256） | 权威 | ≈1.0 | 碰撞概率可忽略 |
| 模糊哈希（ssdeep ≥ 85） | 权威 | 高 | 但只在对方已知恶意时才产结论 |
| YARA 命中 | 权威 | **规则而定** | 第三方规则质量参差；宽泛规则可能高置信地误报 |
| ClamAV 命中 | 权威 | 高 | 依赖 clamd 签名库质量 |
| 威胁情报（confidence ≥ 70） | 权威 | 中高 | 受情报时效与来源影响 |
| 严格行为序列 | 权威 | 高 | 有序签名，噪声容忍度低 |
| 驱动阻断 | 权威 | **确定** | 执行结果，非观察 |
| 启发式 | 证据 | `[0,1]` | 单条最高 0.74 |
| AI | 证据 | `[0,1]` | 12 维 + 64 KiB 采样 |
| 行为评分 | 证据 | `[0,1]` | 需跨类型组合 |
| 静态沙箱 | 证据 | `[0,1]`（≤0.95） | 多族佐证 |
| 解包 / 内存快照 | 证据 | — | |

### 这张表揭示的问题

**"权威"这一列里，Confidence 差别很大。** 尤其：

- **YARA 的置信度完全取决于规则本身**。一条写得太宽的规则，会以"权威"身份产生大批无法被白名单覆盖的误报——这正是 Type B 误报的主要来源；
- 而驱动阻断的置信度是**确定的**（它就是执行结果）。

**建议的方向**：

1. 在规则/情报层面**显式标注置信度**，而不是所有命中一律按最高权威处理；
2. 让"权威"与"可覆盖性"解耦——例如允许管理员对**特定规则 id** 做例外，而不是只能整条白名单路径；
3. 在报告里同时输出 Authority 与 Confidence 两列，让用户知道"这是硬判定还是软判定"。

**已落地的部分**：`engine/src/attribution.rs` 现在把两个维度建模为两个独立枚举，并由 `source_profile()` 这一张表统一裁定：

```rust
pub enum DetectionAuthority { Authoritative, Evidence }

pub enum ConfidenceBasis {
    Deterministic,  // 字节比较，不是判断
    Signature,      // 签名质量取决于作者
    Model,          // 模型输出，只能与同版本模型比较
    RuleSum,        // 手工加权求和，序数而非标定值
    Observed,       // 观察执行得到
}
```

`ConfidenceBasis` 刻意是**分类而不是概率**——这样消费者不会把标定过的模型输出与未标定的规则求和混在一起比较。同一个 `source_profile()` 表同时供判定与指标使用，因此不会出现"代码里算证据、指标里算权威"的分裂。

第 3 条（报告里输出两列）也随之达成：`AttributionRecord.contributions[]` 每一项都带 `authority` 与 `confidence_basis`。

第 1、2 条仍未实现——它们需要改规则/情报的**数据格式**，不属于归因层的工作。

### 12.6.1 Production Fusion 曾缺少装配；现已接入并完成首轮对照

**原缺陷（2026-10-01 接线前）**：`Scanner::new()` 中 `fusion: None`；主程序的 `main.rs::build_scanner()` 未调用 `with_fusion()`，而 `scanner.rs` 静态证据和沙箱后融合两处均被 `if let Some(fusion)` 守卫。Harness 虽复用 `Scanner` 类型与层实现，却自行装配 Fusion——两者的 assembly profile 不同。

**已完成修复**：新增 `Scanner::with_default_fusion()`，将生产默认封装为 `ProtectionFusion::default()`（`FusionResponseLevel::Normal`，阈值 0.70），并在 `engine/src/main.rs::build_scanner()` 调用。NDJSON 与 legacy IPC 共用这一 Scanner 实例，所以两种生产传输入口都覆盖。Harness 注释也已改成准确表述：复用 Scanner 和检测实现，但不是调用生产的 build_scanner；生产 profile 可能额外加载数据库、allowlist 和服务。

IPC 传输同步补齐一个原有缺口：非恶意的 `Suspicious` Fusion 结果此前会被 `malicious || error` 过滤而不发送。现按 per-item `status="suspicious"` 发出；汇总 `threat_count` 仍只统计 `Malicious`，保持原协议含义。

测试覆盖：生产默认 Fusion 已装配且 Normal 静态输入产生 `fusion:static:stage=correlate`；IPC 的 Suspicious response 被保留；已有 12 条纯 Fusion 分支测试通过。接线前遗留 `everbloom_engine.exe` 与接线后的真实主程序各在同一 1805 清单、`ai_threshold=0.9`、sandbox off 下经 NDJSON 测量；Harness 也以相同 AI 阈值及 `--no-cache` 做 no-Fusion / Normal Fusion 配对。完整混淆矩阵、profile 定义和边界见 [12.4.2](12-检测质量与验证.md#1242-production-fusion-接线前后与-harness-消融对照-已实测)。

**首轮结果不是“检出率提升”**：四个 profile 的 TP/FP/TN/FN 都为 **393/1/641/770**。但 Normal Fusion 将 357 个 API-heavy 样本的原因从 `heuristic_high` 变为 `fusion:static_high`，提供了分支归因。样本全为合成静态语料且 sandbox 关闭，不能覆盖动态行为/HIPS/ETW/沙箱分支，也不能代表真实世界检测效能。生产 Scanner 原有 `heuristic_score >= 0.8` / AI 阈值直接裁决 fallback 仍保留，因此本轮这些静态阳性在无 Fusion 与 Normal Fusion 下最终标签相同。

**仍需闭环**：给真实生产请求场景提供隔离的动态分支测试；逐条验证 sandbox/HIPS/ETW 等输入进入 Fusion 的 PID 关联与策略；再收集真实良性安装包与真实恶意语料。不要仅凭“Fusion 现已接线”而宣称用户侧检测改善。

### 12.6.2 契约：Fusion 是唯一裁决中心，`high_confidence_override` 是它内部的一条具名规则

12.6.1 接线后暴露出一个语义冲突，必须正式定义，否则会出现"架构说 Fusion 是唯一裁决器，Scanner 又在 Fusion 外面裁决"：

- 前文（含 §5.9）声明最终裁决是 `FusionDecision`；
- 但 `scanner.rs` 同时保留了一条 `heuristic_score >= 0.8` / `ai_score >= ai_threshold` 的**直接裁决 fallback**；
- 更糟的是这条 fallback 在 Fusion 已经给出 `Suspicious` 之后运行，并**用 `heuristic_high` 覆盖掉刚写入的 `fusion:` 原因**——归因记录因此丢失了分支信息。

#### 正式定义

**三类来源，两条通道：**

| 类别 | 成员 | 能否直接裁决 |
|------|------|--------------|
| **Authority（权威）** | 精确哈希、YARA、ClamAV、威胁情报 IOC、严格序列、驱动阻断 | ✅ 可以，短路流水线 |
| **Evidence（证据）** | 启发式、AI、行为分、静态沙箱、容忍序列、HIPS | ❌ 必须经 Fusion 佐证 |
| **Authority Gate（权威闸门）** | `high_confidence_override` | ✅ 可以，但**是 Fusion 内部的一条规则** |

关键点在于第三类：**单个证据源只有在一条具名、有公布阈值的闸门放行时才能单独定案**。闸门本身是权威，被放行的分数仍然是证据——两者在归因记录里分开表达，不再混为一谈。

```
Evidence（heuristic / ai / behavior / static_sandbox / tolerant_sequence / hips）
        │
        ▼
ProtectionFusion::evaluate()
  1 driver-blocked        ┐
  2 strict sequence       │ 佐证类规则，优先级最高
  3 tolerant sequence     │
  4 behavior score        │
  5 static high-confidence│
  6 static weighted agreement
  7 high_confidence_override  ← 唯一的单源裁决规则
  8 sandbox_flags / hips  ┘
        │
        ▼
FusionDecision ──► 最终 verdict
```

#### 实现约束

1. **规则在 `fusion.rs` 内，不在 `scanner.rs` 内。** `HIGH_CONFIDENCE_HEURISTIC_OVERRIDE = 0.80` 是 `layers::fusion` 的公开常量；AI 那一臂使用请求级 `ai_threshold`，经 `FusionInput::ai_threshold` 传入。
2. **不覆盖佐证分支。** override 排在 1–6 之后，所以驱动阻断、严格序列、ATC、双引擎一致仍然保留自己的 `reason`；override 只在 Fusion 本来会回答 `Suspicious`/`Clean` 时才触发——正是过去被 Scanner 外部裁决的那一批。
3. **不触发回滚。** `rollback: false`：分数是证据，不是执行结果；驱动阻断与严格序列才是。
4. **`scanner.rs` 的外部 fallback 只在 `fusion.is_none()` 时可达**，并注明这是 `--no-fusion` 消融与旧行为的兼容臂，不是第二个裁决中心。
5. **归因记录显式区分闸门与证据。** `contributions[]` 新增 `high_confidence_override` 项，`authority = authoritative`；`heuristic` / `ai` 仍是 `evidence`。`FusionBreakdown` 新增 `threshold` 字段，因此记录能显示"0.85 相对 0.80"而不只是"0.85"。

#### 后果与边界

- 本轮 1805 条语料**结果不变**：357 条走 `fusion:static_high`（1.00 ≥ 0.90），在到达 override 之前就已定案；因此 override 在这批语料上触发 0 次。这正是"契约修正、行为保持"的证据，而不是"改了没用"。
- 过去被 override 覆盖 reason 的那批样本（启发式 0.80–0.90 且未被佐证）现在会以 `fusion:high_confidence_override:...:threshold=0.80` 记录，分支可追溯。合成语料未覆盖该区间。
- **仍未解决**：`heuristic_high` / `ai_high` 这两个历史 reason 串在 `--no-fusion` 路径下保留，`ndjson.rs` 的威胁命名对两条路径给出相同的用户可见名称，避免同一份报告在接线前后改变含义。

## 12.8 绿色软件误报：专项排查方案

这是当前最值得优先做的一项。前 11 章给出了足够的线索来定位问题，不需要盲目调权重。

### 可疑的累积路径

按 [第 5.3 节](05-检测层详解.md#53-启发式层heuristicrs3090-行) 与 [第 5.9 节](05-检测层详解.md#59-融合层fusionrs) 的实现，绿色安装包最可能的误报路径是**多条合法特征同时出现**：

```
绿色/便携安装包
      │
      ├─ 高熵（自解压、内嵌资源、压缩数据）
      │     → entropy 窗口计数上升
      │
      ├─ API 指标（安装程序常做的事）
      │     → VirtualProtect / CreateRemoteThread 类调用
      │     → 甚至 WriteProcessMemory（某些安装器确实会注入）
      │
      ├─ 安全产品名称字符串（安装器扫描已装 AV 做兼容处理）
      │     → defender / avast / avira / bitdefender / crowdstrike / cylance / eset / 360tray
      │     → 同时会触发 static_sandbox 的 discovery ×2
      │
      ├─ 路径上下文 ×1.05
      │     → Temp / Downloads / Desktop
      │
      └─ 多个 family 同时命中
            → score_static_signals 累加
            → heuristic 抬高
                        ↓
              ProductionFusion Normal
              static / static_high 归因分支
                        ↓
       stage 取决于 Normal 阈值与双引擎分数
       静态语料关闭 sandbox，不含动态证据
                        ↓
    Scanner 仍保留 heuristic >= 0.8 / AI >= request threshold
       的直接裁决 fallback（不被 Fusion 替代）
```

### 关键判断：不要先动权重

系统已经明确规定**启发式是证据、不是裁决器**。所以正确的第一步不是"把 `api_injection_chain` 从 0.70 降到 0.5"，而是先回答：

> 这次误报里，**是启发式本身错了，还是启发式 + AI 的组合错了，还是融合阈值错了？**

这三种情况的修复完全不同：

| 根因 | 正确修复 |
|------|----------|
| 启发式单条权重过高 | 调整该规则的权重或加限定条件 |
| 多条低相关规则叠加 | 引入规则互斥/去重，或对"安装器特征"做负向加权 |
| 安全产品字符串识别过宽 | 该族只在**特定上下文**（如驱动加载、服务注册）才计分 |
| 路径乘数放大过头 | 复核 1.05 乘数是否必要 |
| 融合阈值偏低 | 调 `FusionResponseLevel` |
| AI 误判 | 模型校准 / 重新训练 |
| 权威层误报 | 修规则本身（YARA / 情报） |

**基础归因数据现在可以区分层、Fusion 分支和命中规则名**（见 12.5）；但规则权重贡献、路径乘数、API/String 命中和熵窗口仍不完整。真正的绿色/便携安装包语料也尚未导入。下一步先对具体样本确认这些字段和触发路径，再决定是否调权重。

### 建议的专项测试集

构造一组**纯良性**语料，覆盖最容易踩坑的类别：

| 类别 | 样本来源建议 | 关注层 |
|------|--------------|--------|
| 绿色/便携安装包 | 自解压安装器、单文件绿色版 | 熵 + API + 路径 |
| 加壳合法软件 | UPX / Themida / VMProtect 打包的商业软件 | 熵 + 静态沙箱 |
| 开发工具链 | 编译器、调试器、逆向工具（IDA/Ghidra 类） | API 组合 + 静态沙箱 |
| 系统管理工具 | PsExec / 进程管理 / 注册表工具 | API + LOLBin |
| 安全产品二进制 | 各类 AV / EDR 客户端 | 名称字符串 + discovery ×2 |
| 脚本 | 合法的 PowerShell / JS / VBS 自动化脚本 | 脚本启发式 |
| 驱动 | 合法的第三方驱动（`.sys`） | BYOVD 清单精确性 |
| 大型归档 | 压缩包、资源密集的安装包 | 熵 + 大文件路径 |

**验收标准**：以上全部类别的 FP 率应单独统计，**不与真实恶意样本的指标混算**。

### 内核侧的一个正面设计

值得指出：[第 6.4 节](06-内核驱动.md#64-用户态--内核-abi-everbloom_driver_protocolh) 的 BYOVD 清单是**精确 basename 列表**，源码注释明确禁止"因为文件是 `.sys` 就当恶意"。这是一条已经做对的误报防线——如果当初写成扩展名规则，所有第三方驱动都会中招。

## 12.9 阈值校准方法

### 三个可调阈值

| 位置 | 参数 | 当前值 |
|------|------|--------|
| `FusionResponseLevel` | Aggressive / Normal / Relaxed | 0.55 / 0.70 / 0.85 |
| 静态高置信门槛 | 随响应级别 | 0.82 / 0.90 / 0.96 |
| 静态一致分支 | `weakest` 佐证条件 | `threshold × 0.70` |
| `SecurityLevel`（行为层） | Aggressive / Normal / Relaxed | 0.55 / 0.70 / 0.85 |

### 校准流程（建议）

1. **固定语料**：良性集 + 恶意集，各自独立；
2. **导出逐样本归因**（12.5 的 `AttributionRecord`）；
3. **画 ROC**：对 `heuristic` 单层、`ai` 单层、以及 `combined` 分别画 TPR/FPR 曲线；
4. **选工作点**：按可接受的 FP 率反推阈值，而不是凭直觉设 0.70；
5. **回归**：用 `run_quality_baseline.py --gate` 把选定工作点固化，防止后续改动悄悄漂移。

### 已有的一致性

`FusionResponseLevel::threshold()` 与 `SecurityLevel::threshold()` **两处的数值完全相同**（0.55 / 0.70 / 0.85）。这是一个好设计——行为层与融合层用同一套响应级别语义，避免了"行为层在 Aggressive 模式下用 0.55、融合层却用 0.7"这种错配。

## 12.11 数据集划分原则

| 集合 | 用途 | 约束 |
|------|------|------|
| **训练集** | 拟合模型 | 绝不用于评估 |
| **验证集** | 选阈值 / 早停 | 绝不用于最终报告 |
| **测试集** | 最终指标 | **只用一次**；一旦用于调参即作废 |
| **回归集** | CI 门控 | 小而稳定；可反复跑 |
| **对抗集** | 鲁棒性 | 由 `train_adversarial_model.py` 的 PGD 在特征空间生成 |

### 必须遵守的两条

1. **时间切分优先于随机切分**。恶意软件演化有强时间相关性；随机切分会让"未来样本"泄漏进训练集，得出虚高的检出率。
2. **家族级切分**。同一恶意家族的不同变体不能跨训练/测试集——否则测的是"能不能认出见过的家族"，而不是泛化能力。

### 合规约束（来自 [第 11.8 节](11-能力考量与安全边界.md#118-合规与分发)）

仓库**不携带真实恶意样本**。因此：

- 真实样本集只能通过 `tools/import_real_dataset.py` **本地导入**（该脚本从不联网，只读操作者指定路径）；
- 数据集产物只含**特征向量 + 标签 + 元数据**，不含可执行文件本身。
