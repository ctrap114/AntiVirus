# 8. 支撑模块

除三大主体（引擎 / 驱动 / GUI）外，仓库还有一组支撑模块，为集成、自动化、数据与测试提供基础。

---

## 8.1 `libeverbloom_rs` —— Python 绑定

**技术栈**：Rust cdylib + PyO3 0.29（`extension-module` + `auto-initialize`）

**规模**：`libeverbloom_rs/src/` 共 **1,315 行**，9 个源文件。

### 关键设计：复用引擎 crate

```toml
[dependencies]
everbloom_engine = { path = "../engine" }
```

`libeverbloom_rs` 通过 **path 依赖**直接引用引擎 crate。这意味着 Python 侧调用的检测实现与桌面版**完全同源**——不存在"两套逻辑分叉"的风险。任何引擎修复自动惠及 Python 侧。

### 9 个导出类（`#[pyclass]`）

```rust
#[pymodule]
fn libeverbloom_rs(_py: Python<'_>, m: &Bound<'_, PyModule>) -> PyResult<()> {
    m.add_class::<rust_pe_parser::PeParser>()?;
    m.add_class::<rust_feature_extractor::FeatureExtractor>()?;
    m.add_class::<rust_rule_engine::YaraRuleEngine>()?;
    m.add_class::<rust_pattern_matcher::PatternMatcher>()?;
    m.add_class::<rust_cache::ShardedLruCache>()?;
    m.add_class::<rust_fs_monitor::FsMonitor>()?;
    m.add_class::<rust_win_api::WinApi>()?;
    m.add_class::<rust_scan_pipeline::ScanPipeline>()?;
    m.add_class::<rust_sandbox_queue::SandboxQueue>()?;
    Ok(())
}
```

| 类 | 文件 | 能力 |
|----|------|------|
| `PeParser` | `rust_pe_parser.rs` | PE 结构解析（`pelite` 0.10） |
| `FeatureExtractor` | `rust_feature_extractor.rs` | 特征抽取（供训练/分析） |
| `YaraRuleEngine` | `rust_rule_engine.rs` | YARA 规则加载与扫描 |
| `PatternMatcher` | `rust_pattern_matcher.rs` | 多模式匹配（`aho-corasick` 1.1） |
| `ShardedLruCache` | `rust_cache.rs` | 分片 LRU 缓存（`lru` 0.8 + `parking_lot` 0.12） |
| `FsMonitor` | `rust_fs_monitor.rs` | 文件系统监视（`notify` 6.1） |
| `WinApi` | `rust_win_api.rs` | Win32 API 封装（`windows` 0.48） |
| `ScanPipeline` | `rust_scan_pipeline.rs` | 扫描流水线编排 |
| `SandboxQueue` | `rust_sandbox_queue.rs` | 沙箱任务队列（`flume` 0.11 通道） |

### 依赖选择说明

| 依赖 | 用途 |
|------|------|
| `pelite` 0.10 | PE 解析（与引擎用的 `goblin` 不同——`pelite` 提供更细的 Windows 语义） |
| `aho-corasick` 1.1 | 多模式字符串匹配（比逐条 `contains` 快一个数量级） |
| `lru` 0.8 + `parking_lot` 0.12 | 分片 LRU：`parking_lot` 的锁比 `std::sync::Mutex` 快，分片降低争用 |
| `memmap2` 0.9 | 内存映射读取大文件 |
| `notify` 6.1 | 跨平台文件系统事件 |
| `flume` 0.11 | 多生产者多消费者通道（沙箱任务队列） |
| `windows` 0.48 | Win32 API（比 `windows-sys` 更高级的封装） |

`yara` 依赖是**可选**的，由 feature `with_yara` 控制，且默认开启。

## 8.2 `sandbox_monitor` —— 沙箱行为监视器

**技术栈**：Rust（lib + bin），`windows-sys` 0.61.2、`nix` 0.30、`reqwest` 0.12

**规模**：`sandbox_monitor/src/lib.rs` 544 行。

### 双平台后端

源码用 `#[cfg]` 分成两套实现：

```rust
#[cfg(unix)]
use libc;
#[cfg(unix)]
use nix::{ sys::{ ptrace, wait::{waitpid, WaitStatus} }, unistd::Pid };

#[cfg(target_family = "windows")]
use windows_sys::Win32::System::Diagnostics::Etw::*;

#[cfg(unix)]
pub fn monitor_ptrace(child_pid: i32, api_calls: Arc<Mutex<Vec<String>>>, stop_flag: Arc<AtomicBool>) -> Option<i32>
```

| 平台 | 机制 |
|------|------|
| **Windows** | ETW（`Etw*` API）消费内核事件 |
| **Unix** | `ptrace` 系统调用跟踪 |

### 事件收集

`monitor_ptrace` 接受三个参数：

- `child_pid` —— 被监视的子进程；
- `api_calls: Arc<Mutex<Vec<String>>>` —— 共享的 API 调用记录；
- `stop_flag: Arc<AtomicBool>` —— 停止信号。

返回 `Option<i32>`（子进程退出码）。

`Arc<Mutex<...>>` + `AtomicBool` 的组合使监视器可以在独立线程运行，同时让调用方随时取走收集到的调用序列并发出停止信号。

### `reqwest` 的用途

`reqwest` 0.12（`blocking` + `json`）用于把行为数据上报给外部分析服务（如 Cuckoo / CAPE 风格的分析平台）。这是**可选**路径，不参与本地检测。

### 与引擎的关系

`sandbox_monitor` 被 `libeverbloom_rs` 依赖（`sandbox_monitor = { path = "../sandbox_monitor" }`）。引擎自身的沙箱实现在 `engine/src/sandbox.rs`（2,799 行）——两者分工不同：

| | `sandbox_monitor` | `engine/src/sandbox.rs` |
|---|---|---|
| 定位 | 通用行为监视器（可独立使用） | 引擎内置的样本执行与取证 |
| 平台 | Windows ETW / Unix ptrace | Windows AppContainer + ETW |
| 依赖 | 独立 crate | 引擎内部模块 |

## 8.3 `edr` —— EDR 数据模型

**技术栈**：Rust lib，`serde`、`serde_json`、`chrono` 0.4

**规模**：`edr/src/lib.rs` 406 行。

### 定位

模块头注释明确了设计参考方向：

> *参考方向：Fibratus（Windows 内核事件追踪）、Sysmon（遥测格式）、Velociraptor（DFIR 取证查询模式）、Wazuh（HIDS/SIEM 日志合规）*

四项当前职责：

1. 接收 `sandbox_monitor` 的遥测数据（ETW / minifilter 事件）；
2. 标准化为 EDR 事件格式（兼容 Fibratus / Sysmon 风格）；
3. 提供外部分析服务接入接口（CAPE REST API / Detonate FastAPI）；
4. 为后续规则引擎（YARA + 行为规则）与合规报告提供数据结构基础。

### 事件类型枚举

```rust
#[derive(Debug, Clone, Serialize, Deserialize, PartialEq)]
pub enum EdrEventKind {
    // 进程生命周期
    ProcessCreate, ProcessTerminate, ProcessInjection,
    ProcessHollowing, ProcessDoppelganging, ProcessHerpaderping,

    // 文件系统操作
    FileCreate, FileModify, FileDelete, FileRename, FileRead, FileCopy,

    // 注册表操作
    RegistryCreate, RegistryModify, RegistryDelete,
    ...
}
```

事件类型的划分直接对应 ATT&CK 战术：

- `ProcessInjection` / `ProcessHollowing` / `ProcessDoppelganging` / `ProcessHerpaderping` —— 四种进程注入手法，分别对应 T1055 的不同变体；
- 文件操作覆盖 create / modify / delete / rename / read / copy；
- 注册表覆盖 create / modify / delete。

### 能力考量

`edr` 是**数据结构层**，不做检测决策。它的价值在于：为遥测事件提供一个标准化、可序列化、可跨语言（`serde`）交换的表示。这使外部分析服务（SIEM、取证平台）可以消费 Everbloom 的遥测而不需要理解引擎内部结构。

## 8.4 `proto` —— 遗留 IPC 消息定义

**规模**：`proto/messages.proto` 34 行。

```protobuf
message ScanRequest {
  repeated string paths = 1;
  repeated string engines = 2;
  string mode = 3;
}

message ScanResponse {
  string file_path = 1;
  string threat_name = 2;
  map<string, float> engine_scores = 3;
  bool is_malicious = 4;
  string action = 5;
}

message ScanProgress {
  uint64 files_scanned = 1;
  uint64 threats_found = 2;
  uint64 elapsed_ms = 3;
  uint64 estimated_remaining_ms = 4;
}

message ConfigUpdate {
  string preset = 1;
  bool realtime_protection = 2;
  repeated string exclude_paths = 3;
}

message Heartbeat {
  uint64 timestamp = 1;
}
```

### 设计要点

- **`engine_scores` 是 `map<string, float>`** —— 支持多引擎架构：每条结果都带各引擎的独立评分，而不是一个聚合值。这保留了可解释性；
- **`ScanProgress` 含 `estimated_remaining_ms`** —— 进度上报不只是"已完成多少"，还包括预估剩余时间；
- **`Heartbeat`** —— 长连接的存活检测。

### 与 NDJSON 的关系

这套 protobuf 定义服务于 `engine/src/ipc.rs`（4 字节大端长度前缀 + prost 编码的 `IpcEnvelope`）。桌面 GUI **不使用**它——GUI 走 NDJSON。它是为非 GUI 的自动化集成（需要严格 schema 的场景）保留的通道。

## 8.5 `python/` —— Python 包

**规模**：约 **2,100 行**，三个子包。

### `everbloom_config`

| 文件 | 职责 |
|------|------|
| `schema.py` | 配置 schema 定义与校验 |
| `presets.py` | 预设配置（如"高性能"、"高检出"、"平衡"） |
| `factory.py` | 配置对象工厂 |

配置以 schema 为中心：`schema.py` 定义合法字段与取值范围，`presets.py` 提供具名预设，`factory.py` 负责组装。这样"配置文件写错了"能在加载阶段被发现，而不是在运行时产生诡异行为。

### `everbloom_core`

| 文件 | 职责 |
|------|------|
| `synthetic.py` | 合成语料生成的 Python 侧封装 |
| `adversarial.py` | 对抗样本生成与评估 |

`adversarial.py` 与 `tools/train_adversarial_model.py` 配合，构成"对抗训练"实验链路（见 `docs/adversarial_training.md`）。

### `everbloom_viz`

| 文件 | 职责 |
|------|------|
| `mermaid.py` | Mermaid 图生成（架构图、流程图） |
| `report.py` | 报告生成 |
| `threat_naming.py` | 威胁命名（遵循 `docs/malware_naming_convention.md`） |

`threat_naming.py` 实现统一的恶意软件命名规范——这使不同来源的检测结果能有一致的展示名称。

## 8.6 `hashdb/` —— 随包哈希库

```
hashdb/HashDB.db    23,834,624 字节（约 22.7 MiB）
```

这是随安装包分发的**历史哈希库**（legacy），通过 CMake 的 `EVERBLOOM_LEGACY_HASH_DB` 变量安装到 `bin/data/`。

与之并存的还有 `data/local_hashes.sqlite`（`EVERBLOOM_HASH_DB`），用于本地增量更新的哈希记录。

### 格式

`docs/hash_database_formats.md` 描述 schema。核心是 `hashes` 表，支持五种列：

| 列 | 说明 |
|----|------|
| `md5` | MD5 摘要 |
| `sha1` | SHA-1 摘要 |
| `sha256` | SHA-256 摘要 |
| `ssdeep` | 标准 ssdeep 模糊哈希 |
| `ssdeep-lite` | 简化模糊哈希（历史格式） |

### 更新链

`tools/build_local_hashdb.py` 从三个公开源构建/更新：

| 源 | 内容 | 认证 |
|----|------|------|
| MalwareBazaar | 恶意样本哈希 | 无 |
| URLhaus | 恶意 URL | **仅在线查询**（不落库） |
| ThreatFox | IoC | `THREATFOX_AUTH_KEY` |

**只接受 `confidence >= 70` 且未过期的记录**（见 [第 5.10 节](05-检测层详解.md#510-威胁情报层threat_intelrs)）。

## 8.8 `quarantine/` —— 隔离区运行时目录

```
quarantine/store.key    32 字节
```

`store.key` 是隔离区加密密钥。隔离区的完整机制在 [第 4.8 节](04-扫描引擎.md#48-隔离区quarantinerrs-941-行) 已述。

运行时行为：

- 目录由 `EVERBLOOM_QUARANTINE_DIR` 指定（默认 `quarantine/`）；
- 密钥优先从 `EVERBLOOM_QUARANTINE_ENCRYPTION_KEY` 读取，否则用 `store.key`；
- `EVERBLOOM_ENCRYPT_QUARANTINE` 控制是否加密存储（默认开启）。

### 语料设计

- **`corpus/benign/`**：良性样本（PowerShell 笔记、发布说明）——用于验证**零误报**；
- **`corpus/malicious/`**：合成恶意样本（EICAR 变体、Emotet/Qakbot 风格）——全部是**合成的**，不含真实恶意代码；
- **`manifest.json`**：语料清单，含每项的期望判定；
- **`data/synthetic/`**：四类特征画像样本（API 密集、良性、加壳、隐蔽），用于特征抽取与模型的单元测试。

### Python 测试覆盖

| 测试 | 覆盖 |
|------|------|
| `test_yara_regression.py` | YARA 规则回归（规则改动后检测结果不退化） |
| `test_synthetic_corpus.py` | 合成语料生成 |
| `test_adversarial_training.py` | 对抗训练流程 |
| `test_everbloom_config_factory.py` | 配置 schema 与工厂 |
| `test_threat_naming.py` | 威胁命名规范 |
| `test_mermaid_viz.py` | Mermaid 图生成 |
| `test_report_generator.py` | 报告生成 |

### 能力考量

**合成语料而非真实样本**是刻意的合规选择：

- 仓库不含真实恶意代码，降低分发与存储风险；
- 合成样本带 `EVERBLOOM-SYNTHETIC-CORPUS-NOT-MALWARE` 标记，任何扫描器都能识别；
- 代价是覆盖度有限——因此 `tools/` 提供了真实数据集的接入路径（EMBER 2018/2025、MalwareBazaar）。

## 8.10 模块协作关系

```
                      ┌─────────────────────┐
                      │   libeverbloom_rs   │  (PyO3 cdylib)
                      │   9 个 #[pyclass]   │
                      └──────┬──────────────┘
                             │ path 依赖
        ┌────────────────────┼────────────────────┐
        ▼                    ▼                    ▼
  ┌───────────┐      ┌──────────────┐     ┌──────────────┐
  │  engine   │      │sandbox_monitor│     │   python/    │
  │  (Rust)   │      │   (Rust)     │     │ everbloom_*  │
  └───────────┘      └──────┬───────┘     └──────┬───────┘
                            │ 遥测               │ 配置/可视化
                            ▼                    │
                     ┌─────────────┐             │
                     │     edr     │             │
                     │ (数据模型)   │             │
                     └─────────────┘             │
                                                 ▼
                                          ┌─────────────┐
                                          │   tools/    │
                                          │ 训练/转换/   │
                                          │ 打包脚本     │
                                          └──────┬──────┘
                                                 │ 读写
                                                 ▼
                                          ┌─────────────┐
                                          │    data/    │
                                          │ hashdb/     │
                                          │ quarantine/ │
                                          └─────────────┘
```

**关键点**：`libeverbloom_rs` 与 `engine` 是**同一份检测实现**的两种暴露方式。Python 生态与桌面 GUI 走的是同一条检测路径，不存在行为差异。
