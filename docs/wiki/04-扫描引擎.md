# 4. 扫描引擎（`everbloom_engine`）

`engine/` 是 Everbloom Security 的决策中枢。它是一个 Rust 2021 的 **GUI 子系统可执行文件**（`everbloom_engine.exe`），既能作为常驻的 NDJSON 服务被 GUI 拉起，也能以一次性 CLI 模式执行诊断与训练任务。

代码规模：`engine/src/` 共 **37,673 行**，实际编译 **约 35,901 行**。

---

## 4.1 入口与运行模式（`main.rs`，1,523 行）

`#[tokio::main] async fn main()` 按固定顺序执行：

### 步骤 1：日志初始化

```rust
everbloom_engine::logging::initialize();
everbloom_engine::logging::install_panic_hook();
```

`install_panic_hook` 保证 panic 也能被记录，而不是静默消失。

### 步骤 2：引擎二进制完整性自检

若设置了 `EVERBLOOM_BINARY_INTEGRITY_MANIFEST`，引擎会：

1. 用 `std::env::current_exe()` 取自身路径；
2. 流式（64 KiB 缓冲）计算 SHA-256；
3. 读清单文件（`二进制名=十六进制摘要` 的 `key=value` 行格式，支持 `#` 注释）；
4. 摘要不符则**记录错误并返回 `Err`**，进程不进入服务状态。

这使"引擎被替换/打补丁"这一攻击面有了一个可验证的入口防线。

### 步骤 3：`--driver-status` 带外诊断

```rust
if cli_all.iter().any(|arg| arg == "--driver-status") { ... }
```

行为：打开 `\\.\EverbloomSecurity`，发 `EVERBLOOM_IOCTL_CAPABILITIES_QUERY`，打印协商结果后**立即退出**——不启动 IPC 服务、不启动任何防护线程。

输出字段：

```
device: present|absent
compatible: <bool>
capability_flags: 0x<hex>
kernel_model: <bool>          ← 驱动是否真的链入了整数模型
protocol_version: <n>
policy_version: <n>
protection_protocol_version: <n>
event_version: <n>
max_target_chars: <n>
max_payload_bytes: <n>
max_event_batch: <n>
summary: <人类可读摘要>
```

退出码：`0` 兼容 / `3` 设备不存在 / `4` 协议不兼容。

**配套参数 `--driver-status-report <路径>`** 把同一份结论写入文件。这是**脚本化调用的唯一可靠方式**——因为引擎是 GUI 子系统进程，PowerShell 不会等待它、也不会填充 `$LASTEXITCODE`。

### 步骤 4：`--train-synthetic` 带外训练

```rust
if cli_args.iter().any(|arg| arg == "--train-synthetic") {
    return match everbloom_engine::training::run_training_cli(&cli_args) { ... };
}
```

运行合成语料实验并输出 JSON 结果后退出，同样不触碰 IPC 服务。这样 GUI 可以把训练当作一个普通子进程驱动，同时引擎继续对外提供扫描服务。

### 步骤 5：传输模式判定

```rust
fn use_ndjson_transport() -> bool
```

判定优先级（高到低）：

1. 命令行含 `--ndjson` 或 `--stdio` → **NDJSON**；
2. 命令行含 `--legacy-ipc` 或 `--socket` → **IPC**；
3. 环境变量 `EVERBLOOM_ENGINE_TRANSPORT` 为 `ndjson`/`stdio` → NDJSON；`ipc`/`socket`/`legacy` → IPC；
4. 兜底：**未设置** `EVERBLOOM_IPC_ENDPOINT` 时用 NDJSON，设置了则用 IPC。

GUI 启动引擎时会显式把 `EVERBLOOM_IPC_ENDPOINT` 清空并传 `--ndjson`（见 `WinUIEngineProcess.cpp`），因此桌面场景永远是 NDJSON。

### 步骤 6：进入常驻循环

启动扫描器、加载模型与哈希库、启动 HIPS 监视器与沙箱清理，然后进入 `ndjson::run_resident_loop()`（或 IPC 服务循环），直到 EOF 或收到 `{"command":"EXIT"}`。

## 4.2 扫描流水线（`scanner.rs`，2,851 行）

### 并发模型

```rust
pub async fn scan_request(&self, req: ScanRequest) -> Result<Vec<ScanResult>, ScanError>
```

- 外层是 **tokio 异步**：接受请求、发进度、聚合结果；
- 内层用 `tokio::task::spawn_blocking` + **rayon `into_par_iter()`** 做 CPU 密集的逐文件扫描。

进度通过 `Sender<ScanProgress>` 以 `try_send` 上报（非阻塞，满了就丢，不拖慢扫描）。`ScanProgress` 有三个变体：`Started(path)`、`Completed(path)`、`FileError(path, message)`。

`Scanner` 用**构建器模式**装配（全部 `with_*` 方法返回 `Self`）：

```rust
Scanner::new()
    .with_allowlist(Arc<Allowlist>)
    .with_hash(Arc<HashMatcher>)
    .with_yara(Arc<YaraScanner>)
    .with_ai(Arc<AiModel>)
    .with_clamav(Arc<ClamAvClient>)
    .with_behavioral(Arc<BehavioralScorer>)
    .with_sequence(Arc<SequenceMatcher>)
    .with_threat_intel(Arc<ThreatIntelMatcher>)
    .with_fusion(Arc<ProtectionFusion>)
    .with_cache(Arc<ScanCache>)
    .with_sandbox_enabled(bool)
    .with_sandbox_timeout(ms)
    .with_rollback_executor(Arc<RollbackExecutor>)
```

任何一个 `with_*` 没调用，对应层就**不参与**扫描——这是引擎可裁剪性的来源。

### 单文件流水线顺序

按源码实际执行顺序（`scanner.rs` 的并行闭包内）：

| # | 阶段 | 说明 |
|---|------|------|
| 1 | **元数据与大小门** | `std::fs::metadata`；超过 `maximum_file_size` 直接返回错误结果 |
| 2 | **幽灵文件证据** | 文件不存在（`NotFound`）时查 `monitoring::lookup_ghost_file_evidence` —— 处理"扫描期间文件被删"的场景 |
| 3 | **BYOVD 早期判定** | `known_vulnerable_driver_name(basename)` 命中且驱动防护开启时，直接调 `driver_bridge.block_file`。**注释明确要求：basename 清单必须精确，不能因为文件是 `.sys` 就当恶意** |
| 4 | **缓存指纹** | `FileFingerprint::from_metadata` —— 元数据是廉价的预筛选，只有可能有缓存条目的路径才付内容哈希的代价 |
| 5 | **白名单匹配** | `allowlist.matches(path)`；命中则 `suppress_static_layers = true`（只压制静态/AI 的噪声判定，精确哈希、YARA、动态行为**仍然执行**且保持权威） |
| 6 | **内核策略查询** | `protection_state::driver_enabled()` 为真时先调 `driver_bridge.scan_file` —— 内核策略是**强制执行权威**，必须在用户态缓存之前问，否则新装的驱动规则挡不住一条缓存的 Clean 结果 |
| 7 | **缓存命中** | `cache.get_fresh_for_policy_with_context` / `get_evidence_for_policy_with_context`；Cookie 防护候选文件**跳过缓存** |
| 8 | **静态层** | 哈希 → YARA → 启发式 → AI（受 `suppress_static_layers` 与各 `enable_*` 开关控制） |
| 9 | **动态层** | 行为评分、序列匹配、静态沙箱预测、沙箱执行（可选）、内存快照、解包 |
| 10 | **融合裁决** | `ProtectionFusion` 综合全部证据，产出 `FusionDecision` |
| 11 | **回滚执行** | 若融合结果要求干预且存在 `rollback_record`，`RollbackExecutor::execute` 实际执行回滚动作 |
| 12 | **写缓存** | `cache_result_from_scan` |

### 关键实现细节

**白名单只压制"噪声型"判定。** 精确哈希命中、YARA 命中、沙箱观察到的动态行为是**权威证据**，白名单不压制它们。这是为了避免"加了白名单就等于免检"。

**内核策略优先于用户态缓存。** 顺序是刻意的：内核规则可能在上一次扫描之后被更新，先查内核才能保证策略变更立即生效。

**缓存可重算。** `recompute_cached_decision` 与 `cached_summary_is_static_recomputable` 允许在不重跑沙箱的前提下，用新的规则版本重算缓存中静态部分的结论。`cached_summary_is_immutable` 则标记那些**不能**重算的结论（例如已执行过回滚的）。

## 4.3 传输层

### NDJSON（`ndjson.rs`，2,864 行）——平台首选

**协议**：每行一个 JSON 对象，UTF-8 编码，`\n` 结尾。请求与响应通过 stdin/stdout 双向流动。

**请求形态**（两种）：

```jsonc
// 扫描请求
{"task_info":{"task_id":"gui-1234-7","priority":"NORMAL","timeout_ms":60000},
 "target":{"type":"LOCAL_PATH","file_path":"C:/x/y.exe","file_name":"y.exe"},
 "scan_options":{"enable_heuristics":true,"max_archive_depth":3,
                 "max_file_size_mb":256,"enable_yara":true,"enable_ai":true,
                 "enable_sandbox":false,"ai_threshold":0.50000,"cloud_enabled":false}}

// 控制命令
{"command":"RELOAD_HASH_DATABASE"}
{"command":"SET_PROTECTION_MODES","r3_enabled":true,"driver_enabled":true}
{"command":"QUARANTINE_FILE","path":"C:/x/y.exe","reason":"..."}
{"command":"EXIT"}
```

**完整命令集**（`ndjson.rs` 的 `match command.as_str()` 分发）：

| 命令 | 作用 |
|------|------|
| `RELOAD_HASH_DATABASE` | 重载哈希库 |
| `RELOAD_VULNERABLE_DRIVERS` | 从默认位置重载易受攻击驱动名单 |
| `IMPORT_HASH_DATABASE` | 从指定路径导入哈希库 |
| `CONVERT_MODEL` | 调用转换器脚本转换模型格式 |
| `IMPORT_MODEL` | 导入模型 |
| `VALIDATE_MODEL` | 校验模型可用性（返回 `EngineModelValidationResponse`） |
| `SET_AI_STRATEGY` | 切换 AI 策略（如主备/集成） |
| `SET_PROTECTION_MODES` | 设置 R3 防护与驱动防护开关 |
| `BLOCK_FILE` | 实时阻断文件 |
| `ALLOW_FILE` | 实时放行文件 |
| `ALLOWLIST_ADD` | 加入白名单 |
| `QUARANTINE_FILE` | 隔离文件 |
| `RESTORE_QUARANTINE` | 恢复隔离项（可指定 `restore_path` / `overwrite`） |
| `DELETE_QUARANTINE` | 删除隔离项 |
| `LIST_QUARANTINE` | 列出隔离项（可 `include_inactive`） |
| `EXPORT_QUARANTINE` | 导出隔离区 |
| `IMPORT_QUARANTINE` | 导入隔离区 |
| `CLEAR_STEALER_FIREWALL` | 清除 StealerGuard 建立的防火墙规则 |
| `EXIT` | 退出常驻循环 |

**响应契约**：`EngineStatusCode` 枚举表达结果状态，另有 `ContractVerdict::{Malware, Suspicious, Clean}` 用于扫描裁决。所有响应都是单行 JSON。

**常驻循环**：`run_resident_loop()` 读 stdin 直到 EOF 或收到 `EXIT`。读取是逐行的，超长行有上限保护。

### IPC（`ipc.rs`，910 行）——遗留通道

用于非 GUI 的自动化集成：

- **命名管道**：`\\.\pipe\everbloom_engine`，创建时 `reject_remote_clients(true)` —— 只接受本机连接；
- **帧格式**：4 字节**大端**长度前缀 + prost 编码的 `IpcEnvelope`；
- **`IpcEnvelope`** 是 protobuf `oneof`，标签 1–8；
- **`MAX_FRAME_SIZE = 16 MiB`**；
- **`MAX_ACTIVE_SCANS = 2`** —— 最多两个扫描并发。

`proto/messages.proto` 定义了对应的消息（`ScanRequest` / `ScanResponse` / `ScanProgress` / `ConfigUpdate` / `Heartbeat`）。

> **为什么两套并存**：NDJSON 对人类可读、易调试、无需生成代码，适合 GUI 与脚本；IPC 适合需要严格 schema 与高吞吐的内部集成。GUI 场景统一用 NDJSON。

## 4.4 缓存（`layers/cache.rs`，701 行）

### 上下文感知的失效

`ScanContext` 把四个版本号纳入缓存键：

```rust
ScanContext { rules_version, yara_version, ai_model_version, sandbox_policy_version }
```

任一版本变化，旧缓存条目自动不再命中。这意味着**更新规则不需要手动清缓存**。

### 两级世代

```rust
FileFingerprint { modified, size, content_hash }
```

- **证据世代（evidence）**：静态层的原始输出，可跨规则版本复用；
- **决策世代（decision）**：融合后的最终结论。

`invalidate_decisions()` **只**递增决策世代，保留证据。这样规则更新后不必重新读盘、重新解析 PE，只需用新规则重跑融合——这是"缓存可重算"能力的实现基础。

`recompute_cached_decision` 就是这条路径的入口。

## 4.5 HIPS 与主动防御（`hips.rs`，1,549 行）

HIPS 是引擎的**实时行为拦截**子系统，与扫描流水线并行运行。

### 事件模型

```rust
pub enum HipsEvent { ... }   // 事件类型（第 49 行起）
```

每个事件提供：

- `process_id()` → `u32`
- `description()` → 人类可读描述
- `behavior_event()` → `Option<BehaviorEvent>`（可转换为行为评分层的输入）

### 采集与排空

- `start_hips_monitor()` 启动监视器（基于 Win32 回调 + ETW）；
- `drain_hips_events()` 排空事件队列；
- `drain_event_dropped()` 返回 `(已投递, 已丢弃)` 计数——**丢弃计数是显式暴露的**，避免"事件静默丢失"这种不可观测状态。

### 主动防御四阶段

对应 `docs/active_defense_architecture.md` 与 `docs/main_protection_driver_contract.md` 定义的模型：

| 阶段 | 名称 | 行为 |
|------|------|------|
| 1 | **观察（observe）** | 采集行为事件，不干预 |
| 2 | **关联（correlate）** | 把多步行为关联成攻击链（`SequenceMatcher`） |
| 3 | **干预（intervene）** | 达到融合阈值后阻断 |
| 4 | **恢复（recover）** | 通过 `RollbackExecutor` 撤销已造成的更改 |

关键设计：`FusionDecision` **始终**返回 `Clean` / `Malicious` 两态，阶段信息编码在 `reason` 前缀里（`fusion:driver:stage=intervene:`）。这样调用方不需要理解阶段机，也能拿到稳定的布尔裁决。

### 请求关联规则

- 单一 ABI，`RequestId` 原样回显；
- `DriverBlocked` 标记**只在驱动真的阻断时**追加；
- 沙箱重读 HIPS 队列时按 `target_pid` 过滤，避免把无关进程的事件算进来。

## 4.6 沙箱（`sandbox.rs`，2,799 行）

### 三个后端

| 后端 | 机制 | 用途 |
|------|------|------|
| **AppContainer** | `CreateAppContainerProfile` + `CreateRestrictedToken`（`DISABLE_MAX_PRIVILEGE`）+ Job Object 限额 | 默认的轻量隔离执行 |
| **ETW 回放/监视** | 注册 ETW 回调（`EtwCallbackContext`）采集文件/注册表/网络/进程事件 | 行为采集 |
| **外部沙箱**（Cuckoo 等） | HTTP 提交与报告回收 | 深度分析（可选，见 `docs/cuckoo_integration.md`） |

### 资源上限（源码常量）

| 常量 | 值 | 含义 |
|------|-----|------|
| `MIN_TIMEOUT` | 30 s | 最短执行时间 |
| `MAX_TIMEOUT` | 10 min | 最长执行时间 |
| `MAX_SAMPLE_SIZE` | 1 GiB | 单个样本上限 |
| `COPY_BUFFER_BYTES` | 1 MiB | 复制缓冲 |
| `COPY_FREE_SPACE_HEADROOM` | 64 MiB | 复制前预留磁盘余量 |
| `DEFAULT_COPY_RATE_LIMIT_BYTES_PER_SEC` | 256 MiB/s | 复制速率限制（防 I/O 打满） |
| `MAX_INSPECTION_BYTES` | 16 MiB | 静态预检读取上限 |
| `MAX_GUEST_REPORT_BYTES` | 2 MiB | 客户机报告大小上限 |
| `APPCONTAINER_ORPHAN_MAX_AGE` | 24 h | 孤儿 AppContainer profile 的清理阈值 |
| `SANDBOX_POLICY_VERSION` | **3** | 参与缓存键 |

### 清理与防泄漏

- 启动时扫描并清理 `EverbloomSecurity.Sandbox.*` 前缀的孤儿 AppContainer profile（超过 24 小时的）；
- 样本复制带**速率限制**与**磁盘余量检查**，避免沙箱把宿主机 I/O 或磁盘打满；
- 客户机报告有大小上限，超限即拒绝解析。

### 超时语义

`effective_timeout = timeout.clamp(MIN_TIMEOUT, MAX_TIMEOUT)`，回放路径额外放宽到 `timeout * 2`（上限仍受 `MAX_TIMEOUT` 约束）。

## 4.7 驱动桥（`driver_bridge.rs`，1,095 行）

引擎与内核之间的唯一通道。

### 能力协商

```rust
bridge.probe_capabilities() -> Result<DriverCapabilities>
```

返回的 `DriverCapabilities` 包含 `capability_flags`、四个版本号、三个尺寸上限，以及：

- `is_compatible()` —— 协议版本是否与引擎匹配（对应 `EVERBLOOM_DRIVER_PROTOCOL_VERSION = 1`）；
- `has_kernel_model()` —— 检查 `EVERBLOOM_CAPABILITY_KERNEL_MODEL`（0x100）；
- `summary()` —— 人类可读摘要。

### 可用性降级

`DriverError::is_unavailable()` 用于区分"驱动不在"与"驱动报错"。前者是**正常的降级路径**（未安装驱动的机器上引擎应完整可用），后者才需要上报。扫描流水线里每个驱动调用点都处理了这两种情况。

### 结构体镜像

驱动侧的结构体（`EVERBLOOM_DRIVER_REQUEST`、`EVERBLOOM_DRIVER_RESPONSE`、`EVERBLOOM_DRIVER_EVENT` 等）在 Rust 侧用 `#[repr(C)]` 精确镜像。**布局一旦变更必须两边同步**——这也是为什么"评分回传"选择了复用 `EVERBLOOM_DRIVER_EVENT.Status` 字段，而不是新增字段：避免为一条建议性信号改动这个共享布局。

### 易受攻击驱动（BYOVD）

`known_vulnerable_driver_name()` 与 `reload_vulnerable_driver_names_from_default_locations()` 从 `data/vulnerable_drivers.json` 加载 basename 清单。扫描流水线在**第 3 步**就用它做早期判定。

## 4.8 隔离区（`quarantine.rs`，941 行）

### 加密存储

- 目录由 `EVERBLOOM_QUARANTINE_DIR` 指定（默认 `quarantine/`）；
- 密钥来自 `EVERBLOOM_QUARANTINE_ENCRYPTION_KEY` 或目录下的 `store.key`；
- `EVERBLOOM_ENCRYPT_QUARANTINE` 控制是否加密存储（默认开启）；
- `crypto.rs`（415 行）提供加密原语，`EVERBLOOM_ENCRYPT_BEHAVIOR`、`EVERBLOOM_STREAM_TAG_V1`、`EVERBLOOM_NONCE_DERIVE_V1` 控制行为元数据的加密与随机数派生。

### 隔离项模型

隔离项记录 `id`、`original_path`、`quarantine_path`、`restore_path`、`status`、`message`。支持的操作：隔离、恢复（可覆盖）、删除、列出（含非活动项）、导出、导入。

### 未编译的替代实现

`quarantine_clean.rs`（832）、`quarantine_fixed_backup.rs`（807）、`quarantine_new.rs`（108）、`quarantine_header_fixed.rs`（25）四个文件**不在 `lib.rs` 的模块声明中**，因此不参与编译。它们是隔离区实现迭代过程中的中间版本，保留在仓库中供参考。
