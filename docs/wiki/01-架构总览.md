# 1. 架构总览

## 1.1 三层进程模型

Everbloom Security 由三个**独立可执行体**组成，各自运行在不同的特权级别上，通过两条明确定义的通道通信。

```
┌──────────────────────────────────────────────────────────────────────┐
│  用户交互层   everbloom_gui.exe        C++23 / WinUI 3 / C++-WinRT   │
│  ─ 扫描控制、隔离区、实时告警、托盘、模型管理、多语言 UI               │
└───────────────────────────┬──────────────────────────────────────────┘
                            │  NDJSON over stdin/stdout（匿名管道）
                            │  子进程模型：GUI 拉起引擎，持有 stdin 写端 / stdout 读端
┌───────────────────────────▼──────────────────────────────────────────┐
│  决策层       everbloom_engine.exe     Rust 2021（~37,673 行 src/）   │
│  ─ 18 个检测/决策模块 + HIPS + 沙箱 + 隔离区 + 主动防御                     │
│  ─ 唯一持有最终裁决权（FusionDecision）                               │
└───────────────────────────┬──────────────────────────────────────────┘
                            │  DeviceIoControl（\Device\EverbloomSecurity）
                            │  唯一 ABI：everbloom_driver_protocol.h
┌───────────────────────────▼──────────────────────────────────────────┐
│  拦截层       everbloom_driver.sys     C（WDK，Native 子系统）        │
│  ─ 6 个拦截面 + 整数推理核心 + 无锁事件环                             │
└──────────────────────────────────────────────────────────────────────┘
```

### 为什么是三层而不是两层

把"拦截"和"判断"拆开，是为了让内核保持**极小且可审计**：

- 内核驱动只做**低成本的早期动作**——查表、比对路径、判断是否越权、放行或阻断；
- 任何需要解析文件内容、跑启发式、加载 ONNX 模型、发网络请求的工作，全部留在用户态。

这条边界在 `docs/main_protection_driver_contract.md` 中被定义为契约：**用户态拥有决策权，内核是一条低成本的前置防线**。内核返回的 `DriverBlocked` 是"权威否定"（一旦内核说挡了，用户态不再推翻），但内核从不做"权威肯定"——它不会宣称一个文件是恶意的，只会说"这个动作被拦了"。

### 两条通信通道

| 通道 | 方向 | 格式 | 使用者 |
|------|------|------|--------|
| NDJSON | GUI ⇄ 引擎 | 每行一个 JSON 对象，UTF-8，`\n` 结尾 | 桌面 GUI（**平台首选**） |
| DeviceIoControl | 引擎 ⇄ 驱动 | 定长结构体，`everbloom_driver_protocol.h` | 引擎的 `driver_bridge.rs` |

引擎还保留了一套遗留的 IPC 通道（`engine/src/ipc.rs`，命名管道 `\\.\pipe\everbloom_engine`，4 字节大端长度前缀 + prost 编码的 `IpcEnvelope`），用于非 GUI 的自动化集成；GUI 场景一律走 NDJSON。

## 1.3 一次扫描的完整数据流

以 GUI 发起一次手动扫描为例，走通全链路：

```
1. 用户在 WinUI 界面选择目录 → App::OnScanRequested
2. EngineClient::RequestScan(paths, timeout_ms, sandbox, yara, ai, heuristic, ...)
      └─ BuildScanLine(...) 生成 {"task_info":{...},"target":{...},"scan_options":{...}}
      └─ QueueLine(...) 入写队列（上限 kMaximumQueuedRequests = 256）
3. WriteLoop 线程写 stdin → 引擎 main.rs 的 NDJSON 读取循环
4. 引擎 scanner::Scanner::scan_request(req)
      └─ tokio::task::spawn_blocking + rayon into_par_iter() 并行处理每个路径
5. 单文件流水线（见第 4.2 节）逐层执行，产出 ScanResult
6. 引擎把结果序列化为 NDJSON 帧写回 stdout
7. GUI 的 WorkerLoop 读到行 → DecodeJsonLine → 派发到 DispatcherQueue → 更新 UI
8. 若判定为恶意且启用了主动防御 → 引擎执行 HIPS 队列 / 回滚 / 隔离
```

每一步的并发模型都是**单问单答**：GUI 侧协议刻意设计成"一次只允许一个手动扫描在途"（`m_inflight_scan` / `m_waiting_response`），取消操作是**协作式**的——已入队的请求立即移除，在途请求由引擎在超时或取消边界返回。

## 1.4 关键设计决策

### 决策 1：内核只做拦截，不做判断

内核侧不链接任何浮点代码、不解析 PE、不做字符串匹配（除了短常量）。所有"是否恶意"的判断都由用户态完成，内核只执行用户态下发的策略。这样做的收益是：内核的代码量小、可审计、崩溃面小，且不会因为一个启发式规则的 bug 而 BSOD。

### 决策 2：`g_enforcement_matrix` 单表描述全部拦截面

内核的 6 个拦截面不是散落的 `if` 分支，而是一张表（`driver/src/kernel_components.cpp`）：

```cpp
EnforcementRow g_enforcement_matrix[EVERBLOOM_ENFORCEMENT_SURFACE_COUNT] = {
    { "process_notify", TRUE,  0,                                   install_process_notify, remove_process_notify, 0 },
    { "file_filter",    TRUE,  EVERBLOOM_CAPABILITY_RAW_DISK_POLICY, install_file_filter,    remove_file_filter,    0 },
    { "network_wfp",    TRUE,  EVERBLOOM_CAPABILITY_NETWORK_POLICY,  install_network_wfp,    remove_network_wfp,    0 },
    { "image_notify",   FALSE, 0,                                   install_image_notify,   remove_image_notify,   0 },
    { "registry",       FALSE, EVERBLOOM_CAPABILITY_REGISTRY_POLICY, install_registry,       remove_registry,       0 },
    { "object_handle",  FALSE, 0,                                   install_object_handle,  remove_object_handle,  0 },
};
```

- **行序 = 安装序**，`shutdown` 反向遍历同一张表 —— 不需要单独维护回滚清单；
- `static_assert` 钉住"每声明一个拦截面恰好一行"，防止有人加行忘改枚举导致 surface id 静默错位；
- `required = TRUE` 的面安装失败即整体回滚；`required = FALSE` 的面（镜像加载、注册表、对象句柄）被平台拒绝时**降级继续**，剩余防护仍然可用，能力查询相应停止声明这一位。

### 决策 3：能力位由实际注册状态派生，不硬编码

`EverbloomKernelComponentsCapabilityFlags()` 的行为：

- **控制面能力无条件**（`SCAN_FILE` / `BEHAVIOR_ANALYZE` / `POLICY_UPDATE` / `PROTECTION_UPDATE` / `EVENT_READ`）——它们由控制设备和 IOCTL ABI 提供，不依赖任何回调被平台接受；
- **强制能力按注册结果派生**（`RAW_DISK_POLICY` ← minifilter，`REGISTRY_POLICY` ← 注册表回调，`NETWORK_POLICY` ← WFP）；
- **`KERNEL_MODEL`（0x100）只在真的链入了模型时声明** —— 否则用户态会一直等一个永远不来的 `MODEL_SCORE` 事件。

`SCAN_FILE` 刻意**不**绑定 minifilter：它由 `dispatch_device_control` 提供，用户态 `driver_bridge.rs` 的 `is_compatible()` 依赖这一位来表达"这个驱动能接受文件扫描请求"。

### 决策 4：检测是"证据融合"，不是"串联投票"

引擎不采用"任何一层报毒就报毒"的串联结构，而是把每一层的输出作为**证据**送进 `ProtectionFusion`，由融合器按响应级别（Aggressive / Normal / Relaxed）做加权裁决。唯一的例外是**权威来源**：内核已阻断、精确哈希命中、YARA 命中——这些直接生效，不参与加权。

### 决策 5：四套特征表示，互不通用

引擎与内核里同时存在四套**互不通用**的特征表示，名称相近极易混淆，此处先钉死（详见 [第 5.5 节](05-检测层详解.md#55-三层特征契约容易混淆必须分清)）：

| 布局 | 维度 | 位置 | 用途 |
|------|------|------|------|
| **① Canonical base vector** | `[f32; 12]` | `engine/src/layers/ai.rs` 的 `AiModel::extract_features` | 引擎自己算得出的特征基元，始终存在 |
| **② Model input contract** | 由 `features.json` 长度决定；随包为 **1283** | `features.json`（运行期从模型目录加载） | 实际喂给 ONNX 的张量；`[1,1,1283]` |
| **③ Offline feature space** | `STATIC_TOTAL 1892` + `DYNAMIC_TOTAL 380` = **2272** | `engine/src/features/mod.rs` | 离线数据集/训练侧表示，**不参与运行时推理** |
| **④ Kernel model features** | 12 个整数，值域 `[0,127]` | `driver/include/everbloom_kernel_model.h` | 内核侧早期打分，由映像路径/命令行派生 |

关键关系：

- **① → ② 是"名字驱动的展开"**，不是矩阵投影。`extract_named_features` 按 `features.json` 里的名字逐个取值：命中 12 个规范名 → `base[i]`；`dllhash_N` / `apihash_N` → 桶命中得 `0.0`/`1.0`；未知名字 → `0.0`。换模型只需换 `.onnx` + 配套 `features.json`，**不改代码**。
- **③ 与 ② 之间没有任何转换路径**。不存在"2272 投影到 1283"这一步；③ 目前也只被 `lib.rs` 重新导出，无业务代码消费。
- **④ 刻意不同于 ①**：内核只读映像路径与命令行（内核里能低成本拿到的），引擎读 PE 结构与字节统计。两边各训各的模型，**不可互换**。

## 1.5 运行时目录布局

安装后（`DEPLOYMENT_LAYOUT.md`）：

```
<install>/
  bin/     everbloom_gui.exe、everbloom_engine.exe、模型与数据、driver/、tools/
  driver/  everbloom_driver.inf / .cat / .sys
  share/   everbloom/assets（图标、侧栏 SVG）、windows-app-runtime/win10-x64（MSIX）
  doc/     LICENSE、README 等文档
```

资源查找顺序为三级回退：**环境变量 → exe 同目录 → 仓库相对路径**。这使同一份二进制既能跑安装态，也能跑开发态。
