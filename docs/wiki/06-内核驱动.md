# 6. 内核驱动

`everbloom_driver.sys` 是 Everbloom Security 的**拦截层**：一个 x64、Native 子系统的 Windows 内核驱动，导入 `FLTMGR`（minifilter 框架）与 `fwpkclnt`（WFP 网络过滤）。

代码规模：真内核源码 **2,847 行**（`sys_driver.cpp` 476 + `kernel_policy.cpp` 938 + `kernel_components.cpp` 1,433），加内核模型与数学核心 **970 行**（`kernel_model.cpp` 146 + 两个头文件 824）。

---

## 6.1 两套互不相干的代码

驱动目录下存在**两套完全不同**的代码，容易混淆，必须先分清：

| 代码 | 文件 | 行数 | 是否进内核 |
|------|------|------|------------|
| **真内核** | `src/sys_driver.cpp`、`src/kernel_policy.cpp`、`src/kernel_components.cpp`、`src/kernel_model.cpp` | 476 / 938 / 1,433 / 146 | ✅ |
| **用户态仿真桩** | `src/core_protection.cpp`、`self_protection.cpp`、`file_protection.cpp`、`amsi.cpp`、`realtime_scan.cpp`、`network_firewall.cpp`、`advanced_threat.cpp`、`event_bus.cpp`、`logger.cpp`、`irp_dispatcher.cpp` | 各 23–42 行 | ❌ |

用户态桩被编译进静态库 `everbloom_driver_core`，由 `everbloom_driver_stub.exe` 链接。`driver/CMakeLists.txt` 明确**禁止**把这些桩链入内核镜像——它们的用途是提供一个可在用户态演练的驱动接口形状（便于测试与文档化），而不是内核实现。

> `README.md` 中列出的"驱动模块"（core_protection、self_protection、file_protection、amsi、realtime_scan、network_firewall、advanced_threat、event_bus、logger、irp_dispatcher）指的就是这些用户态桩。真内核的实际能力面由 6.2 节的表定义。

## 6.2 六个拦截面与 `g_enforcement_matrix`

内核注册 6 个拦截面，全部由一张表统一描述：

```cpp
EnforcementRow g_enforcement_matrix[EVERBLOOM_ENFORCEMENT_SURFACE_COUNT] = {
    { "process_notify", TRUE,  0,                                   install_process_notify, remove_process_notify, 0 },
    { "file_filter",    TRUE,  EVERBLOOM_CAPABILITY_RAW_DISK_POLICY, install_file_filter,    remove_file_filter,    0 },
    { "network_wfp",    TRUE,  EVERBLOOM_CAPABILITY_NETWORK_POLICY,  install_network_wfp,    remove_network_wfp,    0 },
    { "image_notify",   FALSE, 0,                                   install_image_notify,   remove_image_notify,   0 },
    { "registry",       FALSE, EVERBLOOM_CAPABILITY_REGISTRY_POLICY, install_registry,       remove_registry,       0 },
    { "object_handle",  FALSE, 0,                                   install_object_handle,  remove_object_handle,  0 },
};
```

### 对应的内核 API

| 行 | 拦截面 | 内核 API | 能力 |
|----|--------|----------|------|
| 0 | `process_notify` | `PsSetCreateProcessNotifyRoutineEx` | 进程创建拦截 |
| 1 | `file_filter` | `FltRegisterFilter` | 文件 I/O 拦截（minifilter） |
| 2 | `network_wfp` | `FwpsCalloutRegister2` | 网络连接拦截 |
| 3 | `image_notify` | `PsSetLoadImageNotifyRoutine` | **仅遥测**，不拦截 |
| 4 | `registry` | `CmRegisterCallbackEx` | 注册表写入拦截 |
| 5 | `object_handle` | `ObRegisterCallbacks` | 对象句柄权限拦截 |

### `required` 字段的语义

- `TRUE`（前三行）：安装失败 → **整体回滚并返回错误**。这三个是核心防护面，缺一不可；
- `FALSE`（后三行）：安装失败 → **降级继续**。可能被平台拒绝的原因包括签名策略、altitude 冲突等。剩余防护仍然可用，能力查询相应停止声明对应的位。

### `static_assert` 守护

```cpp
static_assert(
    sizeof(g_enforcement_matrix) / sizeof(g_enforcement_matrix[0])
        == EVERBLOOM_ENFORCEMENT_SURFACE_COUNT,
    "enforcement matrix must have exactly one row per declared surface");
```

**行索引就是 surface id**：`EverbloomKernelComponentsActiveSurfaces()` 为第 `i` 行报告位 `i`。如果新增一行而忘记更新头文件的 `EVERBLOOM_ENFORCEMENT_SURFACE` 枚举，所有 surface id 会**静默错位**——这个 `static_assert` 就是为了让这种错误在编译期暴露。

### 安装与卸载

```cpp
NTSTATUS EverbloomKernelComponentsInitialize(PDRIVER_OBJECT driver_object) {
    KeInitializeSpinLock(&g_ransom_tracker_lock);
    RtlZeroMemory(g_ransom_trackers, sizeof(g_ransom_trackers));
    // 清零所有 installed 标志
    for (index...) { InterlockedExchange(&row.installed, 0); }

    for (index...) {
        EnforcementRow& row = g_enforcement_matrix[index];
        const NTSTATUS status = row.install(driver_object);
        if (NT_SUCCESS(status)) { InterlockedExchange(&row.installed, 1); continue; }
        if (row.required) {
            EverbloomKernelComponentsShutdown();   // 反向遍历同一张表回滚
            return status;
        }
        // 可选面被拒绝：继续
    }
    return STATUS_SUCCESS;
}

VOID EverbloomKernelComponentsShutdown() {
    for (ULONG index = EVERBLOOM_ENFORCEMENT_SURFACE_COUNT; index > 0; --index) {
        EnforcementRow& row = g_enforcement_matrix[index - 1];
        if (InterlockedExchange(&row.installed, 0) != 0) { row.remove(); }
    }
    // 清理勒索追踪表
}
```

**没有单独的回滚清单**——回滚就是反向遍历安装表。这消除了"回滚清单与安装逻辑不同步"这一类 bug。

`InterlockedExchange(&row.installed, 0) != 0` 的写法保证**每个面只被拆一次**，即使 shutdown 被走到两次（回滚路径 + `DriverUnload`）。

## 6.3 能力位派生

```cpp
ULONG64 EverbloomKernelComponentsCapabilityFlags() {
    ULONG64 flags = EVERBLOOM_CAPABILITY_SCAN_FILE
        | EVERBLOOM_CAPABILITY_BEHAVIOR_ANALYZE
        | EVERBLOOM_CAPABILITY_POLICY_UPDATE
        | EVERBLOOM_CAPABILITY_PROTECTION_UPDATE
        | EVERBLOOM_CAPABILITY_EVENT_READ;

    for (index...) {
        if (surface_is_installed(g_enforcement_matrix[index])) {
            flags |= g_enforcement_matrix[index].capability_flags;
        }
    }

    if (EverbloomKernelModelGet() != nullptr) {
        flags |= EVERBLOOM_CAPABILITY_KERNEL_MODEL;
    }
    return flags;
}
```

### 能力位定义

| 位 | 值 | 来源 |
|----|-----|------|
| `SCAN_FILE` | `0x1` | **无条件**（控制面） |
| `BEHAVIOR_ANALYZE` | `0x2` | **无条件** |
| `POLICY_UPDATE` | `0x4` | **无条件** |
| `PROTECTION_UPDATE` | `0x8` | **无条件** |
| `EVENT_READ` | `0x10` | **无条件** |
| `REGISTRY_POLICY` | `0x20` | 派生：注册表回调安装成功 |
| `RAW_DISK_POLICY` | `0x40` | 派生：minifilter 安装成功 |
| `NETWORK_POLICY` | `0x80` | 派生：WFP 安装成功 |
| `KERNEL_MODEL` | `0x100` | 派生：真的链入了模型 |

### 为什么 `SCAN_FILE` 不绑 minifilter

源码注释明确说明：

> *"`EVERBLOOM_CAPABILITY_SCAN_FILE` is served by `dispatch_device_control`, not by the minifilter, so it stays unconditional and `is_compatible()` on the user-mode side keeps its meaning."*

`SCAN_FILE` 表达的是"这个驱动能接受文件扫描请求"（通过 IOCTL），而不是"这个驱动挂了文件过滤"。用户态 `driver_bridge.rs` 的 `is_compatible()` 依赖这一位的稳定语义。

### 为什么能力位不能硬编码

源码注释记录了一段历史教训：

> *"Previously all eight flags were reported unconditionally while the registry and object callbacks were installed with `(void)`, so the driver advertised registry and network enforcement that the platform may have refused."*

硬编码能力位会导致用户态相信一个实际不存在的防护面。派生式声明让"声称"与"事实"始终一致。

## 6.5 整数推理核心（`everbloom_kernel_matrix.h`，311 行）

内核里的神经网络推理**不能有浮点**——`DISPATCH_LEVEL` 上不允许 FPU 操作。因此这套推理核心是**纯整数**的。

### 设计约束

| 约束 | 实现 |
|------|------|
| 无浮点 | 全部 `int8` / `int32` 算术 |
| 无动态分配 | 所有缓冲在栈上或 `const` 静态数据 |
| 无锁 | 纯函数，无共享状态 |
| 无依赖 | **只 include `<stdint.h>`** |

### 常量

```c
#define EVERBLOOM_MATRIX_MAX_UNITS   64u
#define EVERBLOOM_MATRIX_MAX_LAYERS  4u
#define EVERBLOOM_MATRIX_MAX_SHIFT   62u

#define EVERBLOOM_MATRIX_OK           0
#define EVERBLOOM_MATRIX_ERR_NULL    (-1)
#define EVERBLOOM_MATRIX_ERR_SHAPE   (-2)
#define EVERBLOOM_MATRIX_ERR_LAYERS  (-3)
#define EVERBLOOM_MATRIX_ERR_SHIFT   (-4)
```

### 三个非显而易见的设计点

**① `EVERBLOOM_MATRIX_MAX_SHIFT = 62`，不是 31**

乘数归一化为 Q31 定点。真实 per-tensor 尺度约 `1e-2`，Q31 表示后需要约 **37 位**右移才能回到正确量级。若把上界设成 31，乘数只剩约 24 位有效位——精度损失会直接体现在评分上。因此上界设为 62（在 64 位累加器上仍安全）。

**② 取整必须是"半数远离零"**

必须用**"截断余数 vs 半数阈值"**的实现方式（gemmlowp 的 `RoundingDivideByPOT` 形式）：

```
remainder = value & ((1 << shift) - 1)
if (remainder >= (1 << (shift - 1))) { result = (value >> shift) + 1; }
else                                { result = value >> shift; }
```

**不能**用"加 half 再算术右移"——算术右移是**向下取整**，会把可精确表示的 `-1000.0` 变成 `-1001`。这个偏差在多层网络里会累积。

**③ 末层以 int32 全精度返回**

不窄化为 `int8`。如果末层输出 `int8`，评分就只有 256 个级别，阈值判定过粗——`0.55` 与 `0.70` 这样的阈值在 256 级上难以精确区分。

### 错误码与评分域分离

`EVERBLOOM_MATRIX_ERR_*` 都是**负数**。为了让调用方能区分"推理失败"与"推理得出低分"，模型的**输出域必须非负**——即末层的 `activation_min = 0`。这样：

- 返回值 `< 0` → 失败（带具体错误码）；
- 返回值 `>= 0` → 有效评分。

### 测试

`everbloom_kernel_matrix_tests`，**106 个断言**。该目标**位于 WDK guard 之外**，在没有内核工具链的机器上也能构建运行——它是模型数学唯一的自动化检查。

## 6.6 内核特征契约（`everbloom_kernel_model.h`，513 行）

内核只能低成本地拿到**映像路径与命令行**，因此内核模型的 12 个特征全部由这两者派生，取值域 `[0, 127]`。

### 12 个特征

| # | 枚举名 | 含义 |
|---|--------|------|
| 0 | `EverbloomFeaturePathLength` | 完整路径长度 |
| 1 | `EverbloomFeatureBasenameLength` | 文件名长度 |
| 2 | `EverbloomFeatureUserWritableDir` | 位于用户可写目录 |
| 3 | `EverbloomFeatureSystemDir` | 位于系统目录 |
| 4 | `EverbloomFeatureExecutableExtension` | 可执行扩展名（`.exe`/`.dll`） |
| 5 | `EverbloomFeatureScriptExtension` | 脚本扩展名（`.ps1`/`.js`/`.vbs`/`.bat`） |
| 6 | `EverbloomFeatureDoubleExtension` | 双扩展名（如 `report.pdf.exe`） |
| 7 | `EverbloomFeatureLolbinName` | LOLBin 名称（系统自带可被滥用工具） |
| 8 | `EverbloomFeatureDigitRatio` | 文件名数字比例 |
| 9 | `EverbloomFeatureDistinctCharacterRatio` | 不同字符比例 |
| 10 | `EverbloomFeatureCommandLineLength` | 命令行长度 |
| 11 | `EverbloomFeatureObfuscatedCommand` | 命令行混淆特征 |

```c
#define EVERBLOOM_KERNEL_FEATURE_COUNT  12u
#define EVERBLOOM_KERNEL_FEATURE_MAX    127
#define EVERBLOOM_KERNEL_MODEL_NO_INDEX 0xFFFFFFFFu
```

### 目录标记

```c
static const char* const kEverbloomUserWritableMarkers[] = {
    "\\temp\\", "\\appdata\\", "\\downloads\\",
    "\\$recycle.bin\\", "\\programdata\\", "\\users\\public\\",
};
```

注释解释了为什么可以做**简单子串匹配**：

> *"A directory component is always followed by a separator, so an ordinary substring test is exact here: it cannot match a file whose **name** merely contains "temp", because that occurrence is not delimited by separators on both sides."*

即 `\temp\` 前后的分隔符保证了匹配的是**目录组件**，而不是文件名里恰好含 "temp" 的字符串。这避免了 `mytempfile.exe` 被误判。

系统目录标记（`kEverbloomSystemMarkers`）的存在是为了让模型可以**负向加权**——位于 `System32` 的文件应该降低可疑度。

### 与引擎 12 维特征的关系

**刻意不同，且不可互换**：

| | 内核 12 特征 | 引擎 12 特征 |
|---|---|---|
| 输入 | 映像路径 + 命令行 | PE 结构 + 字节统计 |
| 位置 | `driver/include/everbloom_kernel_model.h` | `engine/src/layers/ai.rs` |
| 训练 | `tools/` 导出器 | `tools/train_feature_cnn.py` |

内核拿不到 PE 结构（那需要读文件内容，成本高且不能在 `DISPATCH_LEVEL` 做），引擎也拿不到"这次进程创建的命令行"（那是内核回调的上下文）。因此两边各用各的特征，各训各的模型。

## 6.7 内核模型的打分与回传

### 权重表（`kernel_model.cpp`，146 行）

`kernel_model.cpp` **刻意不包含任何内核头文件**。这样做的直接好处是：用户态测试目标（`everbloom_kernel_matrix_tests`）链接的就是驱动发布的那张表——测的是真东西，不是副本。

只有**数据的段位置**是内核相关的：`const` 数据默认落在非分页段（`INIT`/`PAGE` 之外），因此权重表在 `DISPATCH_LEVEL` 也能访问。**不要**把权重表移入 `PAGE` 段。

### 接入点：`EverbloomProcessNotify`

```cpp
VOID NTAPI EverbloomProcessNotify(
    PEPROCESS Process, HANDLE ProcessId,
    PPS_CREATE_NOTIFY_INFO CreateInfo) { ... }

VOID record_advisory_model_score(PPS_CREATE_NOTIFY_INFO create_info) { ... }
```

行为：

1. 驱动防护开启时，对**每次进程创建**打分；
2. 只有评分越过模型的 `output_threshold` 才记录事件；
3. **已被阻断的创建不再重复打分**——避免为同一事件产生两条记录。

### 评分如何回传

```c
EVERBLOOM_EVENT_KIND_MODEL_SCORE = 7
```

评分放在事件的 **`Status` 字段**。这个选择有明确理由：

> *"`Status` 是 `EVERBLOOM_DRIVER_EVENT` 唯一空闲的数值字段，按 Kind 赋予含义可让用户态直接读数字，无需解析 `Reason`，也避免为一条建议性信号改动 `driver_bridge.rs` 用 `#[repr(C)]` 镜像的结构布局。"*

即在 `Kind == MODEL_SCORE` 时，`Status` **不表示 NTSTATUS**，而是评分值。这是"按 Kind 复用字段"的约定，必须在两侧文档中保持一致。

### 能力位

无模型链入时**不声明** `EVERBLOOM_CAPABILITY_KERNEL_MODEL`（0x100）。用户态因此不会等待一个永远不会到来的 `MODEL_SCORE` 事件。

### 路径绝不否决

内核模型是**建议性信号**，它从不否决（veto）一个进程创建。原因：

- 特征只有 12 个、全部来自路径与命令行，信息量有限；
- 误报的代价是阻断合法程序启动，用户体验代价高；
- 真正的裁决权在用户态融合器。

### 引擎侧的刻意不作为

引擎的 `record_kernel_behavior_event` **刻意不**把 `MODEL_SCORE` 映射成行为事件。理由（记忆与源码注释一致）：

> *"模型只读映像路径与命令行，用户态关联本来就有，回灌等于把本流水线自己的输入伪装成独立证据。"*

如果把内核模型分当成"独立的行为证据"再喂给融合器，就会出现"同一份输入被算两次"的循环论证。因此 MODEL_SCORE 只作为**参考信息**呈现给用户态，不参与融合加权。

## 6.8 minifilter altitude 策略

### 组与区间

| 项 | 值 |
|----|-----|
| 组 | `FSFilter Anti-Virus` = **320000–329999** |
| `Class` | `AntiVirus` |
| `ClassGuid` | `{b1d1a169-c54f-4379-81db-bee7d88d7454}` |
| `LoadOrderGroup` | `"FSFilter Anti-Virus"` |
| minifilter altitude | **329671** |
| 对象句柄 altitude | **329670** |

**三者必须互相一致**：`Class`、`ClassGuid`、`LoadOrderGroup` 描述的是同一个"反病毒过滤组"。若 `ClassGuid` 与组名不匹配（历史上曾用过伪造值），Filter Manager 会拒绝加载。

> 320000–329999 是 FSFilter Anti-Virus 区间。280000–289999 是 Continuous Backup（备份软件），360000–389999 是 Activity Monitor（只观察上报的组）。选错区间意味着过滤器被挂到一个语义不符的位置。

### altitude 越大 = 越早看到 I/O

组内 altitude 越大，过滤器挂得越**远离**文件系统，因而越**早**看到 I/O 请求。Filter Manager 内部按栈序排列，这与加载顺序相反。

### 对象句柄共享同一命名空间

`ObRegisterCallbacks` 的 `Altitude` 与 minifilter **共用同一 altitude 命名空间**，因此两者**不能取同一个值**——否则本驱动与自己撞号，句柄防护面每次加载都会失败。

`ObRegisterCallbacks` 文档确认它会返回 `STATUS_FLT_INSTANCE_ALTITUDE_COLLISION`，所以句柄回调也走同样的递减重试逻辑。

> `OB_CALLBACK_REGISTRATION.Altitude` 的文档**并未**规定 320000–329999 这个范围——真正的约束只是**全局唯一**。之所以仍选组内值，是为了与 minifilter 保持一致的部署语义。

### INF 要点

```ini
Class         = AntiVirus
ClassGuid     = {b1d1a169-c54f-4379-81db-bee7d88d7454}
CatalogFile   = everbloom_driver.cat
DriverVer     = 08/04/2026,1.0.0.0
LoadOrderGroup = "FSFilter Anti-Virus"
Dependencies  = FltMgr
[SourceDisksFiles]  everbloom_driver.sys
[Strings]
  ServiceName     = "EverbloomSecurity"
  DefaultInstance = "EverbloomSecurity Instance"
  Altitude        = "329671"
```

两条硬要求：

1. **`Dependencies = FltMgr`** —— 过滤器管理器必须先于任何 minifilter 运行；
2. **无论 `StartType` 为何，都必须指定 `LoadOrderGroup`**。

`[InstanceAddReg]` 写入 `Instances`、`Altitude`、`Flags` 三个注册表项。

### Microsoft 分配何时需要

- **首次**向某个组添加过滤器需要向 Microsoft 申请 altitude；
- **在已有分配值之后追加**（如 `325000.7`）**无需重新申请**；
- **`329671` 已定为可直接使用的值**：测试签名 / 自签名部署可正常加载挂载，且不与占用整数位的既有过滤器冲突；
- Microsoft 分配**只在走 WHQL / 认证签名服务时才需要**，属于分发前的文书步骤，不是功能前提。

## 6.9 运行期调整 altitude 的三种手段

三种手段都已落地，语义各不相同。

### 手段 1：改注册表（首选）

**altitude 不编译进驱动**。Filter Manager 在加载时从服务键读取：

```
HKLM\SYSTEM\CurrentControlSet\Services\<服务名>\Instances\<实例名>\Altitude
```

**类型必须是 `REG_SZ`**。

> ⚠️ 紧邻的 `ProtectedPaths` 确实是 `REG_MULTI_SZ`，很容易顺手写成 MULTI_SZ——而 Filter Manager 会因此**拒绝该实例**。

`tools/dev_driver.ps1 -Action install -Altitude <值>` 会在启动服务**之前**写入（写晚了无效）。

**语义**：**移动**正常实例到新的 altitude。

### 手段 2：`FltAttachVolumeAtAltitude`（仅调试）

Microsoft 文档明确：这是**调试支持例程**，"零售版 minifilter 不应调用"。

约束：

- 必须在 `FltStartFiltering` **之后**调用（否则返回 `STATUS_FLT_FILTER_NOT_READY`）；
- 必须在 `PASSIVE_LEVEL`；
- 每次成功附加都要配一次 `FltObjectDereference`。

本驱动的做法是**显式 opt-in + 附加式**：

```cpp
const WCHAR kAltitudeOverrideValue[] = L"AltitudeOverride";
```

- 只有当服务键下存在 `AltitudeOverride`（`REG_SZ`）时才执行；
- 在正常挂载**之后**运行；
- **失败不影响**文件过滤面。

实现函数：`altitude_override_query()`、`read_altitude_override()`、`attach_volumes_at_override_altitude()`。

**语义**：在正常实例之外**额外**挂一个实例（与手段 1 不同，手段 1 是移动）。

### 手段 3：撞号递减重试

两条路径（minifilter 与对象句柄）在遇到 `STATUS_FLT_INSTANCE_ALTITUDE_COLLISION` 时都会递减 altitude 并重试：

| 项 | 值 |
|----|-----|
| 重试上限 | `EVERBLOOM_ALTITUDE_RETRY_LIMIT` = **8** |
| 下界 | 320000（绝不越出组外） |
| 失败行为 | 到组下界仍失败 → 返回错误 |

**绝不越出 320000–329999**：越界会落到并非为之设计的组。

算术在 `driver/include/everbloom_altitude.h`（143 行，纯整数、无内核依赖），由 `everbloom_kernel_altitude_tests` 验证——**61 个断言，0 失败**。

> 为什么放在用户态测：真正触发撞号的现场无法按需复现，因此把算术单独提取成无内核依赖的头文件，在用户态穷举验证。

### 常量关系

```cpp
constexpr uint32_t EVERBLOOM_OBJECT_CALLBACK_ALTITUDE = EVERBLOOM_ALTITUDE_SHIPPED - 1u;
```

对象句柄的 altitude 由 minifilter 的 shipped 值**减 1** 派生（329671 → 329670），保证两者永不相同，且都在组内，留出完整的重试余量。

## 6.10 其它内核实现要点

### 勒索软件写入追踪

```cpp
constexpr ULONG kRansomTrackerCount = 128;
constexpr ULONGLONG kRansomWindow100ns      = 5ULL * 10ULL * 1000ULL * 1000ULL;   // 5 秒
constexpr ULONGLONG kRansomSlowWindow100ns  = 60ULL * 10ULL * 1000ULL * 1000ULL;  // 60 秒
constexpr ULONG kRansomWriteThreshold        = 200;
constexpr ULONG kRansomMixedDocumentThreshold = 32;
constexpr ULONG kRansomSlowDocumentThreshold  = 24;
constexpr ULONG kRansomVerySlowDocumentThreshold = 48;
```

- **128 个追踪槽**（按进程）；
- **快窗口 5 秒 / 慢窗口 60 秒**两个时间尺度；
- **快路径**：5 秒内 200 次写入 → 触发；
- **慢路径**：60 秒内 24 / 48 个**不同文档族**的写入 → 触发（区分"大量写同一文件"与"跨多种文档格式加密"）。

`document_family_bit()` 把路径映射到文档族位图（`ULONG`，最多 32 族），`record_ransomware_write()` 累加。

这个追踪器由 `KeInitializeSpinLock` 保护的 `g_ransom_trackers` 数组承载。

### 长针搜索的最小长度

内核侧的字符串搜索有最小长度约束（`kMinUnboundedNeedleLength = 5`）+ 词边界检查。原因是：过短的针（如 3 字符）在任意二进制里都会命中，产生大量误报。词边界检查进一步保证匹配的是完整词而不是更长标识符的子串。

### 浏览器 Cookie 保护

在 minifilter 的 pre-operation 里拦截"非浏览器进程以读方式打开 Cookie 库"。

### 受保护进程与目录

## 6.11 内核策略引擎（`kernel_policy.cpp`，938 行）

### 路径规范化与匹配

内核里的路径匹配**不能**用浮点、不能分配大内存，因此是手工实现的：

| 函数 | 作用 |
|------|------|
| `normalize_path()` | 把 `\??\C:\...` 之类的 DOS 设备路径规范化为可比较形式 |
| `split_components()` | 按分隔符切分路径组件（用 `starts`/`lengths` 数组，避免分配） |
| `equal_component()` | 组件级比较（大小写不敏感） |
| `dos_path_suffix_matches()` | 后缀匹配（规则是目录，实际是文件） |
| `process_rule_matches()` | 进程规则匹配（比对映像名） |
| `file_rule_matches()` | 文件规则匹配 |
| `registry_rule_matches()` | 注册表规则匹配 |
| `has_network_rule()` / `network_rule_equals()` | 网络规则匹配（IPv4 + 端口） |

### 规则存储

```cpp
typedef struct OwnedUnicodeRule { ... } OwnedUnicodeRule;

NTSTATUS copy_rule(OwnedUnicodeRule* destination, PCUNICODE_STRING source);
VOID free_rule(OwnedUnicodeRule* rule);
BOOLEAN rule_equals(PCUNICODE_STRING left, PCUNICODE_STRING right);
NTSTATUS update_prepared_unicode_rule(...);
NTSTATUS clear_unicode_rule(...);
```

规则是**自有内存**的 `UNICODE_STRING`（`OwnedUnicodeRule`），在 `update` 时替换、在 `clear` 时释放。这避免了引用调用方缓冲区的生命周期问题。

### 对外接口

```cpp
NTSTATUS EverbloomKernelPolicyInitialize();
VOID     EverbloomKernelPolicyShutdown();

NTSTATUS EverbloomKernelPolicyUpdate(const EVERBLOOM_POLICY_COMMAND* command, ...);
NTSTATUS EverbloomKernelPolicyClear(...);

NTSTATUS EverbloomKernelPolicySetProtection(BOOLEAN r3_enabled, BOOLEAN driver_enabled);
BOOLEAN  EverbloomKernelPolicyIsR3Enabled();
BOOLEAN  EverbloomKernelPolicyIsDriverEnabled();

BOOLEAN  EverbloomKernelPolicyIsVulnerableDriverPath(PCUNICODE_STRING path);
```

`EverbloomKernelPolicyUpdate` 首先校验：

```cpp

    || command->Action != EVERBLOOM_POLICY_ACTION_BLOCK) { return STATUS_INVALID_PARAMETER; }
```

然后按 `Kind` 分派到 PROCESS / FILE / REGISTRY / RAW_DISK / NETWORK 五条路径。

`EverbloomKernelPolicyIsVulnerableDriverPath` 与用户态的 `known_vulnerable_driver_name()` 是**同一份 basename 清单的两侧实现**，用于 BYOVD 早期拦截。

### 事件文本复制

```cpp
VOID copy_event_text(...);
```

把内核里的 `UNICODE_STRING` 安全复制到事件结构的定长 `WCHAR` 数组（`Target[260]` / `Reason[128]`），含截断保护。

## 6.12 驱动运维工具（`tools/dev_driver.ps1`）

| Action | 作用 | 已实测 |
|--------|------|--------|
| `sign` | 对驱动签名 | 未实跑（需测试签名 + 重启） |
| `install` | 创建服务并启动 | 仅验证了测试签名守卫（退出 4） |
| `uninstall` | 停止并删除服务 | — |
| `status` | 查询服务状态 | ✅ 退出 0，`service state: not-registered` |
| `smoke` | 探测设备存在性 | ✅ 退出 8，正确判 `device: absent` |

### 设计要点

- **刻意不用 `sc.exe`**（在本机被黑名单拦截），改用 **SCM API P/Invoke** 并显式指定 `SERVICE_KERNEL_DRIVER`；
- **包注册用 `pnputil`**（未被拦截），它会创建 minifilter 必需的 `Instances` / `Altitude` 注册表项；
- **开测试签名绝不隐式执行**（要改启动配置 + 重启），必须显式传 `-EnableTestSigning`；
- 报告按 **UTF-8** 写出；PowerShell 5.1 的 `Get-Content` 默认按 ANSI 读，必须显式 `-Encoding UTF8`。

### 退出码约定

| 码 | 含义 |
|----|------|
| 0 | 成功 / 兼容 |
| 2 | 前置条件不满足（如 INF 未找到） |
| 3 | 设备不存在 |
| 4 | 测试签名未启用 / 协议不兼容 |
| 5 | 其它失败 |
| 8 | smoke 探测判定设备缺失 |

## 6.14 能力考量小结

| 约束 | 原因 | 应对 |
|------|------|------|
| 内核不能有浮点 | `DISPATCH_LEVEL` 不允许 FPU | 纯整数 Q31 定点核心 |
| 内核不能动态分配大内存 | 分页/非分页池压力、IRQL 限制 | 定长结构 + `const` 静态数据 + 栈缓冲 |
| 内核代码量必须小 | 可审计性、崩溃面 | 只做查表与匹配，不做内容解析 |
| altitude 必须唯一 | 共享命名空间 | minifilter 329671 / 句柄 329670 |
| altitude 必须在组内 | 越界落入语义不符的组 | 递减重试硬下界 320000 |
| 源码必须纯 ASCII | codepage 936 编译会触发 C4819 | 用 `-` 而非排版破折号 |
| 能力位不能撒谎 | 硬编码曾导致"声称了不存在的防护" | 全部由注册状态派生 |
| 模型不能否决 | 12 特征信息量有限，误报代价高 | 只作建议性信号 |
| 评分字段必须复用 | 共享 `#[repr(C)]` 布局不宜轻改 | 复用 `Status`，按 Kind 赋予含义 |
