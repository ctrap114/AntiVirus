# 3. 构建与打包

## 3.1 三段式构建

Everbloom Security 使用**三种构建系统各管一段**，由顶层 CMake 串联：

```
┌─ 段 1：Cargo ────────────────────────────────────────────────┐
│  cargo build --release --manifest-path engine/Cargo.toml      │
│  → engine/target/release/everbloom_engine.exe                 │
│  由 CMake 的 add_custom_target(engine ALL) 驱动                │
└──────────────────────────────────────────────────────────────┘
                            ↓
┌─ 段 2：CMake + Ninja（顶层） ────────────────────────────────┐
│  cmake -S . -B <build> -G Ninja -DCMAKE_BUILD_TYPE=Release     │
│  cmake --build <build>                                        │
│  → everbloom_gui.exe（经 add_subdirectory(gui)）              │
│  → stage_engine 目标（把运行时资源复制到构建树）                │
└──────────────────────────────────────────────────────────────┘
                            ↓
┌─ 段 3：CMake install ────────────────────────────────────────┐
│  cmake --install <build> --prefix artifacts/package/install    │
│  → 暂存树（54 个文件 / 约 107 MB）                             │
└──────────────────────────────────────────────────────────────┘
                            ↓
┌─ 段 4（可选，独立）：驱动 ───────────────────────────────────┐
│  cmake -S driver -B driver/build -G Ninja                     │
│  → everbloom_driver.sys / _stub.exe / 两个测试 exe             │
└──────────────────────────────────────────────────────────────┘
                            ↓
┌─ 段 5（可选）：Inno Setup ───────────────────────────────────┐
│  tools/build_install_full.ps1 → build_installer.ps1 → ISCC.exe │
│  → 单个 Setup.exe                                             │
└──────────────────────────────────────────────────────────────┘
```

驱动构建与主构建**互相独立**：`driver/` 有自己的 `CMakeLists.txt`，顶层 CMake 通过 `option(BUILD_DRIVER "Build the optional driver components" OFF)` 控制是否纳入（默认关闭，因为需要 WDK）。

## 3.2 顶层 CMakeLists.txt

### 项目与选项

```cmake
project(EverbloomSecurity VERSION 1.0.0 LANGUAGES CXX C)

option(BUILD_DRIVER          "Build the optional driver components"      OFF)
option(BUILD_TESTS           "Build EverbloomSecurity test targets"      ON)
option(EVERBLOOM_BUILD_ENGINE "Build the Rust engine from source"        ON)
option(EVERBLOOM_INSTALL_PYTHON "Install the Python packages (editable)" ON)
```

### 运行时资源路径（第 39–75 行）

这些变量是构建期的"真值来源"，`stage_engine` 与 `install()` 规则都引用它们：

| 变量 | 值 |
|------|-----|
| `EVERBLOOM_ENGINE_BINARY` | `engine/target/release/everbloom_engine.exe` |
| `EVERBLOOM_HASH_DB` | `data/local_hashes.sqlite` |
| `EVERBLOOM_LEGACY_HASH_DB` | `hashdb/HashDB.db` |
| `EVERBLOOM_AI_MODEL` | `${CMAKE_CURRENT_SOURCE_DIR}/everbloom_feature_cnn.onnx` |
| `EVERBLOOM_AI_MODEL_FEATURES` | `${CMAKE_CURRENT_SOURCE_DIR}/features.json` |
| `EVERBLOOM_AI_MODEL_CONTRACT` | `${CMAKE_CURRENT_SOURCE_DIR}/model_contract.json` |
| `EVERBLOOM_DENSE_TREE_MODEL` | `artifacts/models/tree_ensemble/everbloom_dense_tree.onnx` |
| `EVERBLOOM_RULES_DIR` | `data/rules/` |
| `EVERBLOOM_ALLOWLIST_FILE` | `data/allowlist.json` |
| `EVERBLOOM_VULNERABLE_DRIVERS_FILE` | `data/vulnerable_drivers.json` |

> **注意**：主 AI 模型的三个文件（`.onnx` / `features.json` / `model_contract.json`）在**仓库根目录**，且是必需项——缺失会让 `cmake --install` 报 `file INSTALL cannot find`。

### 可选模型的门控

稠密树模型是**可选的**，用三重 `EXISTS` 门控：

```cmake
set(EVERBLOOM_OPTIONAL_MODEL_STAGE_COMMANDS)
if(EXISTS "${EVERBLOOM_DENSE_TREE_MODEL}"
        AND EXISTS "${EVERBLOOM_DENSE_TREE_MODEL_FEATURES}"
        AND EXISTS "${EVERBLOOM_DENSE_TREE_MODEL_CONTRACT}")
    list(APPEND EVERBLOOM_OPTIONAL_MODEL_STAGE_COMMANDS ...)
endif()
```

三个文件任一缺失，该模型被**静默排除**（只在配置日志打印 "Optional dense tree AI model is not available"），构建继续。这是一条刻意的容错设计：模型是增强项，不应该让整个构建失败。

### `stage_engine` 目标

`add_custom_target(stage_engine ALL ...)` 把上述全部运行时资源复制进构建树，使 `everbloom_gui.exe` 在开发态也能就地运行（引擎与 GUI 同目录，`EngineProcess::Start` 会在 exe 同目录找 `everbloom_engine.exe`）。

### install 规则

```
install(PROGRAMS ${EVERBLOOM_ENGINE_BINARY}  → bin/)
install(FILES    ${EVERBLOOM_HASH_DB}        → bin/data/)
install(FILES    ${EVERBLOOM_LEGACY_HASH_DB} → bin/data/)
install(FILES    ${EVERBLOOM_AI_MODEL} ...   → bin/)
install(DIRECTORY ${EVERBLOOM_RULES_DIR}/    → bin/data/rules/)
install(FILES    ${EVERBLOOM_ALLOWLIST_FILE} ... → bin/data/)
```

### CPack WIX（备选打包路径）

顶层 CMake 还定义了 CPack 的 WIX 生成器配置，包含固定升级 GUID：

```cmake
CPACK_WIX_UPGRADE_GUID A2CD8223-686C-45E5-91F4-44F4F504D207
```

这条路径与 Inno Setup 路径**并存**：WIX 用于 MSI 分发场景，Inno Setup 用于主推的 Setup.exe。

## 3.3 GUI 构建（`gui/CMakeLists.txt`）

### 源文件收集

```cmake
file(GLOB_RECURSE WINUI_SOURCES winui/*.cpp)
list(FILTER WINUI_SOURCES EXCLUDE REGEX "vcpkg/.*\\.cpp$")
```

`GLOB_RECURSE` 会把 `gui/winui/` 下所有 `.cpp` 收进来，包括那些**尚未实现完成的自定义控件**。这些控件没有 `.g.cpp`（因为项目的 cppwinrt 调用不生成自定义组件投影），无法编译。因此有一道显式排除：

```cmake
set(EVERBLOOM_WIP_CONTROL_SOURCES
    App.xaml
    EverbloomButton
    EverbloomCard
    EverbloomNavigationView
    EverbloomScanRing
    MaterialAdapter
)
foreach(wip_source IN LISTS EVERBLOOM_WIP_CONTROL_SOURCES)
    list(FILTER WINUI_SOURCES EXCLUDE REGEX "/${wip_source}\\.cpp$")
endforeach()
```

排除后 GUI 视觉树全部由 `WinUIApp.cpp` 中的本地辅助函数（`EverbloomCard()`、`EverbloomButton()`，返回普通 `controls::Border` / `controls::Button`）构建，不依赖任何自定义 WinRT 组件。

### 目标定义

```cmake
add_executable(everbloom_gui WIN32 ${WINUI_SOURCES})
target_link_libraries(everbloom_gui PRIVATE
    WinAppSdk::Microsoft.WindowsAppSDK
    Microsoft::WindowsAppSDK
    ...
)
```

`WIN32` 关键字使产物为 **Windows GUI 子系统（subsystem 2）**。这一点有实际影响：PowerShell **不等待** GUI 子系统进程、也不填 `$LASTEXITCODE`，脚本化调用时需改用 `--driver-status-report <路径>` 写文件的方式获取结果。

### 资源安装

```
install(TARGETS everbloom_gui RUNTIME DESTINATION bin)
install(FILES assets/everbloom_icon.png assets/everbloom_icon.ico DESTINATION share/everbloom/assets)
install(DIRECTORY assets/sidebar/ DESTINATION share/everbloom/assets/sidebar PATTERN "*.svg")
install(FILES <4 个 MSIX> DESTINATION share/everbloom/windows-app-runtime/win10-x64)
```

## 3.4 驱动构建

```bash
export PATH="/f/insiders/VC/Tools/MSVC/14.51.36231/bin/Hostx64/x64:/c/Program Files (x86)/Windows Kits/10/bin/10.0.26100.0/x64:$PATH"
export INCLUDE="F:/insiders/VC/Tools/MSVC/14.51.36231/include;C:/Program Files (x86)/Windows Kits/10/Include/10.0.26100.0/ucrt;C:/Program Files (x86)/Windows Kits/10/Include/10.0.26100.0/um;C:/Program Files (x86)/Windows Kits/10/Include/10.0.26100.0/shared"
export LIB="F:/insiders/VC/Tools/MSVC/14.51.36231/lib/x64;C:/Program Files (x86)/Windows Kits/10/Lib/10.0.26100.0/ucrt/x64;C:/Program Files (x86)/Windows Kits/10/Lib/10.0.26100.0/um/x64"

cmake -S driver -B driver/build -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build driver/build
```

产物在 `driver/build/`：`everbloom_driver.sys`、`everbloom_driver_stub.exe`、`everbloom_kernel_matrix_tests.exe`、`everbloom_kernel_altitude_tests.exe`。

### 关键环境要点

1. **`rc.exe` / `mt.exe` 必须在 PATH 上**。缺了它们，CMake 在**编译器探测阶段**就失败，报 `CMAKE_MT-NOTFOUND` —— 这时还没有编译任何代码，错误信息容易误导。
2. **WDK `km` 树只在 `10.0.28000.0`**。`10.0.26100.0` 只有 `ucrt`/`um`/`shared`/`winrt`/`cppwinrt`，没有内核头。
3. **在 Git Bash 里用 `dumpbin` 必须写 `cmd //c "dumpbin /headers ..."`**。否则 Git Bash 会把 `/headers` 当路径转换成 `...\PortableGit\...\headers`，dumpbin 报 `LNK1181 无法打开输入文件`。更稳妥的做法是用 Python 直读 PE 头（`e_lfanew` 在 `0x3c`，machine 在 `e+4`，subsystem 在 `opt+68`）。

### 校验镜像属性（Python 直读，推荐）

| 产物 | Machine | Subsystem |
|------|---------|-----------|
| `everbloom_gui.exe` | x64 (`0x8664`) | 2 = Windows GUI |
| `everbloom_engine.exe` | x64 | 2 = Windows GUI |
| `everbloom_driver.sys` | x64 | 1 = Native |
| `everbloom_driver_stub.exe` | x64 | 3 = Console |

### `tools/build_install_full.ps1` 的职责

1. 可选调用 `driver/package/sign_driver.ps1` 做驱动签名；
2. 把 `everbloom_driver.inf`、第一个 `*.cat`、`everbloom_driver.sys` 暂存到 `artifacts/package/install/driver`；
3. 从 `jrsoftware/issrc` 引导 3 个 Inno Setup 语言文件；
4. 调用 `tools/build_installer.ps1`；
5. 写出 `build-report.json`。

> **✅ 驱动路径已改为自动探测（2026-10-01 修复）。** 原默认值 `driver\build\Release\everbloom_driver.sys` 与本仓库实际产出的单配置 Ninja 布局 `driver\build\everbloom_driver.sys` 不符，**直接执行会在找不到 `.sys` 时静默跳过签名，再暂存一个不存在的驱动**——即"自动化安装链直接失败"。现在 `$DriverSys` 默认为空表示自动探测，按序尝试：
>
> | 顺序 | 候选路径 | 对应布局 |
> | --- | --- | --- |
> | 1 | 显式 `-DriverSys` 传入值 | 始终优先；路径不存在会**报警告**而不是被忽略 |
> | 2 | `driver\build\everbloom_driver.sys` | Ninja / 单配置生成器（**当前实际使用**） |
> | 3 | `driver\build\Release\everbloom_driver.sys` | MSVC 多配置 |
> | 4 | `driver\build\Debug\everbloom_driver.sys` | MSVC 多配置（Debug） |
> | 5 | `artifacts\driver\bin\everbloom_driver.sys` | 旧文档提到的产物落点 |
>
> `build-report.json` 的 `driver_signing.driver_sys` 现在写入**解析后的绝对路径**（而非原始参数），并新增 `driver_sys_candidates` 列出全部候选，便于事后核对究竟用了哪一个。

驱动 INF 需要配套的 `.cat` 目录文件才能被 Windows 接受。工具位置特殊：

```

```

## 3.6 构建产物完整性校验

推荐在打包前做三项校验：

1. **PE 属性**：用 Python 直读 PE 头确认 subsystem（GUI=2 / Native=1 / Console=3）；
2. **哈希一致性**：安装树中的二进制应与构建输出**逐字节相同**（比对 MD5）；
3. **旧名残留**：全树搜索 `helios` / `HeliosAV`（大小写不敏感），确认零命中。

第三项尤其重要，因为历史遗留物（旧名脚本、旧名编译产物）可能藏在 `artifacts/**` 里——而 `artifacts/**` 通常不在改名脚本的覆盖范围内。

> **✅ 截至 2026-10-01，第三项已从"人工确认"升级为"构建门控"。** 此前 `artifacts/package/install/` 实测有 4 个文件命中旧名，且**都会被打包进安装包**——`tools/installer.iss` 的 `[Files]` 段显式声明了 `Source: "{#SourceDir}\doc\*"` 与带 `recursesubdirs` 的 `bin\*`：
>
> | 文件 | 命中数 | 根因 | 处置 |
> | --- | --- | --- | --- |
> | `install/doc/README.md` | 18 | 8-29 的旧版 README，与正确的 `share/doc/EverbloomSecurity/README.md`（10-01）**是两份不同的文件** | `build_installer.ps1` 每次构建前从 `README.md` 同步 |
> | `install/doc/SANDBOX_SECURITY.md` | 4 | 8-04 的旧版，首行 `# HeliosAV sandbox security` | 同上，从 `docs/SANDBOX_SECURITY.md` 同步 |
> | `install/bin/everbloom_feature_cnn.onnx` | 36 | **ONNX 内嵌元数据**：`producer_name = "HeliosAV feature CNN tract converter"` + `node[*].metadata_props` 里的 `File "E:\\HeliosAV\\pyas\\Engine\\Properties\\train_cnn.py"` torch 堆栈串 | `tools/sanitize_onnx_metadata.py` |
> | `install/bin/models/tree_ensemble/everbloom_dense_tree.onnx` | 3 | 同类：producer 元数据 + `graph.name` + `node.name` | 同上 |
>
> 三点值得记住：
>
> 1. **两个 `.onnx` 的命中用 `strings` 找不到**——它们位于 `node[*].metadata_props[].value`，被 protobuf 的长度前缀切断，只有裸字节正则（`grep -a`）才能命中。常规文本扫描会漏报。
> 2. **`install/doc/` 根本不是当前构建的产物**。`CMakeLists.txt` 第 254–257 行唯一的文档安装规则目标是 `CMAKE_INSTALL_DOCDIR`（即 `share/doc/EverbloomSecurity/`），全仓库没有任何规则写入 `install/doc/`。它是更早的目录布局留下的残留，因为 `cmake --install` 被指向了一个**已存在的**前缀目录而未被清理；向空目录重新安装不会产生它。
> 3. **模型里的旧名是"陈旧产物"而不是"改名漏改"**：`tools/convert_feature_cnn_for_tract.py` 与 `convert_tree_ensemble_for_tract.py` 早已写入 `EverbloomSecurity ...`，出厂的 `.onnx` 只是 8-09 生成的旧文件。修复因此不需要重新训练，只需重写元数据。
>
> **门控**（`tools/build_installer.ps1`，在调用 `ISCC.exe` 之前）：
>
> 1. 从 `README.md` / `docs/SANDBOX_SECURITY.md` 同步 `install/doc/`（该目录必须存在——`doc\*` 匹配不到文件会让 ISCC 直接编译失败）；
> 2. **逐字节、大小写不敏感地扫描整个暂存树**，命中 `helios` 即拒绝构建并列出文件。
>
> 为什么是字节扫描而不是文本扫描：ONNX 元数据被 protobuf 长度前缀切断，文本工具会漏；为什么是"拒绝构建"而不是"打警告"：旧名残留是**会出货的**问题，警告会被忽略。
>
> **仍未处理（不在暂存树内，不影响安装包）**：`artifacts/gui/bin/`、`artifacts/driver/bin/`、`artifacts/engine/bin/`、各 `cmake-ninja/` 缓存与 `artifacts/package/output/` 下的旧名产物。`artifacts/package/_stale-pre-rename/` 是**故意**保留的隔离区，不参与打包。
