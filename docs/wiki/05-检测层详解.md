# 5. 检测层详解

`engine/src/layers/` 下共 **18 个文件**。本章逐一拆解每一个。

> **命名说明**：这 18 个文件里**并不都是"检测层"**。严格说它们是 **18 个检测 / 决策相关模块**：
>
> - **检测层**（15 个）：哈希、YARA、启发式、AI、行为、序列、静态沙箱、威胁情报、ClamAV、Cookie 防护、内存快照、解包、进程状态，加上 `mod.rs`（模块声明）；
> - **决策器**（1 个）：`fusion.rs` —— 它不产生新证据，只裁决已有证据；
> - **基础设施**（1 个）：`cache.rs` —— 结果缓存，不检测；
> - **动作**（1 个）：`rollback.rs` —— 执行回滚，不检测；
> - **离线工具**（1 个）：`synthetic.rs` —— 合成语料生成，只用于训练，不参与扫描。
>
> 后 4 类保留在 `layers/` 下是因为它们与检测层共享同一套数据结构和常量。本章一并说明，但会明确标注各自性质。

### "权威" vs "证据"

- **权威来源**：一旦命中，直接产生 `Malicious`，不参与加权，也不被白名单压制（精确哈希 / YARA / ClamAV / 威胁情报 / 有序行为签名）；
- **证据来源**：输出一个 `[0,1]` 分数或一组指标，送进 `ProtectionFusion` 综合裁决（启发式 / AI / 行为 / 静态沙箱）。

## 5.1 哈希层（`hash.rs`）

### 三种摘要 + 模糊哈希

| 算法 | 用途 |
|------|------|
| MD5 | 兼容历史哈希库 |
| SHA-1 | 兼容历史哈希库 |
| SHA-256 | 主摘要 |
| **ssdeep 兼容模糊哈希** | 变形样本的相似度匹配 |

### 模糊哈希实现（标准 ssdeep 兼容）

| 常量 | 值 | 含义 |
|------|-----|------|
| `FUZZY_MIN_BLOCK_SIZE` | 3 | 最小块大小 |
| `FUZZY_PRIMARY_LIMIT` | 64 | 主哈希长度上限 |
| `FUZZY_SECONDARY_LIMIT` | 64 | 次哈希长度上限 |
| `FUZZY_MATCH_THRESHOLD` | **85** | 相似度百分比阈值 |
| `FUZZY_ALPHABET` | `A-Za-z0-9+/` | Base64 变体字母表 |
| `FUZZY_HASH_INIT` | `0x28021967` | 滚动哈希初始值 |
| `FUZZY_HASH_PRIME` | `0x01000193` | FNV 素数 |
| `FUZZY_ROLLING_WINDOW` | 7 | 滚动窗口字节数 |

块大小合法性校验：必须在 `[3, 1<<20]` 范围内，且是 3 的倍数（`block_size.is_multiple_of(FUZZY_MIN_BLOCK_SIZE)`）。签名必须只含字母表字符。

### 相似度计算

两个签名之间用**最长公共子串**（滚动窗口 7 字节）计算相似度：

```
similarity = (common_substring_length * SPAMSUM_LENGTH) / (len(a) + len(b))
```

`similarity >= 85` 即认为匹配。

### 能力考量

- **只有恶意记录能产生恶意裁决**。模糊匹配可能在良性文件之间产生高相似度（例如同一工具的不同版本），因此相似度匹配**只在对方是已知恶意时才产生结论**——`docs/detection_pipeline.md` 明确这条规则。
- **`ssdeep-lite:` 前缀**：历史版本使用的简化格式仍可读取，保证旧哈希库不失效。
- **SQLite schema**：`hashes` 表支持 `md5` / `sha1` / `sha256` / `ssdeep` / `ssdeep-lite` 五种列。
- 哈希层代码 2,035 行中约 800 行是自实现的 ssdeep 与测试——**刻意不依赖外部 ssdeep 库**，因为外部库在 Windows 上的可用性不可靠。

## 5.2 YARA 层（`yara.rs`）

### 接口

```rust
pub struct YaraScanner { ... }

impl YaraScanner {
    pub fn new<P: AsRef<Path>>(rules_dir: P) -> Result<Self, YaraError>;
    pub fn version(&self) -> u64;                              // 参与缓存键
    pub fn reload_rules(&self) -> Result<usize, YaraError>;    // 返回加载的规则数
    pub fn scan_bytes(&self, data: &[u8]) -> Result<Vec<YaraMatch>, YaraError>;
}

pub fn verify_rule_integrity(
    manifest_path: Option<PathBuf>,
    source_hashes: Vec<(PathBuf, String)>,
) -> Result<bool, String>;
```

### 规则完整性

`verify_rule_integrity` 用 `EVERBLOOM_RULE_INTEGRITY_MANIFEST` 指定的清单校验规则文件的哈希——防止"规则被替换成空规则集"这种静默失效攻击。

### 随包规则

`data/rules/everbloom_core.yar` 与 `everbloom_extended.yar`。规则集里还包含第三方规则（例如 Linux 恶意家族规则），这些是**独立的检测内容**，与产品命名空间无关。

### 能力考量

- YARA 使用 `yara` crate 的 `bundled-4_5_5` feature，YARA 4.5.5 静态链接——规则语法版本与引擎版本严格对应；
- `ndebug` feature 关闭 YARA 内部断言，避免在异常规则上崩溃；
- `reload_rules` 返回加载数量，使"规则文件存在但一条都没加载"这种问题可见。

## 5.3 启发式层（`heuristic.rs`，3,090 行）

引擎最大的单层，也是覆盖面最广的一层。

### 版本与常量

| 常量 | 值 |
|------|-----|
| `STATIC_RULES_VERSION` | **5**（参与缓存键） |
| `ENTROPY_WINDOW_BYTES` | **512** |
| `HIGH_ENTROPY_WINDOW_THRESHOLD` | **7.40** |

### 熵分析

把文件切成 512 字节窗口，统计：

- 熵 ≥ 7.40 的窗口数量；
- 检查过的窗口总数；
- 最长连续填充（filler run）长度，归一化为 `longest_filler_run / (windows * 512)`。

高熵窗口比例高 + 填充段长 → 典型的加壳/加密载荷特征。

### 规则集（约 55+ 条）

规则 id 采用 `family_behavior_chain` 命名法，权重与 id 一起定义。代表性规则：

| 规则 id | 权重 | 说明 |
|---------|------|------|
| `api_injection_chain` | 0.70 | 注入 API 组合（`VirtualAllocEx` + `WriteProcessMemory` + `CreateRemoteThread`） |
| `impact_recovery_inhibition_chain` | 0.74 | 破坏恢复能力（`vssadmin` / `wbadmin` / `bcdedit` 组合） |
| `driver_security_termination` | 0.72 | 尝试终止安全驱动 |
| `reverse_shell_chain` | 0.72 | 反弹 shell 特征 |
| `amsi_etw_bypass_chain` | 0.66 | AMSI / ETW 绕过 |
| `advanced_injection_chain` | — | 高级注入手法 |
| `anti_analysis_evasion_chain` | — | 反分析规避 |
| `container_evasion_chain` | — | 容器/沙箱规避 |
| `credential_harvest_chain` | — | 凭据收集 |
| `defender_tampering_chain` | — | Defender 篡改 |
| `defense_impairment_firewall_chain` | — | 防火墙削弱 |
| `dynamic_load_chain` | — | 动态加载 |
| `api_ransom_chain` | — | 勒索 API 组合 |
| `packer_detected` | 0.10 | 加壳检测（低权重，因为加壳本身合法） |
| `timestamp_anomaly` | 0.05 | 时间戳异常（极低权重，只是提示） |

还有大量单 API / 单字符串指示器（`createremotethread`、`virtualprotect`、`diskshadow`、`bitsadmin`、`certutil`、`cmstp`、`forfiles`、`frombase64string`、`downloadstring` 等）以及安全产品名称识别（`defender`、`avast`、`avira`、`bitdefender`、`crowdstrike`、`cylance`、`eset`、`360tray` 等）。

### 路径上下文加权

同一组 API 在不同目录下的可疑程度不同：

| 路径上下文 | 乘数 |
|-----------|------|
| `System32` | ×0.90 |
| `System32\Drivers` | ×1.10 |
| `Program Files` | ×0.95 |
| `Temp` / `Downloads` / `Desktop` | ×1.05 |

这条设计避免了"系统目录里的合法工具因为用了同样 API 就被误报"。

### 两套入口

```rust
pub fn analyze_bytes_with_context(blob: &[u8], context: &PathContext) -> HeuristicReport;
pub fn analyze_script_bytes(blob: &[u8]) -> HeuristicReport;
```

脚本类文件（`.ps1` / `.js` / `.vbs` / `.bat`）走独立路径——脚本没有 PE 结构，但可以匹配字符串型指示器（`downloadstring`、`frombase64string`、`iex` 等）。

### 契约守护

规则簿与 `score_static_signals` 的 `match` 分支必须同步。测试 `every_new_family_has_a_matching_scoring_arm` 保证"每新增一个规则族，必有对应的打分分支"——否则规则会被识别但拿不到分数。

### 能力考量

- **权重是标定过的，不是拍脑袋的**。0.05 的 `timestamp_anomaly` 与 0.74 的 `impact_recovery_inhibition_chain` 差了两个数量级，反映的是"单独出现时的证据强度"；
- **不追求单一规则定罪**。最重的规则 0.74 也低于 `Normal` 模式的干预阈值 0.70 之上但低于 0.90 的高置信阈值——它需要 AI 或行为的独立佐证才能升级为干预。

## 5.4 AI 层（`ai.rs`，2,542 行）

### 12 维特征契约

```rust
pub fn extract_features(blob: &[u8]) -> [f32; 12];
fn extract_features_with_size(blob: &[u8], file_size: u64) -> [f32; 12];
```

| # | 特征 | 说明 |
|---|------|------|
| 1 | coverage | 节区覆盖比例 |
| 2 | sections / 32 | 节区数归一化 |
| 3 | imports / 256 | 导入函数数归一化 |
| 4 | TLS | 是否含 TLS 目录 |
| 5 | timestamp anomaly | 时间戳异常度 |
| 6 | section entropy | 节区平均熵 |
| 7 | printable ratio | 可打印字符比例 |
| 8 | null ratio | 零字节比例 |
| 9 | distinct bytes | 不同字节值数量 |
| 10 | mean byte | 字节均值 |
| 11 | global entropy | 全局熵 |
| 12 | large-file flag | 是否大文件 |

**图像采样 64 KiB**：特征抽取只读文件头部 64 KiB，保证大文件的推理延迟有界。

### 推理后端

`tract-onnx 0.23.4`（纯 Rust）。模型文件 `everbloom_feature_cnn.onnx`（321,350 字节），配套 `features.json`（22,894 字节）与 `model_contract.json`（102 字节）。

### 特征缓存

```rust
const MAX_ENTRIES: usize = 1024;
```

`FeatureCache` 有两个子表（`base` 与 `named`），各自超过 1024 条时触发**整代刷新**（full-generation flush）——而不是逐条 LRU 淘汰。理由：特征抽取比缓存查找贵得多，整代刷新能保证高命中率，同时避免 LRU 链表维护开销。

### 结果结构

```rust
pub struct AiScore {
    score: f32,
    components: Vec<...>,        // 可解释性：各分量贡献
    is_fallback: bool,           // 是否走了降级路径
    fallback_reason: Option<String>,
}
```

`is_fallback` 与 `fallback_reason` 是关键设计：模型加载失败或超时时，AI 层**不静默返回 0 分**，而是标记降级。

> **⚠️ 这个标记以前到不了归因记录。** `scanner.rs` 从 `AiScore` 里只取了 `score` 与 `components`，把 `is_fallback` / `fallback_reason` 丢掉了——于是"模型真跑出 0.47"和"模型没跑、启发式顶了个 0.47"在记录里完全一样。2026-10-01 已修：`ScanResult.ai_fallback_reason` 承接该标记，`AttributionRecord` 的 `ai` 贡献项据此填 `unavailable`（见 [第 12.4.1 节](12-检测质量与验证.md#1241-harness-交付当天就抓到的两个缺陷已修) 缺陷二）。
>
> 同一轮修复还改掉了闸门的失败方式：推理许可排队超时以前会返回致命错误、让整个文件变成"无结论"，现在降级为带标记的启发式估计——AI 是证据源，不该有否决权（见 [第 12.6 节](12-检测质量与验证.md#126-detection-confidence-与-detection-authority-应当拆成两个维度)）。

### 模型管理

| 能力 | 说明 |
|------|------|
| 多模型 | `EVERBLOOM_AI_ENSEMBLE`、`EVERBLOOM_AI_BLEND_PRIMARY`、`EVERBLOOM_AI_MODEL_KIND` |
| 模型目录 | `EVERBLOOM_AI_MODEL_DIR`（GUI 默认为 `%LOCALAPPDATA%\EverbloomSecurity\models`） |
| 模型清单 | `EVERBLOOM_AI_MODELS_CONFIG`（`models.json`） |
| 降级模型 | `EVERBLOOM_AI_FALLBACK_MODEL` |
| 超时 | `EVERBLOOM_AI_MODEL_LOAD_TIMEOUT_MS`（默认 30,000）、`EVERBLOOM_AI_QUEUE_TIMEOUT_MS` |
| 并发 | `EVERBLOOM_AI_THREADS`、`EVERBLOOM_AI_MAX_IN_FLIGHT` |
| 边车文件 | `MAX_MODEL_SIDECAR_BYTES = 1 MiB` |

`AiModelInfo` / `AiModelValidationReport` 支撑 GUI 的"导入模型 / 校验模型"功能（`IMPORT_MODEL` / `VALIDATE_MODEL` 命令）。

### 能力考量

- **纯 Rust 推理的代价**：`tract` 不支持全部 ONNX 算子，因此训练侧需要算子兼容性转换（`tools/convert_feature_cnn_for_tract.py`、`docs/onnx_model_compatibility.md`）。收益是零原生依赖、可完全静态分发；
- **降级必须可见**。这是安全产品的基本要求：一个"悄悄失效"的检测层比没有这一层更危险；
- **正确的定位是"快速风险评分器"，而不是"主要恶意判定器"**。这一点必须说清楚，否则会高估 AI 层的覆盖：

#### AI 层的表达力边界（重要）

当前随包模型的实际形态（已实测）：输入 `[1, 1, 1283]`，输出 `logits [1,2]` + `probs [1,2]`，opset 18，11 个节点、9 个初始化器。

它的**信息来源**受两条硬约束限制：

| 约束 | 值 | 后果 |
|------|-----|------|
| 采样范围 | **文件头 64 KiB** | 只存在于 overlay、文件尾部、资源区、压缩数据里的载荷**不在视野内** |
| 特征来源 | 由 `features.json` 的名字驱动，全部来自字节统计 / PE 结构 / 导入导出名哈希 | 不含语义分析、不含控制流、不含字符串上下文 |

因此下列情形**不能**指望这一层给出判断：

- 恶意载荷完全位于 overlay / 尾部 / 资源段；
- 需要解包后才能看到的第二阶段载荷（这属于解包层与内存快照层的职责）；
- 语义型攻击（合法 API 的异常组合、逻辑滥用）。

**架构上这一点是被正确处理的**：AI 输出是 `evidence`，不是 `authority`。它必须与启发式、行为、序列等信号一起进 `ProtectionFusion` 才能产生 `Malicious`。单靠 AI 一层永远不会直接定罪——见 [第 5.9 节](05-检测层详解.md#59-融合层fusionrs)的裁决顺序。

**12 维基向量（①）本身的取舍**：

- 低维让对抗样本的微扰空间变小，也让模型可被人工审计；
- 代价是表达能力有限，这也是为什么 ② 允许通过 `features.json` 把宽度扩到 1283（`dllhash_N` / `apihash_N` 提供 1280 个导入/导出名桶）——即**用"名字哈希桶"补回一部分语义信息**，同时保持推理仍然只是简单的整数/浮点运算。

## 5.5 三层特征契约（容易混淆，必须分清）

仓库里同时存在**三种**不同的特征表示，名称相近但用途、维度、来源完全不同。本节把它们逐一钉死。

### 概览

| # | 名称 | 维度 | 定义位置 | 谁在用 |
|---|------|------|----------|--------|
| ① | **Canonical base vector**（规范基向量） | **12** | `layers/ai.rs::extract_features` | 引擎内部的特征基元，始终存在 |
| ② | **Model input contract**（模型输入契约） | **由 `features.json` 长度决定**，随包模型为 **1283** | `features.json`（运行时从模型目录加载） | 实际喂给 ONNX 模型的张量 |
| ③ | **Offline feature space**（离线特征空间） | **2272** = `STATIC_TOTAL 1892` + `DYNAMIC_TOTAL 380` | `features/mod.rs` | 离线数据集与训练侧，**不参与运行时推理** |

### ① Canonical base vector（12 维）

```rust
pub fn extract_features(blob: &[u8]) -> [f32; 12];
fn extract_features_with_size(blob: &[u8], file_size: u64) -> [f32; 12];
```

12 个规范名（顺序固定，见 `DEFAULT_NAMES`）：

| # | 名称 | # | 名称 |
|---|------|---|------|
| 0 | `coverage` | 6 | `printable_ratio` |
| 1 | `section_count` | 7 | `null_ratio` |
| 2 | `import_count` | 8 | `distinct_byte_ratio` |
| 3 | `tls_present` | 9 | `mean_byte` |
| 4 | `timestamp` | 10 | `entropy_norm` |
| 5 | `section_entropy` | 11 | `large_flag` |

图像采样固定为**文件头 64 KiB**。这是引擎里唯一"始终存在"的特征向量。

### ② Model input contract（随包 1283 维）——**与 ① 的关系在这里**

引擎**不是**直接把 12 维喂给模型。`extract_model_features` 会按 `features.json` 里给出的**名字列表**把 12 维基向量**展开**成模型期望的宽度：

```rust
// 无 features.json 时：直接用 12 维
let Some(names) = self.feature_map.read()... else { return base.to_vec(); };
// 有 features.json 时：按名字逐个解析
let features = extract_named_features(blob, file_size, &names, base);
```

`extract_named_features` 的名字解析规则（**这就是 ① → ② 的映射机制**）：

| 名字形态 | 取值 |
|----------|------|
| 命中 12 个规范名（含别名 `timestamp_anomaly`） | `base[index]` |
| `entropy` | `base[10]`（即 `entropy_norm`） |
| `filesize` | 对数归一化后的文件大小 |
| `stringcount` | 可打印字符串数 / 64，上限 1.0 |
| `entropy_raw` / `byte_entropy` | 原始香农熵 |
| `head_entropy` / `tail_entropy`（别名 `pe_overlay_entropy`） | 头部 / 尾部窗口熵 |
| `max_section_entropy` / `mean_section_entropy` / `first_section_entropy` | 节区熵统计 |
| `bytehist_N` / `byte_N` | 字节直方图第 N 桶 |
| `dllhash_N` | DLL 名哈希是否落在第 N 桶 → **0.0 / 1.0** |
| `apihash_N` | API 名哈希是否落在第 N 桶 → **0.0 / 1.0** |
| `derived_*`（如 `derived_hash_density`） | 若干派生乘积 |
| **其它任何未知名字** | **0.0** |

随包的 `features.json` 恰好 **1283** 条，构成为：

```
filesize, stringcount, entropy            →    3
dllhash_0 … dllhash_255                   →  256
apihash_0 … apihash_1023                  → 1024
                                        ─────────
                                            1283
```

**已实测确认**：随包模型 `everbloom_feature_cnn.onnx` 的输入张量形状是 `[1, 1, 1283]`，两个输出 `logits [1,2]` 与 `probs [1,2]`；`model_contract.json` 指定 `output_index: 1`（`probs`）、`malicious_index: 1`。

> **所以"12 维"与"1283 维"并不矛盾**：12 是引擎能自己算出来的**基元**，1283 是**当前这个模型要求输入的名字布局**。换一个模型（连同它自己的 `features.json`），输入宽度就跟着变——`apply_feature_mapping` / `extract_named_features` 是通用的，不需要改代码。这也解释了为什么 `AiModel` 里有 `input_shape_candidates()`：模型输入宽度是运行期才知道的。

### ③ Offline feature space（2272 维）——**与 ② 无关**

```rust
// engine/src/features/mod.rs
STATIC_TOTAL = 1892
  ├─ PE_STRUCTURE       50
  ├─ PE_IAT_API        512
  ├─ STRING_FEATURES  1024
  ├─ BYTE_HISTOGRAM    256
  └─ RESOURCE_METADATA  50

DYNAMIC_TOTAL = 380
  ├─ API_CLUSTERS      200
  ├─ FILE_OPERATIONS    50
  ├─ NETWORK_OPERATIONS 50
  ├─ REGISTRY_PERSIST   50
  └─ PROCESS_THREAD     30
```

它由 `FeatureVector { static_features, dynamic_features }` 承载，面向**离线数据集与训练**（EMBER 风格的高维表示）。

> **⚠️ 关键事实：2272 与 1283 之间没有转换关系，也不存在"2272 → 1283 投影"这一步。**
> 两者是**独立的两套体系**：② 是"模型输入要哪些名字"，③ 是"离线数据集怎么表示一个样本"。代码里没有任何从 `FeatureVector` 生成 `features.json` 的路径，也没有把 2272 维裁剪到 1283 维的逻辑。
> 并且 `features/mod.rs` 的 `FeatureVector` 目前**只被 `lib.rs` 重新导出，没有任何业务代码消费它**（`libeverbloom_rs` 里的 `FeatureVector` 是另一个独立结构，在 `rust_feature_extractor.rs` 中定义）。
> 因此 ③ 应当被理解为**离线/训练侧的表示契约**，而不是运行时的第三条输入通道。

### 一句话总结

| 问题 | 答案 |
|------|------|
| 引擎能自己算出多少维特征？ | **12** |
| 随包模型吃多少维？ | **1283**（由 `features.json` 决定，名字驱动展开） |
| 12 → 1283 怎么变的？ | `extract_named_features` 按名字解析；规范名取 `base[i]`，`dllhash_N`/`apihash_N` 取桶命中 0/1，未知名字填 0.0 |
| 1892 + 380 = 2272 是什么？ | 另一套**离线**表示，与模型输入无关，无自动转换 |
| 换模型要改代码吗？ | 不要。换 `.onnx` + 配套 `features.json` 即可 |

`score_events_by_process` 按进程分组打分，并对特定组合给额外加成：

### 能力考量

- **"写文件或网络回调不能单独制造高分"**（源码注释明示）。单一类型的重复事件不会累加出高分——必须有跨类型的事件组合。这直接对抗"用大量无害操作刷分"的对抗手法；
- `score_events_by_process` 的存在使多进程场景（如浏览器多进程、脚本宿主链）能正确归因，而不是把不同进程的行为混在一起。

## 5.7 序列匹配层（`sequence.rs`）

### 有序签名

```rust
pub struct SequenceSignature { ..., pub tolerant: bool }
pub struct SequenceMatch { ..., pub tolerant: bool }

pub fn match_sequence(&self, events: &[BehaviorEventKind]) -> Vec<SequenceMatch>;
```

内置签名约 15 条，其中 **9 条严格**（`tolerant: false`）、**6 条宽容**（`tolerant: true`）。

### 严格 vs 宽容

| 类型 | 匹配规则 | 在融合中的地位 |
|------|----------|----------------|
| **严格** | 事件必须按序连续出现 | **权威**——直接产生 `Malicious`（`fusion:kaspersky_sequence:`） |
| **宽容** | 事件按序出现在有界窗口内，允许中间插入噪声 | **证据**——默认 `Suspicious`，需独立信号佐证才升级 |

### 宽容签名的升级条件（融合器逻辑）

```rust
let escalate = score >= self.response_level.threshold()
    || (matches.len() >= 2 && independent_action)
    || (matches.len() >= 2 && independent_kinds >= 3)
    || (matches.len() >= 2 && score >= 0.5);
```

其中 `independent_action` 要求沙箱标志里出现 `files_changed` / `network_activity` / `registry_activity` / `api_activity` / `unpacked` 之一。

### 能力考量

- 宽容签名"容忍交错的噪声"是**设计目标**（真实恶意软件不会干净地按序调用 API），但这使它不能单独定罪——因此被降级为相关性证据；
- 升级条件要求**独立**信号：多个宽容签名同时命中、事件种类够多、或行为分达到阈值。这防止"一条宽容签名 + 一点噪声"就误报。

## 5.8 静态沙箱预测层（`static_sandbox.rs`，955 行）

不需要真正运行样本，**纯从静态字节**（PE 导入表、字符串、结构特征）推断沙箱中"会表现出哪些能力"。

### 10 个能力族与权重

| 能力族 | 权重 | ATT&CK |
|--------|------|--------|
| `recovery_inhibition` | **0.60** | T1490 |
| `impact` | **0.45** | T1485, T1486 |
| `injection` | **0.30** | T1055 |
| `persistence` | **0.25** | T1547, T1053 |
| `credential_access` | **0.25** | T1555, T1003 |
| `network` | **0.20** | T1071, T1105 |
| `execution` | **0.20** | T1059, T1106 |
| `evasion` | **0.15** | T1497, T1622, T1562 |
| `discovery` | **0.12** | T1057, T1518 |
| `recon` | **0.10** | T1082, T1016 |

### `recovery_inhibition` 权重最高的理由

源码注释解释：它是"最可靠的单一静态信号"——破坏备份恢复能力的 API 组合（`vssadmin delete shadows`、`wbadmin delete catalog`、`bcdedit /set recoveryenabled no`）在良性软件中几乎不出现。它被单独立为一个族，而不是当作 `impact` 的子情形。

### 打分公式

```rust
calibrated() = residual_product + (n - 1) * 0.025
```

- `residual_product`：各命中族权重之积的残差（概率型组合）；
- `(n - 1) * 0.025`：命中族数量的**佐证加成**；
- 结果截断在 0.95。

即：单个族命中时接近该族权重；多个族同时命中时，加成累积但仍受 0.95 上限约束——**不轻易给出 1.0 的确定性**。

### 链式判定

```rust
pub fn is_high_confidence_chain(&self) -> bool {
    let injection = has("injection:");
    let persistence = has("persistence:");
    let channel = has("network:") || has("credential_access:");
    injection && persistence && channel && self.score >= 0.55
}
```

"注入 + 持久化 + 外传通道"三要素齐备且分数达标 → 高置信链。

另有 `is_high_confidence_chain` 的变体，针对 `recovery_inhibition` + (`impact` | `credential_access`) 的组合——勒索软件典型特征。

### 特殊规则

`discovery` 族在**枚举安全产品**时权重 ×2——这是"攻击者先侦察有哪些防护"的强指示。

### 能力考量

- `STATIC_SANDBOX_POLICY_VERSION = 2`（参与缓存键）；
- 输出 `triggered capabilities` 形如 `injection:write_process_memory`、`network:...`，**保留具体命中的 API 名**，使判定可解释、可复核；
- `attack_techniques_for()` 的 `match` 表与 10 个族**一一对应**，保证每个族都有 ATT&CK 映射。

> 本节说明融合算法和分支设计；生产装配、A/B 对照及真实语料/动态分支边界见 [第 12.6.1 节](12-检测质量与验证.md#1261-production-fusion-曾缺少装配现已接入并完成首轮对照)。
>
> `eval_harness` 复用 Scanner 类型与检测实现，但自行装配评测 profile；默认 Fusion Normal，`--no-fusion` 用于受控消融。它不是直接调用 `main.rs::build_scanner()`，额外数据库和生产环境服务可能不同。对照数据见 [第 12.4.2 节](12-检测质量与验证.md#1242-production-fusion-接线前后与-harness-消融对照-已实测)。

### 裁决顺序（`evaluate` 的实际执行顺序）

**① 驱动阻断 —— 最高优先级**

```rust
if hips_alerts.iter().find(|a| a.to_ascii_lowercase().contains("driver blocked")) {
    return Malicious { reason: "fusion:driver:stage=intervene:...", rollback: true };
}
```

驱动阻断是**执行结果**而非观察，因此无条件权威——即使在 Relaxed 模式下也直接判恶意。注意只接受 `"driver blocked"` 这个**显式标记**，普通 HIPS 告警走后续的多步证据路径。

**② 严格序列命中 —— 权威**

```rust
if let Some(matches) = &input.sequence_matches {
    if !matches.is_empty() {
        return Malicious { reason: "fusion:kaspersky_sequence:stage=intervene:...", rollback: true };
    }
}
```

**③ 宽容序列命中 —— 条件升级**

按 5.7 节的四条升级条件判定 `Intervene` / `Correlate`。

**④ 行为分达阈值**

```rust
if score_value >= self.response_level.threshold() {
    let corroborated = independent_kinds >= 2 || score.matched_indicators.len() >= 2;
    let stage = if self.response_level == Aggressive || score_value >= 0.85 || corroborated {
        Intervene
    } else {
        Correlate
    };
    // reason: "fusion:atc:{score}:stage={stage}:evidence={kinds}:{indicators}"
}
```

**⑤ 静态高置信 —— 防平均化**

```rust
let strongest = heuristic.max(ai);
let weakest  = heuristic.min(ai);
let high_confidence = match response_level {
    Aggressive => 0.82,
    Normal     => 0.90,
    Relaxed    => 0.96,
};
if strongest >= high_confidence {
    let stage = if strongest >= 0.96 { Intervene } else { Correlate };
    // reason: "fusion:static_high:stage={stage}:heuristic=..:ai=..:strongest=.."
}
```

源码注释直白说明了动机：

> *"Do not average a high-confidence independent signal down into a clean verdict. A 0.90 heuristic finding combined with a weak AI score is still a strong malicious indicator; the old weighted mean could turn that into 0.42 and silently discard the evidence."*

**⑥ 静态一致 —— 加权 + 佐证**

```rust
let corroborated = weakest >= self.response_level.threshold() * 0.70;
let combined = heuristic * 0.4 + ai * 0.6;
if corroborated && strongest >= self.response_level.threshold() {
    let stage = if strongest >= 0.85 && combined >= 0.75 { Intervene } else { Correlate };
    // reason: "fusion:static:stage={stage}:heuristic=..:ai=..:combined=..:corroboration=.."
}
```

权重 **启发式 0.4 / AI 0.6** —— AI 权重更高，因为它是学习型信号；启发式权重较低但更可解释。

**⑦ 单源高置信闸门（`high_confidence_override`）**

前面六条都要求佐证（或本身是执行结果）。这一条是**唯一**允许单个证据源单独定案的规则：

```rust
pub const HIGH_CONFIDENCE_HEURISTIC_OVERRIDE: f32 = 0.80;

// heuristic >= 0.80  →  Malicious
// ai >= input.ai_threshold（请求级，经 FusionInput 传入）  →  Malicious
// reason: "fusion:high_confidence_override:stage=intervene:source=<heuristic|ai>:score=..:threshold=.."
```

三条约束：

- **排在佐证规则之后**，所以驱动阻断、严格序列、ATC、双引擎一致都保留自己的 `reason`，不会被闸门顶掉；
- **`rollback: false`**：分数是证据，不是执行结果，没有可回滚的已发生动作；
- **AI 那一臂用请求级阈值**，不是硬编码常量，因此 `--ai-threshold` 仍然有效。

它排在动态 `sandbox_flags` / `hips` 之前，但这不是优先级声明：Scanner 只在结论未定时才运行沙箱阶段，触发闸门的样本根本不会走到动态分析，两种顺序在可观测行为上等价。

### `reason` 前缀一览

| 前缀 | 含义 |
|------|------|
| `fusion:driver:stage=intervene:` | 驱动阻断 |
| `fusion:kaspersky_sequence:stage=intervene:` | 严格序列命中 |
| `fusion:kaspersky_sequence_tolerant:stage=..:events=..:score=..:` | 宽容序列命中 |
| `fusion:atc:..:stage=..:evidence=..:` | 行为分达标 |
| `fusion:static_high:stage=..:heuristic=..:ai=..:strongest=..` | 静态高置信 |
| `fusion:static:stage=..:heuristic=..:ai=..:combined=..:corroboration=..` | 静态一致 |
| `fusion:high_confidence_override:stage=intervene:source=..:score=..:threshold=..` | 单源高置信闸门 |

其它在 `scanner.rs` 中出现的 reason 前缀：`yara:`、`clamav:`、`behavior_sequence:`、`sandbox_behavior`、`threat_intel:`、`fusion:anti_sandbox:`、`fusion:sandbox_flags:`、`fusion:cookie_theft_suspected:`。

### 能力考量

- **`FusionDecision` 只有 `Clean` / `Malicious` / `Suspicious` 三态**，阶段信息编码在 reason 里。这使调用方（HIPS、GUI、报告）不需要理解阶段机；
- **`rollback: true`** 标记需要执行回滚——只有达到 `Intervene` 的裁决才带这个标记；
- **顺序即优先级**。先判权威来源，再判证据组合；一旦命中即返回，不做后续计算。这既省算力，也避免了"证据互相抵消"这类难以解释的行为。

### 能力考量

- **连接超时极短（750 ms）**。ClamAV 是可选增强，不能让它的不可用拖慢主扫描路径；
- **重试冷却 300 s**。ClamAV 守护进程不可用时，5 分钟内不再尝试——避免每个文件都白等 750 ms；
- **并发上限 2**。clamd 的 `INSTREAM` 是重操作，限制并发避免把守护进程打满；
- **响应上限 16 KiB**。clamd 的正常响应很短，超过这个大小说明响应异常（或对端不是 clamd），直接拒绝解析；
- **流式传输分块 1 MiB**，避免把整个样本读进内存。

## 5.12 Cookie 防护层（`cookie_guard.rs`，437 行）

### 定位

这一层的目标不是"检测恶意软件"，而是**在凭据被窃取前阻止访问**。它是隐私保护型的检测层。

### 接口

```rust
pub const SILVERFOX_INDICATORS: &[&str] = &[...];   // 凭据窃取工具特征
const MAX_PROCESS_IMAGE_BYTES: u64 = 8 * 1024 * 1024;

pub struct CookieGuardScore { ... }
impl CookieGuardScore {
    pub fn high_confidence(&self) -> bool;
    pub fn medium_confidence(&self) -> bool;
}

pub fn is_browser_cookie_store(path: &Path) -> bool;
pub fn is_cookie_guard_candidate_file(path: &Path) -> bool;
pub fn is_browser_process_name(path_or_name: &str) -> bool;
pub fn is_known_cookie_tool_name(path_or_name: &str) -> bool;
pub fn analyze_bytes(path: &Path, bytes: &[u8]) -> CookieGuardScore;
pub fn analyze_process_image(path: &Path) -> CookieGuardScore;
```

### 检测逻辑

识别三类对象：

1. **浏览器 Cookie 存储文件**（`Cookies` SQLite 数据库等）；
2. **浏览器进程**（按进程名）；
3. **已知的 Cookie 窃取工具**（`SILVERFOX_INDICATORS` 等特征）。

当"非浏览器进程读取浏览器 Cookie 库"这一组合出现时，判定为凭据窃取可疑。

### 在流水线中的特殊地位

Cookie 防护候选文件**跳过缓存**（`if !cookie_guard_candidate`）——因为这类判定依赖进程上下文，而缓存键只含文件指纹，无法表达"哪个进程在读"。跳过缓存保证每次都重新评估。

融合器中有专门的 reason 前缀 `fusion:cookie_theft_suspected:`。

### 内核侧配合

驱动侧也有对应实现（`kernel_components.cpp` 的 `is_browser_cookie_store_path` / `is_cookie_requestor_exempt` / `is_cookie_store_read_open`），在内核层就拦截"非浏览器进程以读方式打开 Cookie 库"。

`docs/cookie_protection.md` 描述完整策略。

### 能力考量

- **豁免清单是必需的**：浏览器自身的子进程（渲染器、GPU 进程）也会读 Cookie 库，`is_cookie_requestor_exempt()` 负责识别它们；
- **进程镜像大小上限 8 MiB**：分析进程镜像时只读前 8 MiB，避免大进程拖慢；
- **误报代价高**：这一层需要"进程不是浏览器 + 目标是 Cookie 库"两个条件同时成立，单看任一条都不成立。

## 5.13 内存快照 / 解包层（`memory_snapshot.rs`，788 行）

### 目的

沙箱执行期间，样本常常会把自己的真实载荷在内存中解出来再执行。内存快照层在**运行时**采集这些内存区域，弥补"静态看是加壳文件"的盲区。

### 接口

```rust
pub struct SandboxUnpackingReport { ... }
pub struct MemoryImageCandidate { ... }
pub struct MemorySnapshotCollector;

impl SandboxUnpackingReport {
    pub fn unavailable(reason: impl Into<String>) -> Self;
    pub fn no_candidate(reason: impl Into<String>) -> Self;
}

impl MemorySnapshotCollector {
    pub fn unavailable() -> SandboxUnpackingReport;
    pub fn start(process: HANDLE, pid: u32, trigger: Arc<AtomicBool>, timeout_ms: u64) -> Self;
    pub fn finish(mut self) -> SandboxUnpackingReport;
    pub fn trigger_now(&self);
}
```

### 触发式采集

`MemorySnapshotCollector` 是一个**可被外部触发**的采集器：沙箱观察到可疑行为时通过 `trigger_now()` 触发，采集器在超时内完成采集并 `finish()` 返回报告。

报告会标注 `unavailable` 或 `no_candidate` 的原因（`reason` 字符串），使"没有采到"与"采到但没找到候选"可区分。

### 能力考量

- **只在沙箱内工作**。内存采集需要 `HANDLE` 与进程控制权，因此只对沙箱内运行的样本可用；
- **超时保护**。`timeout_ms` 约束采集时长，避免大内存进程拖死沙箱；
- **采集失败必须显式报告**。`unavailable(reason)` / `no_candidate(reason)` 强制调用方处理"没采到"的情况，而不是把它当作"没发现"。

## 5.16 回滚层（`rollback.rs`）

```rust
pub struct RollbackExecutor { ... }
impl RollbackExecutor {
    pub fn new(dry_run: bool, allow_restore: bool) -> Self;
    pub fn execute(&self, record: &RollbackRecord) -> Vec<Result<String, String>>;
}

pub struct RollbackRecord { ... }
pub struct RollbackPlanner;
impl RollbackPlanner {
    pub fn from_sandbox_report(report: &SandboxReport) -> RollbackRecord;
}
```

### 计划与执行分离

`RollbackPlanner` 从沙箱报告生成 `RollbackRecord`（"需要撤销哪些更改"），`RollbackExecutor` 执行它。分离的好处：

- **可在沙箱里演练**（`dry_run: true`）而不产生副作用；
- **可审计**：计划是数据，执行是动作，两者都能记录；
- **可限制**：`allow_restore` 控制是否允许从备份恢复（更激进的动作）。

### 执行结果

`execute` 返回 `Vec<Result<String, String>>`——**逐动作的成功/失败**，不是一个总布尔值。这样"3 个动作里 2 个成功"是可见的。

`scanner.rs` 把结果映射为 `rollback_actions` 字符串列表，失败项前缀为 `rollback_error:`。

### 能力考量

- 只有融合裁决达到 `Intervene`（`rollback: true`）才执行回滚；
- `docs/active_defense_state_rollback.md` 描述状态回滚的完整语义。

## 5.17 合成语料层（`synthetic.rs`，989 行）

**训练专用**，不参与扫描。

```rust
pub const SYNTHETIC_MARKER: &[u8] = b"EVERBLOOM-SYNTHETIC-CORPUS-NOT-MALWARE";
pub const FAMILY_NAMES: [&str; 7] = [...];

pub struct Rng { ... }          // 确定性随机（可复现）
pub struct PeTemplate { ... }
pub fn family_template(family: &str) -> Option<PeTemplate>;
pub fn build_pe(template: &PeTemplate, seed: u64) -> Vec<u8>;
pub fn generate_corpus(...) -> ...;
pub fn validate_output_root(root: &Path) -> Result<PathBuf, String>;
```

### 设计要点

- **确定性 RNG**：给定 seed，生成的语料完全可复现。这使训练实验可重复；
- **7 个恶意家族模板**：每个模板定义节区（`SectionSpec`）与导入（`ImportSpec`）；
- **内嵌标记 `EVERBLOOM-SYNTHETIC-CORPUS-NOT-MALWARE`**：合成的 PE **不是真实恶意软件**，标记保证：
  1. 任何真实杀毒软件不会把它当威胁（也提醒人工分析者）；
  2. `validate_output_root` 可校验输出目录，避免语料被误当作真实样本分发。

### 能力考量

合成语料的价值是**在没有真实样本的情况下做实验与回归**。它的局限同样明确：合成数据训练出的模型在真实样本上的泛化能力有限，因此 `tools/` 里同时提供了真实数据集路径（EMBER、MalwareBazaar）。

## 5.19 检测层之间的协作关系

```
                    ┌──────────── 权威路径（命中即恶意）────────────┐
                    │  hash(精确) · yara · clamav · threat_intel    │
                    │  sequence(严格) · driver_blocked              │
                    └───────────────────┬───────────────────────────┘
                                        │
  静态证据 ──┬─ heuristic ──────┐      │
             ├─ ai ─────────────┤      │
             ├─ static_sandbox ─┤      ▼
             └─ unpacking ──────┴──► ProtectionFusion ──► FusionDecision
                                        ▲                 Clean / Suspicious / Malicious
  动态证据 ──┬─ behavior ──────────────┘                 (+ rollback 标记)
             ├─ sequence(宽容) ───────┘
             ├─ process_state ────────┘
             ├─ memory_snapshot ──────┘
             └─ sandbox ──────────────┘

  特殊：cookie_guard（隐私保护路径，可独立产生 cookie_theft_suspected）
  基础设施：cache（结果复用）、rollback（动作执行）
```

**一句话总结融合哲学**：权威来源直接定案，证据来源加权但**绝不互相稀释**——高置信的单一信号不会被低置信的另一个信号"平均掉"。
