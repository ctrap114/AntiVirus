# 11. 能力考量与安全边界

前 10 章描述了"是什么、怎么做"。本章集中说明**为什么这么做**——每一项关键设计背后的约束、取舍与安全边界。

阅读方式：这不是缺陷清单，而是**设计前提清单**。每一条都是"在这个约束下，我们选择了这个方案"，理解它们才能正确评估产品的实际能力范围。

---

## 11.1 权限与信任边界

### 三条边界

```
┌────────────────────────────────────────────────────────────┐
│  Ring 3 · 用户态                                            │
│  ┌──────────────────┐  ┌──────────────────┐                │
│  │ everbloom_gui    │  │ everbloom_engine │                │
│  │  （无特权要求）   │  │ （决策权持有者）  │                │
│  └──────────────────┘  └──────────────────┘                │
│         ▲                      ▲                           │
│         │ NDJSON               │ DeviceIoControl           │
├─────────┼──────────────────────┼───────────────────────────┤
│  Ring 0 · 内核态              │                            │
│  ┌──────────────────────────────┴──────────────┐           │
│  │ everbloom_driver.sys                        │           │
│  │  （只执行策略，不做判断）                     │           │
│  └─────────────────────────────────────────────┘           │
└────────────────────────────────────────────────────────────┘
```

### 决策权归属

**用户态拥有最终裁决权，内核是低成本的前置防线。**

这条边界在 `docs/main_protection_driver_contract.md` 中被定义为契约。具体含义：

| 情况 | 处理 |
|------|------|
| 内核阻断了一个动作 | **权威否定**——用户态不推翻 |
| 内核没有阻断 | **不构成任何肯定**——用户态独立判断 |
| 内核不可用 | **正常降级**——用户态完整可用 |

内核**从不**宣称一个文件是恶意的。它只说"这个动作被拦了"。因此"内核没报"不能作为"安全"的依据。

### 为什么这样分

| 理由 | 说明 |
|------|------|
| **可审计性** | 内核代码 2,847 行，可人工审完；若把检测逻辑放内核，代码量会膨胀一个数量级 |
| **崩溃面** | 内核 bug = BSOD。检测逻辑（尤其模型推理、字符串匹配）是 bug 高发区，放用户态最多让引擎崩溃 |
| **可更新性** | 规则、模型、情报可以热更新；内核驱动更新需要重新签名、重启 |
| **能力受限** | 内核不能有浮点、不能动态分配大内存、不能发网络请求 |

### GUI 无特权要求

`everbloom_gui.exe` 不要求管理员权限。它只负责界面与子进程管理，所有需要特权的操作都通过引擎完成。这是"最小权限"原则的体现——用户日常使用的界面不应该运行在高权限下。

## 11.2 内核侧的硬约束

内核驱动的能力边界由**操作系统本身**决定，不是实现选择。

| 约束 | 原因 | 应对方案 |
|------|------|----------|
| **不能使用浮点** | `DISPATCH_LEVEL` 及以上不允许 FPU 操作（上下文切换代价、可能损坏浮点状态） | 纯整数 Q31 定点推理核心（`everbloom_kernel_matrix.h`） |
| **不能动态分配大内存** | 分页池/非分页池压力、IRQL 限制 | 定长结构 + `const` 静态数据 + 栈缓冲 |
| **不能做文件内容解析** | I/O 代价高、可能在 DISPATCH_LEVEL 被调用 | 内核只看路径与命令行（12 个特征全部由此派生） |
| **不能发网络请求** | 无网络栈、不可阻塞 | 情报查询全在用户态 |
| **不能调用多数 Win32 API** | 那是用户态 API | 只用 `ntddk.h` / `fltKernel.h` / `wdmsec.h` 提供的原语 |
| **代码量必须小** | 可审计性、崩溃面 | 2,847 行真内核代码 |
| **源码必须纯 ASCII** | 工具链按 codepage 936 编译，U+2014 等字符触发 `C4819` | 用 `-` 而非排版破折号 |
| **altitude 必须唯一且组内** | 全局命名空间 + Filter Manager 组语义 | minifilter 329671 / 句柄 329670，递减重试硬下界 320000 |

### 关键取舍：内核模型只作建议

内核模型（12 个整数特征 → 打分）**从不否决**进程创建。原因：

- 特征只有路径与命令行，信息量有限；
- 误报代价是阻断合法程序启动；
- 真正的裁决权在用户态融合器。

因此内核模型只在评分越过阈值时**记录一个事件**（`EVERBLOOM_EVENT_KIND_MODEL_SCORE`），作为参考信息。引擎侧还刻意**不**把这个分映射成行为事件——因为"模型只读映像路径与命令行，用户态关联本来就有，回灌等于把本流水线自己的输入伪装成独立证据"。

## 11.3 沙箱的安全边界

沙箱是产品中**风险最高**的组件——它执行不受信任的代码。因此它的设计最保守。

### 优先级链（失败即关闭）

```
① AppContainer + Job Object（本地）
      ↓ 不可用
② Windows Sandbox VM
      ↓ 不可用
③ 失败并报告 sandbox_unavailable
```

**没有"直接在宿主机执行"的降级路径。** 这是 fail-closed 设计的核心。

### 本地后端（AppContainer + Job Object）的隔离策略

| 控制项 | 值 |
|--------|-----|
| AppContainer 网络能力 | **无** |
| 受限令牌 | 所有可移除特权**禁用** |
| 进程创建 | **挂起**，直到被分配到 Job Object 才恢复 |
| 子进程树 | Job Object 关闭时**整树终止** |
| 内存上限 | 每进程 1 GiB / 每 Job 2 GiB |
| 活跃进程上限 | 32 |
| 桌面 / 剪贴板 / 句柄 / 窗口系统 | 全部限制 |
| 句柄继承 | **无继承** |
| 可执行目标类型 | 仅 `.exe` / `.com` / `.scr` |

### Windows Sandbox 后端（VM）的配置

| 控制项 | 值 |
|--------|-----|
| 网络 | **禁用** |
| 虚拟 GPU | 禁用 |
| 剪贴板 / 音频 / 视频 / 打印机重定向 | 全部禁用 |
| Protected Client | 启用 |
| 宿主输入目录 | **1 个，只读映射** |
| 可写宿主目录 | **无** |
| 样本大小上限 | 512 MiB |
| 沙箱内存上限 | 4096 MiB |
| 会话超时 | 最短 30 秒 / 最长 10 分钟 |
| 并发会话 | **1 个** |

**自动执行的目标类型**（两种后端合并）：`.exe` / `.com` / `.scr` / `.bat` / `.cmd` / `.ps1` / `.msi`。

### 样本处理

- 样本先复制到**专用临时目录**；
- **原始文件位置从不映射进客户机**——这防止样本通过路径推断出宿主环境布局，也防止它写回原目录。

### 启动前的校验链

后端在启动前依次校验：

1. 规范化后的样本路径；
2. 常规文件类型（非目录、非符号链接）；
3. 大小上限；
4. 支持的扩展名；
5. 暂存副本大小；
6. 受信任的安全对象；
7. （回退路径）生成的 `.wsb` 策略文件。

**本地后端以挂起状态创建进程，只有在分配到 Job Object 之后才恢复执行**——这消除了"进程在隔离建立之前就跑了"的时间窗。

### 结果可信性

```rust
// 只有两者都为真，队列报告才被认为可信
isolation_verified && cleanup_verified
```

| 情况 | 处理 |
|------|------|
| 超时 | Job Object 终止整棵进程树，并**必须**确认终止信号 |
| 清理失败 | 报告为**不可信沙箱结果**，而不是当作"干净执行" |
| 隔离失败 | 视为**可疑** |

### 诚实的局限声明

`docs/SANDBOX_SECURITY.md` 明确写出：

> *`windows_appcontainer_job` is host-level restricted execution, not a VM. It reduces privileges and storage/network access through Windows security boundaries, but it does not provide the same kernel boundary as Windows Sandbox.*

> *Neither backend maps a writable guest-to-host report directory. The local backend reports session completion and timeout, but it does not yet export rich file, registry, or network telemetry.*

> *Static hash, YARA, heuristic, and AI layers should remain the primary detection path.*

即：

- AppContainer 是**宿主级受限执行**，不是虚拟机——它降低权限与访问，但不提供 VM 的内核边界；
- 两个后端都**不**映射可写的客户机→宿主报告目录，因此**丰富的客户机遥测（文件/注册表/网络）目前不导出**；
- 因此**静态层（哈希 / YARA / 启发式 / AI）应作为主检测路径**，沙箱是补充证据。

> 附带效应：因为不映射可写目录，`api_calls` 字段里装的是**隔离控制元数据**而非真实样本行为。扫描器会**过滤掉这些控制记录**，避免把"沙箱自身的控制操作"算作"样本行为"。

### 平台要求

Windows Sandbox 需要：

- Windows **Pro / Enterprise / Education** 版本（家庭版不支持）；
- 硬件虚拟化支持；
- 可选的 `Containers-DisposableClientVM` Windows 功能。

不满足时，设置页的"启用隔离沙箱分析"选项不可用——GUI 会反映这一事实，而不是提供一个点了没反应的开关。

## 11.4 隐私与数据边界

### 不存原始样本

数据集工具（`tools/extract_features.py`）的策略：

> *提取时高维全面（~2671 维），存储时极致压缩（CSR 稀疏 + 特征哈希降维），**坚决不存原始样本**（只存特征向量 + 标签 + 元数据）。*

这使数据集可以安全存储、传输、共享——它不含任何可执行代码。

### 本地优先

| 能力 | 默认 | 数据流向 |
|------|------|----------|
| YARA | ✅ 开启 | 纯本地 |
| 启发式 | ✅ 开启 | 纯本地 |
| AI 推理 | ❌ 关闭 | 纯本地（`tract-onnx` 本地推理，无云端调用） |
| 沙箱 | ❌ 关闭 | 本地隔离执行 |
| ClamAV | ❌ 关闭 | 本地守护进程（`127.0.0.1:3310`） |
| 云查杀 | ❌ 关闭（`cloud_placeholder_enabled{false}`） | — |

**默认配置下，产品不做任何网络请求**（威胁情报更新是显式的工具操作，不是后台行为）。

### AI 推理不出网

`tract-onnx` 是纯 Rust 本地推理——模型在进程内执行，**没有任何网络调用**。这与"云 AI 检测"有本质区别。

### 进程上下文的使用

内核允许读取进程/镜像回调上下文作为特征来源（这是用户确认过的架构决策）。用途严格限于：

- 内核模型的 12 个特征（映像路径 + 命令行）；
- 进程创建/终止事件；
- Cookie 防护的进程身份判断。

**不采集**：进程内存内容（除沙箱内取证）、用户输入、屏幕内容、剪贴板内容（沙箱内除外，且沙箱默认禁用剪贴板重定向）。

### Cookie 防护的隐私取向

`cookie_guard.rs` 的设计目标是**阻止凭据被窃取**，而不是"读取用户的 Cookie"。它的判定依据是"哪个进程在读"，而非"读到了什么内容"。`analyze_process_image` 只读进程镜像的前 8 MiB（`MAX_PROCESS_IMAGE_BYTES`），不读取 Cookie 数据库内容。

### 隔离区加密

- `EVERBLOOM_ENCRYPT_QUARANTINE` 默认**开启**；
- 密钥来自 `EVERBLOOM_QUARANTINE_ENCRYPTION_KEY` 或 `quarantine/store.key`；
- 行为元数据也可加密（`EVERBLOOM_ENCRYPT_BEHAVIOR`）。

隔离的文件是恶意样本，加密存储防止被其他程序（或用户误操作）当作正常文件执行。

### 缓存的性能价值

`ScanContext` 把四个版本号（`rules_version` / `yara_version` / `ai_model_version` / `sandbox_policy_version`）纳入缓存键，配合**证据/决策两级世代**：

- 规则更新 → 只重跑融合，不重读磁盘、不重新解析 PE；
- 这是"更新规则几乎零成本"的实现基础。

## 11.6 对抗鲁棒性

### 融合层：绝不平均化

这是产品最重要的抗对抗设计之一。源码注释直白说明：

> *"Do not average a high-confidence independent signal down into a clean verdict. A 0.90 heuristic finding combined with a weak AI score is still a strong malicious indicator; the old weighted mean could turn that into 0.42 and silently discard the evidence."*

**攻击面**：如果融合器用简单加权平均，攻击者只要让一个检测层给出极低分，就能把另一个层的高分"拉下来"。

**应对**：

```
strongest = max(heuristic, ai)
if strongest >= high_confidence(0.82/0.90/0.96) {
    → 直接进入 Correlate 或 Intervene
    → 完全不看另一个层的分数
}
```

只有**两个层都中等**时才走加权路径，且加权路径要求 `weakest >= threshold * 0.70`（佐证条件）。

### 行为评分：单一类型不刷分

源码注释：

> *"...writes or network callbacks cannot manufacture a high score."*

**攻击面**：攻击者用大量无害的同类操作（如几千次文件写入）刷高行为分。

**应对**：`score_events` 要求**跨类型组合**才能拿到额外加成（+0.18 / +0.18 / +0.24）。单一类型的重复事件只会累加基础权重，上限受限。

### 宽容序列：必须独立佐证

**攻击面**：宽容签名容忍交错噪声（这是为真实恶意软件设计的），因此单独一条宽容签名不能定罪。

**应对**：升级到 `Intervene` 需要四条条件之一：

- 行为分达到响应级别阈值；
- ≥2 条宽容签名 + 沙箱出现独立动作标志（`files_changed` / `network_activity` / `registry_activity` / `api_activity` / `unpacked`）；
- ≥2 条宽容签名 + 事件种类 ≥3；
- ≥2 条宽容签名 + 行为分 ≥0.5。

### 内核模型：不复用为独立证据

**攻击面**：如果内核模型分被当作"独立行为证据"喂回融合器，就形成"同一份输入算两次"的循环论证——攻击者只需欺骗输入一次，就能影响两个"独立"信号。

**应对**：引擎的 `record_kernel_behavior_event` **刻意不**把 `MODEL_SCORE` 映射成行为事件。

### 静态沙箱：多族佐证 + 上限

**攻击面**：单一能力族的静态命中可能是巧合。

**应对**：

```
calibrated() = residual_product + (n - 1) * 0.025   // n = 命中族数
clamp 到 0.95
```

多族命中才累积加成，且**永不给出 1.0**——保留"不确定"这一状态。

### 对抗训练

`tools/train_adversarial_model.py` 用 PGD（Projected Gradient Descent）在**特征空间**做对抗训练，提升模型对微扰的鲁棒性。严格限定：

- **防御性**：只训练模型，不生成攻击样本；
- **不编辑输入文件，不产出可执行样本**。

### 12 维特征契约的鲁棒性价值

特征维度低（12 维）是**刻意的**：

- 攻击者通过微扰欺骗高维模型的自由度更大；
- 低维特征空间更容易人工审计与解释；
- 12 维中的多数特征（节区数、导入数、熵）与文件功能强相关，微扰它们通常会破坏文件可用性。

### 完整性自校验

| 校验 | 环境变量 | 作用 |
|------|----------|------|
| 引擎二进制 | `EVERBLOOM_BINARY_INTEGRITY_MANIFEST` | 防止引擎被替换/打补丁 |
| YARA 规则 | `EVERBLOOM_RULE_INTEGRITY_MANIFEST` | 防止规则被替换成空集 |
| 驱动文件 | `EVERBLOOM_DRIVER_SHA256` | 防止驱动被替换 |

引擎启动时若二进制摘要不匹配，**记录错误并拒绝进入服务状态**。

### 内核策略不可绕过

内核策略在**用户态缓存之前**查询：

```rust
if protection_state::driver_enabled() {
    match driver_bridge.scan_file(&path) {
        Ok(verdict) if verdict.blocked => { /* 直接返回恶意 */ }
        ...
    }
}
```

**攻击面**：如果先查用户态缓存，攻击者可以让一个已被内核规则封禁的文件返回缓存的 Clean 结果。

**应对**：内核策略是强制执行权威，必须在缓存之前问。

### 白名单不豁免权威证据

**攻击面**：攻击者诱导用户把恶意文件加入白名单，从此免检。

**应对**：白名单只压制静态/AI 的噪声判定；**精确哈希命中、YARA 命中、动态行为**仍然执行且保持权威。

## 11.7 可用性与降级

### 降级矩阵

| 组件不可用 | 行为 |
|------------|------|
| 驱动未安装 | 引擎完整可用，能力查询返回控制面能力，`--driver-status` 退出码 3 |
| 驱动协议不兼容 | 退出码 4；引擎不尝试使用 |
| 驱动可选拦截面被拒绝 | 该面降级，其余防护继续，能力位停止声明该面 |
| AI 模型加载失败/超时 | `AiScore.is_fallback = true` + `fallback_reason`；**不静默返回 0 分** |
| YARA 规则加载 0 条 | `reload_rules` 返回加载数量，使"规则存在但没加载"可见 |
| ClamAV 不可用 | 750 ms 超时后放弃，300 s 内不再尝试 |
| 沙箱两个后端都不可用 | **fail-closed**，报告 `sandbox_unavailable` |
| 沙箱清理未确认 | 报告为**不可信结果**，而非"干净执行" |
| 稠密树模型缺失 | 构建期静默排除（只打印提示），运行时不加载 |
| 哈希库缺失 | 清空 `EVERBLOOM_HASH_DB`，该层不参与 |
| GUI 找不到引擎 | 返回带完整路径的错误，不静默失败 |

### "失效必须可见"原则

产品在多处刻意让降级状态**可观测**：

| 机制 | 暴露什么 |
|------|----------|
| `AiScore.is_fallback` / `fallback_reason` | AI 层是否降级及原因 |
| `YaraScanner::version()` / `reload_rules() -> usize` | 实际加载的规则数 |
| `EVERBLOOM_EVENT_READ_RESPONSE.Dropped` | 内核事件丢弃计数 |
| `m_r3_event_window_suppressed` | GUI 侧被压制的事件数 |
| `SandboxUnpackingReport::unavailable(reason)` | 内存采集为何没做 |
| `--driver-status` 的 `capability_flags` | 内核实际提供的能力 |
| `rollback_actions` 里的 `rollback_error:` 前缀 | 哪些回滚动作失败 |
| `SandboxReport` 的 `isolation_verified` / `cleanup_verified` | 沙箱结果是否可信 |

**一个"悄悄失效"的检测层比没有这一层更危险**——用户会以为自己在被保护。

### 报告的可信度标记

沙箱结果只有在 `isolation_verified && cleanup_verified` 都为真时才被认为可信。这不是可选的装饰——它直接影响扫描器是否把沙箱观察作为证据。

## 11.8 合规与分发

### 不携带真实恶意代码

| 位置 | 内容 |
|------|------|
| `tests/corpus/malicious/` | **合成**样本（EICAR 变体、Emotet/Qakbot 风格） |
| `engine/src/layers/synthetic.rs` | 合成 PE 生成器，内嵌 `EVERBLOOM-SYNTHETIC-CORPUS-NOT-MALWARE` 标记 |
| `data/indicators.db` | IoC 指标（哈希、域名、IP、URL），**不是**可执行文件 |

合成样本的标记有三重作用：

1. 真实杀毒软件不会误报；
2. 人工分析者能立即识别；
3. `validate_output_root()` 可校验输出目录，防止语料被当作真实样本分发。

### 第三方检测内容的完整性

`engine/Heuristic/MALW_LinuxHelios.yar` 是**第三方** YARA 规则（Linux.Helios 家族，2017 年，作者 Joan Soriano，含真实 MD5/SHA256）。

这份规则中的 `Helios` 是**恶意家族名**，与产品曾用名 `HeliosAV` **无关**。在 2026-10-01 的全树改名中，这 4 个文件（规则本体 + 3 个 index 的 `include` 行，共 5 行）被**显式排除**并逐字节还原：

- 改了会让检测失效；
- 更重要的是，会把真实威胁**错误归因**到本产品。

这是一个通用原则：**第三方内容里的标识符不属于本产品的命名空间**。

### 数据来源授权

| 源 | 授权模型 |
|----|----------|
| MalwareBazaar | 公开 API |
| URLhaus | 公开，**仅在线查询** |
| ThreatFox | 需要 `THREATFOX_AUTH_KEY` |
| EMBER 2018/2025 | 学术数据集 |
| 本地数据集 | `import_real_dataset.py` 只读操作者指定的路径，**从不联网** |

### 沙箱的平台合规

Windows Sandbox 的使用受 Windows 版本许可限制（Pro / Enterprise / Education）。产品在功能不可用时**明确告知**，而不是尝试绕过。

### 驱动签名的分发阶段

- **测试签名 / 自签名**：开发与内部部署可用，`329671` altitude 可直接使用；
- **WHQL / 认证签名**：正式分发需要，此时才需要向 Microsoft 申请 altitude 分配。

**Microsoft 分配是分发前的文书步骤，不是功能前提**——不应把驱动落地卡在这一步。

## 11.9 威胁模型

### 防护的威胁

| 威胁 | 主要防线 |
|------|----------|
| 已知恶意软件 | 哈希（精确 + 模糊）、YARA、威胁情报 |
| 未知恶意软件 | 启发式、AI、静态沙箱预测 |
| 加壳/混淆样本 | 熵分析、解包评估、内存快照 |
| 勒索软件 | 内核写入追踪（快/慢双窗口）、静态沙箱 `recovery_inhibition` |
| 凭据窃取 | Cookie 防护（用户态 + 内核双层） |
| 无文件攻击 | 行为序列、HIPS |
| BYOVD | basename 精确清单（用户态 + 内核双层） |
| 横向移动 | 网络策略（WFP） |
| 持久化 | 注册表回调、文件过滤 |
| 注入攻击 | 内核对象句柄回调、启发式注入链 |

### 产品自身的威胁

| 威胁 | 防线 |
|------|------|
| 引擎被替换/打补丁 | 二进制 SHA-256 自校验 |
| 规则被替换成空集 | 规则完整性清单 |
| 驱动被替换 | `EVERBLOOM_DRIVER_SHA256` |
| 用户被诱导加白名单 | 白名单不压制权威证据 |
| 缓存绕过新策略 | 内核策略优先于缓存 |
| 融合器被"拉平" | 高置信信号不被平均 |
| 行为分被刷 | 跨类型组合要求 |
| 内核模型被当独立证据 | 刻意不回灌 |
| 事件静默丢失 | `Dropped` 计数 + 压制计数可见 |
| 沙箱逃逸 | 无直接宿主执行路径；fail-closed |
| 沙箱清理失败被误判为干净 | `cleanup_verified` 标记 |
| 降级被误认为正常 | 所有降级路径显式标记 |

### 明确不在防护范围

| 项 | 说明 |
|----|------|
| 物理访问攻击 | 不在产品范围内 |
| 供应链攻击（编译器/依赖） | 部分覆盖（完整性清单），但依赖树本身未做验证 |
| 内核漏洞利用 | 驱动自身可能有漏洞，产品不防护自己的内核代码 |
| 固件/BIOS 层威胁 | 不在范围内 |
| 社会工程学 | 不在范围内 |
| 客户机内丰富的动态遥测 | 当前两个沙箱后端都不导出（见 11.3） |

## 11.10 设计原则总结

贯穿全项目的能力考量，可以归纳为十条原则：

| # | 原则 | 体现 |
|---|------|------|
| 1 | **决策在用户态，内核只拦截** | 内核 2,847 行，只查表与匹配 |
| 2 | **权威与证据分离** | 哈希/YARA/ClamAV/情报/严格序列 = 权威；启发式/AI/行为/静态沙箱 = 证据 |
| 3 | **高置信不被平均** | `strongest >= high_confidence` 直接定案 |
| 4 | **失效必须可见** | `is_fallback`、`Dropped`、`suppressed`、`cleanup_verified`、`rollback_error:` |
| 5 | **失败即关闭（沙箱）** | 无直接宿主执行降级路径 |
| 6 | **能力由事实派生，不硬编码** | `EverbloomKernelComponentsCapabilityFlags()` |
| 7 | **声明自己的能力边界** | `SANDBOX_SECURITY.md` 明说 AppContainer 不是 VM、不导出丰富遥测 |
| 8 | **不存原始样本** | 特征向量 + 标签 + 元数据 |
| 9 | **本地优先，默认不出网** | YARA/启发式/AI 全本地；云查杀默认关闭 |
| 10 | **第三方内容不属于本产品命名空间** | Linux.Helios 规则保持原名 |
