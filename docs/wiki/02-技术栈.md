| `sha2` / `sha1` / `md-5` | 0.10 | 哈希匹配层的三种摘要 |
| `hex` | 0.4 | 摘要十六进制表示 |
| `getrandom` | 0.2 | 隔离区密钥、随机 ID |
| `thiserror` | 1.0 | 错误类型派生 |
| `log` | 0.4 | 日志门面 |
| `serde` / `serde_json` | 1.0 | 全部 JSON 序列化（配置、NDJSON 帧、报告） |
| `csv` | 1.3 | 数据集与导出 |
| `rusqlite` | 0.31（bundled） | 哈希库 / 威胁情报 SQLite，内嵌 SQLite 免外部依赖 |
| `yara` | 0.32（vendored, bundled-4_5_5, ndebug） | YARA 4.5.5 静态编译进二进制，无需外部 DLL |
| `libc` / `nix` | 0.2 / 0.27 | 平台系统调用（沙箱后端、文件属性） |
| `goblin` | 0.7 | PE/ELF/Mach-O 解析（启发式与静态沙箱） |
| `tract-onnx` | 0.23.4 | **纯 Rust** ONNX 推理，无需 onnxruntime DLL |
| `prost` / `bytes` | 0.11 / 1.4 | 遗留 IPC 的 protobuf 编解码 |
| `hyper` | 0.14（full） | HTTP 客户端（威胁情报在线源） |
| `walkdir` | 2.3 | 目录递归枚举 |
| `tempfile` | 3.5 | 沙箱与解包临时目录 |
| `lazy_static` | 1.4 | 全局单例 |
| `windows-sys` | 0.61.2 | Win32 API 绑定，启用 20 个 feature 分组 |

**为什么选 `tract-onnx` 而不是 `onnxruntime`**：`tract` 是纯 Rust 实现，编译进二进制后没有原生 DLL 依赖、没有版本冲突、不需要随包分发 C++ 运行时。代价是不支持全部 ONNX 算子——因此训练侧的导出脚本会做算子兼容性转换（见 `tools/convert_feature_cnn_for_tract.py`、`docs/onnx_model_compatibility.md`）。

**为什么选 `yara` 的 `bundled-4_5_5`**：YARA 规则文件是安全行业的事实标准，静态链接保证规则引擎版本与规则集版本可精确对应，避免"用户机器上装了别的 YARA"这类不可复现问题。

> **命名澄清**：本项目用的是 **`yara` crate**（`0.32`），它是 **YARA C 库 4.5.5 的 Rust 绑定**，通过 `bundled-4_5_5` feature 把 C 库源码一起编译进来。
> 它**不是** `yara-x` —— `yara-x` 是 VirusTotal 用纯 Rust 重写的下一代 YARA 实现，与本项目无关。全仓库不含任何 `yara-x` / `yara_x` 依赖或引用。

**`windows-sys` 启用的 feature 分组**（体现引擎实际用到的 Win32 能力面）：

```
Win32_Foundation, Win32_Graphics_Gdi, Win32_Security,
Win32_Security_Authorization, Win32_Security_Isolation, Win32_System_Antimalware,
Win32_System_Com, Win32_System_Diagnostics_Etw, Win32_System_Diagnostics_Debug,
Win32_System_JobObjects, Win32_System_Kernel, Win32_System_StationsAndDesktops,
Win32_System_Threading, Win32_System_SystemServices, Win32_System_Time,
Win32_System_Diagnostics_ToolHelp, Win32_System_Memory, Win32_System_IO,
Win32_Storage_FileSystem
```

其中 `Win32_System_Antimalware` 用于 AMSI 提供者注册，`Win32_Security_Isolation` + `Win32_System_JobObjects` + `Win32_System_StationsAndDesktops` 用于沙箱的 AppContainer 后端，`Win32_System_Diagnostics_Etw` 用于行为监视。

### 代码规模

- `engine/src/` 共 **37,673 行**，其中**实际参与编译的约 35,901 行**。
- `lib.rs` 只声明 `pub mod quarantine;`，因此以下文件**不参与编译**（保留为开发中间产物）：`quarantine_clean.rs`（832 行）、`quarantine_fixed_backup.rs`（807 行）、`quarantine_new.rs`（108 行）、`quarantine_header_fixed.rs`（25 行）。
- `unsafe` 使用约 **127 处**，集中在三个文件：`sandbox.rs`（71）、`hips.rs`（17）、`driver_bridge.rs`（10）——即所有需要直接调用 Win32 API 的地方。检测逻辑层（`layers/`）几乎不含 `unsafe`。

## 2.3 内核驱动技术栈

### 构建配置（`driver/CMakeLists.txt`）

```cmake
project(everbloom_driver LANGUAGES CXX)
set(CMAKE_CXX_STANDARD 17)
set(CMAKE_MSVC_RUNTIME_CHECKS "")
set(CMAKE_VS_GLOBALS "TrackFileAccess=false")
```

### 工具链要求（非标准位置）

| 组件 | 路径 | 说明 |
|------|------|------|
| MSVC 编译器 | `F:/insiders/VC/Tools/MSVC/14.51.36231/` | cl `19.51.36252.0` |
| Windows SDK（用户态头/库、`rc.exe`/`mt.exe`） | `C:/Program Files (x86)/Windows Kits/10/`，版本 `10.0.26100.0` | **必须在 PATH 上**，否则 CMake 编译器探测阶段即失败 |
| WDK 内核工具链 | 同目录，版本 **`10.0.28000.0`** | `10.0.26100.0` **没有 `km` 树** |
| `Inf2Cat.exe` | `10.0.28000.0/x86/` | 目录编目工具，26100 里没有 |

WDK `km` 树提供内核头（`ntddk.h`、`fltKernel.h`、`wdmsec.h`、`crt/`）与库（`Lib/10.0.28000.0/km/x64/`：`ntoskrnl`、`fltMgr`、`fwpkclnt`、`BufferOverflowK`、`wdmsec`、`ntstrsafe`）。

### 构建产物

| 目标 | 类型 | 说明 |
|------|------|------|
| `everbloom_driver.sys` | Kernel driver | x64、Native 子系统、`DriverEntry` 入口、导入 FLTMGR + fwpkclnt |
| `everbloom_driver_core` | Static lib | 用户态仿真桩的静态库 |
| `everbloom_driver_stub.exe` | Console exe | 用户态桩程序 |
| `everbloom_kernel_matrix_tests.exe` | Console exe | 整数推理核心测试（106 断言），**在 WDK guard 之外** |
| `everbloom_kernel_altitude_tests.exe` | Console exe | altitude 算术测试（61 断言），**在 WDK guard 之外** |

两个测试目标刻意放在 `BUILD_EVERBLOOM_DRIVER_SYS` 守卫**之外**，这样在没装内核工具链的机器上也能构建运行——它们是模型数学与 altitude 算术唯一的自动化检查手段。

### 编码约束

- **内核源码必须纯 ASCII**。工具链按 codepage 936 编译，注释里出现 U+2014（em dash）等字符会触发 `C4819`。内核侧统一用 `-` 代替排版破折号。

## 2.4 桌面 GUI 技术栈

### 构建配置（`gui/CMakeLists.txt`）

```cmake
set(CMAKE_CXX_STANDARD 23)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(EVERBLOOM_VCPKG_TRIPLET "x64-windows")
set(EVERBLOOM_CPPWINRT_VERSION "2.0.250303.1")
```

### Windows App SDK 固定版本

| 组件 | 版本 | 来源 |
|------|------|------|
| `Microsoft.WindowsAppSDK`（bundle） | **2.3.1** | `external/nuget/Microsoft.WindowsAppSDK.2.3.1` |
| `Microsoft.WindowsAppSDK.Foundation` | 2.3.5 | NuGet |
| `Microsoft.WindowsAppSDK.Runtime` | 2.3.1 | NuGet |
| `Microsoft.WindowsAppSDK.WinUI` | 2.3.0 | NuGet |
| `Microsoft.WindowsAppSDK.InteractiveExperiences` | 2.1.3 | NuGet |
| cppwinrt 工具 | `2.0.250303.1` | `vcpkg/installed/x64-windows/tools/cppwinrt/` |

`gui/CMakeLists.txt` 在配置阶段做**强制版本校验**：读 `Microsoft.WindowsAppSDK.nuspec`，若 bundle 版本不符即 `FATAL_ERROR`；执行 `cppwinrt.exe -help` 并用正则 `C\+\+/WinRT v([0-9.]+)` 提取实际版本，与 `EVERBLOOM_CPPWINRT_VERSION` 不符同样 `FATAL_ERROR`。这样避免了"构建机上的工具链悄悄升级导致投影 ABI 漂移"。

### C++/WinRT 投影生成

配置阶段通过 `add_custom_command` 调用 `cppwinrt.exe`，把 Windows App SDK 的 5 个 `.winmd` 生成 C++ 投影头，产出 `winrt_generated/` 目录，并用 `everbloom_winrt_projection.stamp` 做增量标记（`add_custom_target(everbloom_winrt_projection)`）。

参与投影的 winmd：

```
Microsoft.UI.Xaml.winmd                          (WinUI 2.3.0)
Microsoft.UI.Text.winmd                          (WinUI 2.3.0)
Microsoft.Windows.ApplicationModel.Resources.winmd (Foundation 2.3.5)
Microsoft.UI.winmd                               (InteractiveExperiences 2.1.3)
Microsoft.Graphics.winmd                         (InteractiveExperiences 2.1.3)
```

> **注意**：本项目的 `cppwinrt.exe` 调用**只为 Windows App SDK 生成投影**，不生成 `Everbloom*` 自定义控件的 `.g.cpp`。仓库中签入的 `EverbloomButton.g.h` 等文件是 `#pragma once` + `#include "X.h"` 的空壳。自定义控件因此不参与构建（见第 7 章）。

### 编译选项

```
/permissive- /Zc:__cplusplus /utf-8 /EHsc /Zi
```

`/utf-8` 是关键：GUI 源码含大量中文字面量，缺了它会按本地 codepage 解释而报错。

### 运行时 MSIX

GUI 依赖 Windows App SDK 运行时。4 个 MSIX 包从 `Microsoft.WindowsAppSDK.Runtime.2.3.1/tools/MSIX/win10-x64` 复制到安装树的 `share/everbloom/windows-app-runtime/win10-x64/`，由 `install_windows_app_runtime.cmd` 在安装时注册。

## 2.5 辅助技术栈

| 模块 | 技术 | 关键依赖 |
|------|------|----------|
| `libeverbloom_rs` | Rust cdylib + PyO3 0.29 | `everbloom_engine`（path 依赖）、`pelite 0.10`、`aho-corasick 1.1`、`lru 0.8`、`parking_lot 0.12`、`memmap2 0.9`、`notify 6.1`、`flume 0.11`、`windows 0.48`、`sandbox_monitor` |
| `sandbox_monitor` | Rust bin/lib | `reqwest 0.12`（HTTP 上报）、`windows-sys`（ETW）、`nix 0.30` |
| `edr` | Rust lib | `serde`、`serde_json`、`chrono 0.4` |
| `python/` | Python 包 | 三个子包：`everbloom_config`、`everbloom_core`、`everbloom_viz` |
| `proto/` | Protobuf | `messages.proto`：`ScanRequest` / `ScanResponse` / `ScanProgress` / `ConfigUpdate` / `Heartbeat` |

`libeverbloom_rs` 通过 `path = "../engine"` 直接复用引擎 crate，因此 Python 侧调用的是**与桌面版完全相同的检测实现**，不存在两套逻辑分叉。
